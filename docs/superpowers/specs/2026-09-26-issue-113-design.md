# Translating the font-download errors and the SD-card error

Design note for issue #113, on `fix/113-i18n-font-download-sd-error`.
Research: `docs/superpowers/research/2026-09-26-issue-113-research.md`.
Modelled on: `docs/superpowers/specs/2026-09-23-store-refusal-surfacing-design.md`, which uses the same numbered-decision layout and also moved on-screen error text into new `STR_*` keys in `english.yaml` and `spanish.yaml` (commit `32f66774`, #82).

## Changes after spec review 0

Review: `docs/superpowers/reviews/issue-113-spec-review-0.md` (CLEAR).
- **MAJOR 1:** two Spanish file-name prefixes overflowed 480 px with real file names. They are shortened, and the measurement is recorded in A4.
- **MINOR 1:** the fallback check in testing step 2 now uses `-v`, without which it could not fail.
- **MINOR 2:** the claim that `-Wformat` checks the new format strings is removed.
- **MINOR 3:** "Fallo de descarga" now matches the existing `STR_DOWNLOAD_FAILED`, and the shortened checksum wording is explained in A7.

## Problem

CLAUDE.md requires every piece of user-facing text to go through `tr()`. Two places draw hardcoded English instead:

- **`FontDownloadActivity`** assigns English literals to `errorMessage_` (`src/activities/settings/FontDownloadActivity.h:83`) at 11 sites: `FontDownloadActivity.cpp:92, 102, 113, 120, 148, 295, 358, 370, 380, 392, 432`. The ERROR branch of `render()` draws that string under the already-translated heading `tr(STR_FONT_INSTALL_FAILED)` (`:674-681`). Four of the 11 sites (`:358, 370, 380, 392`) add the manifest file name to the literal, for example `"Download failed: " + file.name`. The issue lists only 7 lines. The other 4 are the same defect on the same screen.
- **`src/main.cpp:405`** calls `activityManager.goToFullScreenMessage("SD card error", EpdFontFamily::BOLD)`.

## Goal

- Every string that reaches the screen on those 12 paths comes from a `STR_*` key.
- Each new key has an English value and a Spanish value.
- English output is unchanged byte for byte.

## Non-goals

- **Translating into the other 30 languages.** `gen_i18n.py` falls back to English for any key a language file lacks (`scripts/gen_i18n.py:217-222`), which is what the issue asks for ("`spanish.yaml` at least").
- **Showing the SD-card error in the user's language.** This is impossible; see A5.
- **Fixing how the error line draws when it is too wide.** `drawCenteredText` computes `x = (screenWidth - textWidth) / 2` and draws without clipping or wrapping (`lib/GfxRenderer/GfxRenderer.cpp:624-628`). A line wider than the screen gets a negative `x` and is cut off at both edges. That behaviour already exists for the English strings with long file names. This change keeps the Spanish strings short (A4) rather than rewiring the render.
- **The unlocked `errorMessage_` write inside `fetchAndParseManifest()`.** That write (`:92-148`) happens outside `RenderLock`, while the caller takes the lock only for `state_ = ERROR` (`:66-71`). This is an existing threading question unrelated to translation. The change keeps the current locking exactly.
- **Adding a check that format specifiers match across languages.** See A6.
- **Any change to `LOG_ERR` text.** Log messages may stay hardcoded under CLAUDE.md.

## Assumptions (each one is a decision the review should attack)

**A1: This task edits `english.yaml`, `spanish.yaml` and `src/main.cpp` itself.**
`.claude/agents/ui-dev.md` names those files as shared append points: it says to put the line in the PR description and let the orchestrator apply it. Issue #113 explicitly asks for keys in both YAML files and a change at `main.cpp:405`, and this task owns #113 alone in its own worktree. The rule exists to stop two agents editing the files in parallel. This branch rebases onto `main` right before `implement`, as the pipeline's re-read rule requires, and each addition is appended as its own new lines, so a conflict with a sibling's appended keys stays textual and trivial. If the orchestrator disagrees, the fallback is to list the exact YAML lines and the `main.cpp` line in the PR body, as `ui-dev.md` describes.

**A2: New dedicated keys, not reuse of `STR_DOWNLOAD_FAILED` or `STR_CHECKSUM_MISMATCH`.**
- `STR_DOWNLOAD_FAILED` ("Download failed", `english.yaml:216`) carries no file name. Reusing it would mean concatenating `": " + name` in code, which leaves a hardcoded `": "` separator that a translator cannot move.
- `STR_CHECKSUM_MISMATCH` ("Checksum mismatch, download discarded", `english.yaml:460`) has different wording. Reusing it would break the goal that English output stays byte-identical.
- `FontDownloadActivity.cpp:113` and `:148` share a key, because their text is identical today.

**A3: File-name messages are `%s` format keys filled with `snprintf`, not `tr()` joined to the name with `+`.**
This mirrors `BibleSearchActivity.cpp:830` (`snprintf(statusLine, sizeof(statusLine), tr(STR_BIBLE_SEARCH_STATUS), name, chapter)`) and the key `STR_BIBLE_SEARCH_STATUS: "%s · chapter %d"` (`english.yaml:39`, Spanish at `spanish.yaml:37`). It also matches CLAUDE.md's string policy (`snprintf` into a fixed `char[]`). The concatenation form at `FontDownloadActivity.cpp:653` was rejected because it fixes the word order in code.
- The buffer is a local `char message[128]`, within CLAUDE.md's 256-byte limit for stack locals. It is copied into `errorMessage_` (a `std::string`, `:83`), which the render reads.
- A longer message is truncated by `snprintf`. It would not fit on one line of the screen anyway (Non-goals).
- `file.name` is only ever passed as a `%s` argument, never as the format, so a `%` in a manifest file name is safe.

**A4: English stays byte-identical, and each Spanish string is kept close to its English length.**
The error line is drawn with no wrapping, as described under Non-goals, so a Spanish string much longer than its English original could push an otherwise-fitting line off the panel. Where a literal Spanish translation runs long, the shorter idiomatic form wins. The Spanish noun for "font" is "tipografía", as in the existing keys at `spanish.yaml:340, 342, 343`.

The widths were measured, not estimated. Spec review 0 summed `advanceX` from `lib/EpdFont/builtinFonts/ubuntu_10_regular.h`, the font behind `UI_10_FONT_ID` (`main.cpp:327`), against real manifest file names. Those names are `<Family>_<size>.cpfont` (`scripts/generate-font-manifest.py:16,177`), for example `NotoSerifExtended_14.cpfont`.
- All seven plain keys fit within 480 px. The widest is "No se pudo crear la carpeta de tipografías" at about 394 px.
- `STR_FONT_FILE_INVALID` and `STR_FONT_FILE_CHECKSUM_MISMATCH` were first drafted as "Archivo de tipografía no válido: %s" and "Suma de verificación errónea: %s". With the file name added, they measured 514-583 px where the English lines fit. They are now "Archivo no válido: %s" (at most about 456 px) and "Suma no coincide: %s" (about 458 px). The file name already carries the "font" sense.

**A5: The SD-card error goes through `tr()` but will always render in English.**
- The failure branch (`main.cpp:402-406`) returns before `SETTINGS.loadFromFile()` and before `I18N.setLanguage(...)` at `main.cpp:414`.
- `I18n` starts at `Language::EN` (`lib/I18n/I18n.h:33`).
- The language setting lives on the SD card that just failed to mount, so it cannot be read here.

The change meets the `tr()` rule and makes the string translatable if the startup order ever changes. The PR must not claim a Spanish SD-error screen.

**A6: No new host test. The red step of TDD is the i18n generator.**
- No host test exists for `FontDownloadActivity` or for `I18n` (research §7). The activity depends on Arduino, WiFi, HalStorage and the renderer, none of which the host suites build against.
- A new test harness just to assert string-table contents would invent a pattern this repo does not have.
- `gen_i18n.py` already fails the build when source references a `STR_*` key that is missing from `english.yaml` (`scripts/gen_i18n.py:872-881`). It does not check that `%s` specifiers agree between languages. That is a known gap across all format keys, and closing it belongs in its own issue.
- For the four new format keys, the plan includes a manual check that each Spanish value contains exactly one `%s` and no other conversion.

**A7: The Spanish wording below is final unless review objects.**
No native-speaker review step exists in this repo. The existing Spanish file is the style reference.
- `STR_FONT_FILE_DOWNLOAD_FAILED` uses "Fallo de descarga", the wording of the existing `STR_DOWNLOAD_FAILED` (`spanish.yaml:207`).
- "No se pudo verificar: %s" for "Failed to compute checksum" is a deliberate shortening. It drops the word "checksum" to stay within the width budget in A4.

## Architecture

There is no new component, mechanism or format. The change is confined to:

1. `lib/I18n/translations/english.yaml` and `spanish.yaml`: 11 new lines each.
2. `src/activities/settings/FontDownloadActivity.cpp`: 12 assignment sites rewritten. Everything else is untouched: the error-branch render at `:674-681`, the `errorMessage_` type, and `state_`, which each site sets before assigning the message.
3. `src/main.cpp:405`: the literal is replaced with `tr(STR_SD_CARD_ERROR)`. `goToFullScreenMessage` takes a `std::string` (`src/activities/ActivityManager.h:91`), which is built implicitly from the `const char*`.

The generated `I18nKeys.h`, `I18nStrings.h` and `I18nStrings.cpp` are gitignored and rebuilt by the PlatformIO `pre:` step (`platformio.ini:131`). They are never committed.

## Data and control flow

Plain sites (7 of them). Before and after:

```cpp
errorMessage_ = "Invalid font manifest";
errorMessage_ = tr(STR_FONT_MANIFEST_INVALID);
```

`tr()` returns a `const char*` into a flash-resident string table (`lib/I18n/I18n.h:39`), and `std::string::operator=` copies it. The same thing happens today with the literal. The only difference is the source of the pointer.

File-name sites (4 of them), inside the `RenderLock` scope each site already holds:

```cpp
char message[128];
snprintf(message, sizeof(message), tr(STR_FONT_FILE_DOWNLOAD_FAILED), file.name.c_str());
errorMessage_ = message;
```

Heap: today's `"literal" + file.name` builds a temporary `std::string`, then assigns it. The new code builds no temporary and copies the formatted text straight into `errorMessage_`. That is at most one heap allocation, the same as today's final assignment, and there are no new allocations.

Render: unchanged. `render()` still draws `errorMessage_.c_str()` (`:678`).

The SD error at `main.cpp:405` follows the same path as today, apart from where the string comes from (A5).

## Error handling

Nothing new can fail:
- `tr()` always returns a valid pointer, falling back to English when a language lacks the key (A1, `gen_i18n.py:217-222`).
- `snprintf` into a fixed buffer truncates instead of overflowing (A3).
- A Spanish value whose specifiers do not match the English value would be undefined behaviour in `snprintf`. A6's manual check guards the four format keys.

The existing failure paths (`state_ = ERROR`, cleanup via `fontInstaller_.deleteFamily`, the Retry hint) are untouched.

## Testing strategy

1. **Red.** Rewrite the call sites first, then run `python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/`. It must exit 1 with `CRITICAL: 11 string(s) used in source but missing from english.yaml`, listing exactly the 11 keys above.
2. **Green.** Add the English and Spanish keys and rerun the generator. It must exit 0 with `String keys: 486` (475 + 11). Then run `python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/ -v | grep "missing in ES"`. None of the 11 new keys may appear in its output. The fallback lines print only with `-v` (`gen_i18n.py:217-222`).
3. **No literal left.** `grep -n 'errorMessage_ = "' src/activities/settings/FontDownloadActivity.cpp` returns nothing, and `grep -n '"SD card error"' src` returns nothing.
4. **Format specifiers.** Each of the four `STR_FONT_FILE_*` values in both files contains exactly one `%s` and no other `%` conversion. The check is `grep -n 'STR_FONT_FILE_' lib/I18n/translations/{english,spanish}.yaml`, read by eye.
5. **Build.** `pio run` (env `x4pro`) succeeds with no new warnings. The compiler cannot check that a translated format string's specifiers match its arguments, because `tr()` is a runtime `const char*` (`I18n.h:39`). Step 4 is the only guard.
6. **Host suite.** It should run unchanged, as a regression check. No new test (A6).
7. **Format.** `./bin/clang-format-fix` over the whole tree.

**For the human tester (device):**
- With the UI language set to Spanish, force a font-browser error, for example by turning off WiFi after the network is joined so the manifest fetch fails. Confirm the Spanish detail line shows and fits.
- In Spanish, provoke one file-level error on a long-named family, for example by pulling WiFi mid-download of `NotoSerifExtended`. Confirm the "Fallo de descarga: …" line is not clipped.
- Boot with no SD card inserted. Confirm "SD card error" still shows, in English, as A5 predicts.
