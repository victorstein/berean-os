# Dropping serial logging from the release build

Design for issue #112, on `fix/112-release-serial-logging` at `f82737e9` (base `2f303f6f`).
Research: `docs/superpowers/research/2026-09-26-issue-112-research.md` (cited below as *R §n*).

**Modelled on `27369bdd`** (`ci: build one board, and fix the release repo guard`). That commit is
this fork's most recent edit to the `x4pro-gh_release` env. It was a `platformio.ini` change, and
every file that described the env moved in the same commit (R §6). This spec keeps that shape: one
flag change, plus the documents that describe the flag. No spec in `docs/superpowers/specs/` covers a
build-flag-only change, so the section layout follows `2026-09-19-issue-63-design.md`.

---

## Problem

AGENTS.md (CLAUDE.md is a symlink to it, R §1) documents two things about the build that are not
true.

1. It says `x4pro-gh_release` is "production, `LOG_LEVEL=0`, no serial logging"
   (`AGENTS.md:173-174`, repeated at `:854-855`). The env actually sets `-DENABLE_SERIAL_LOG`
   (`platformio.ini:187`) and `-DLOG_LEVEL=1` (`platformio.ini:188`).
2. It says the standard is `-std=c++2a` (`AGENTS.md:176`). The build uses `-std=gnu++2a`
   (`platformio.ini:40`).

Because of (1), the build that OTA installs (`.github/workflows/release-publish.yml:44`):

- calls `Serial.begin(115200)` at boot, after a `delay(250)` (`src/main.cpp:342-353`);
- prints every `LOG_ERR`/`LOG_INF` to USB CDC (`lib/Logging/Logging.h:44-56`,
  `lib/Logging/Logging.cpp:71-73`);
- has a live serial command handler (`src/main.cpp:618-633`). `CMD:SCREENSHOT` dumps the 48,000-byte
  framebuffer to the host. And if any byte is waiting, `readStringUntil('\n')` blocks `loop()` for
  up to `Stream::_timeout`, 1000 ms by default (framework `cores/esp32/Stream.h:62`; R §2 step 3).

## Goal

The owner decided on #112: drop serial logging from the release build.

- **G1.** `x4pro-gh_release` builds without `ENABLE_SERIAL_LOG`, with `LOG_LEVEL=0`.
- **G2.** In the release build, the `CMD:` handler never runs and never blocks `loop()`.
- **G3.** AGENTS.md matches `platformio.ini` on both points: the logging (becomes true by G1) and the
  C++ dialect (`gnu++2a`).
- **G4.** No user-facing document tells someone on the OTA build to do something that no longer
  works.

## Non-goals

- **N1.** The dev env `x4pro` (`platformio.ini:160-176`) does not change. It keeps
  `-DENABLE_SERIAL_LOG`/`-DLOG_LEVEL=2`, the handler, and `debugging_monitor.py`.
- **N2.** No replacement for the crash report's "Last logs" section (see A-4). A ring buffer that
  fills without serial logging would be a new mechanism, and a separate issue if the owner wants it.
- **N3.** No edit to `src/main.cpp` (see A-2).
- **N4.** No edit to the `freeink-sdk` submodule. Its `ENABLE_SERIAL_LOG` sites (R §1) follow the
  global define on their own.
- **N5.** Historical plans, specs and reviews under `docs/superpowers/` that quote
  `platformio.ini:187-188` as `LOG_LEVEL=1` stay as they are. They are dated records (R §7).
- **N6.** No change to `lib/Logging/`. The macro gate at `Logging.h:44-66` already does the right
  thing when the flag is absent.

## Assumptions

Each one is a decision the review can attack.

**A-1. Remove the flag; set `LOG_LEVEL=0` anyway.** Delete `platformio.ini:187`
(`-DENABLE_SERIAL_LOG`). Replace `:188` with `-DLOG_LEVEL=0`, with no trailing comment, because the
old one ("info for release builds") would become false. `LOG_LEVEL` is read only inside
`#ifdef ENABLE_SERIAL_LOG` (`Logging.h:44-61`), and `Logging.h:30-32` defaults it to 0 when unset.
So the line changes nothing in the compiled output. It stays because the owner asked for it, and
because it makes the env read the way AGENTS.md describes it. *Attack surface: a reader may take
`LOG_LEVEL=0` to mean "errors still log". It does not; A-7's doc wording says so.*

**A-2. G2 is met by runtime unreachability, not by compiling the handler out.** After A-1, nothing
calls `Serial.begin`:

- the only call is `src/main.cpp:349`, inside `#ifdef ENABLE_SERIAL_LOG` (`:342-353`);
- the Arduino core begins Serial itself only under `ARDUINO_USB_CDC_ON_BOOT && !ARDUINO_USB_MODE`
  (framework `cores/esp32/main.cpp:99-100`), and `ARDUINO_USB_MODE=1` (`platformio.ini:32`);
- the core's `printBeforeSetupInfo()` path is off: `ARDUHAL_LOG_LEVEL` 1 < DEBUG, and
  `shouldPrintChipDebugReport()` is the weak `false` (framework `main.cpp:43-60`, sdkconfig `:639`;
  R §2 step 1).

`HWCDC::begin` is what allocates `rx_queue` (framework `HWCDC.cpp:306-315`). With `rx_queue == NULL`,
`HWCDC::available()` returns `-1` (`HWCDC.cpp:562-565`), so `logSerial.available() > 0`
(`main.cpp:620`) is false on every loop. `readStringUntil` and the framebuffer dump never run.

The handler stays compiled in. R §8 measured the `SCREENSHOT_START` and `CMD:` strings in the
flag-removed binary. It is not wrapped in `#ifdef ENABLE_SERIAL_LOG`, even though that guard is the
established pattern (`main.cpp:342`, `HalPowerManager.cpp:70`,
`WifiSelectionActivity.cpp:552`), because `src/main.cpp` is a shared file this surface must not
edit (`.claude/agents/hal-dev.md`, "Shared files — report, do not edit"). The PR description carries
the exact guard for the orchestrator to apply if wanted:

```cpp
#ifdef ENABLE_SERIAL_LOG
  // Handle incoming serial commands,
  ...                                   // src/main.cpp:618-633 unchanged
#endif
```

*Attack surface: unreachability rests on nobody calling `Serial.begin` in release. A future
`CORE_DEBUG_LEVEL>=4`, a `shouldPrintChipDebugReport()` override, or a new `Serial.begin` outside the
`#ifdef` would bring the handler back without any diff to it. The guard above would close that. It
is offered, not applied, only because of the file-ownership rule.*

**A-3. The 250 ms boot delay goes too, and that is wanted.** `delay(250)` sits inside the same
`#ifdef` (`main.cpp:348`). It exists only to let USB enumerate before `Serial.begin` (comment at
`:343-347`). With no `Serial.begin` it has no purpose, and every release boot is about 250 ms faster.

**A-4. Release crash reports lose "Last logs"; accepted, and stated in the PR.**

- The RTC ring buffer is written only by `logPrintf` (`Logging.cpp:22,75`).
- `logPrintf` is reached only through the `LOG_*` macros (`Logging.h:46,52,58`), and those are empty
  without the flag (`Logging.h:62-66`). R §8 confirms `logPrintf`'s format prefix is gone from the
  binary.
- On this Xtensa board the stack section is already empty, because `__wrap_panic_print_backtrace`
  returns before filling `panicStack` under `#if !__riscv` (`lib/hal/HalSystem.cpp:47-49`).

So a release `/crash_report.txt` (`HalSystem.cpp:100-119`, `:131-139`) will hold the version, the
panic reason, and two empty sections. Upstream raised release logging to INFO in c40e92e4 partly for
crash-report content (R §6). The owner's decision reverses that, and the PR body must say so in one
sentence so the trade-off is visible at merge. `getPanicInfo` still prints the empty
`"Last logs:\n"` header; changing crash-report layout is out of scope (N2). *Attack surface: this
removes the only field diagnostics a release user can attach.*

**A-5. The heap print at `main.cpp:612-616` stays.** In release its body reduces to
`lastMemPrint = millis()`, because the `LOG_INF` is empty, and `if (Serial && …)` still calls
`HWCDC::isCDC_Connected()` each loop (framework `HWCDC.cpp:271-273`). That is a cheap register read
and has no side effects. Removing it means editing `main.cpp` (A-2's rule). Behaviour is unaffected.

**A-6. AGENTS.md: correct the dialect line only.** `AGENTS.md:176` changes from
`C++20 (`-std=c++2a`)` to `C++20 as GNU++20 (`-std=gnu++2a`, `platformio.ini:40`)`. `:173-174` and
`:854-855` become true under A-1 and are left as written.

**A-7. `.clangd:2` follows the build: `-std=c++2a` → `-std=gnu++2a`.** It has the same mismatch as
AGENTS.md:176. The owner's comment names only CLAUDE.md, but `.clangd` is the other file that states
the dialect, and leaving it contradicts G3's intent. This is editor-only: clangd diagnostics, no
effect on the firmware. *Attack surface: this goes beyond the owner's literal wording. If the review
rules it out, drop it; nothing else depends on it.*

**A-8. USER_GUIDE.md "Serial logs" gets a dev-build qualifier.** `USER_GUIDE.md:390-398` tells users
to connect USB and run `debugging_monitor.py`. On the OTA build, which is what a USER_GUIDE reader
runs, that now shows nothing. Add one sentence at `:390`: serial logs come only from a development
build (`pio run -e x4pro`, flashed by cable or side-loaded, as AGENTS.md "Flashing" describes). The
OTA build is silent on serial. The "Crash reports" paragraph at `:388-389` stays: the report is still
written and still worth attaching (A-4).

**A-9. No new automated check.** No host test touches build flags (`test/CMakeLists.txt` has no
`platformio.ini` reference other than a comment at `:25`; R §9), and the repo has no pattern for
asserting on a firmware binary in CI. Inventing one would need a decision. Verification is a binary
`strings` check run by hand before and after (§Testing), plus the existing CI `x4pro` build
(`.github/workflows/ci.yml`).

**A-10. PR title `fix: drop serial logging from release builds`.** It is conventional and a patch
bump. It is user-visible: OTA builds stop emitting serial output.

## Architecture

There is no new code. The change is three lines of build configuration and three lines of
documentation:

| File | Change | Assumption |
| --- | --- | --- |
| `platformio.ini:187-188` | delete `-DENABLE_SERIAL_LOG`; `-DLOG_LEVEL=1 ; …` → `-DLOG_LEVEL=0` | A-1 |
| `AGENTS.md:176` | `c++2a` → `gnu++2a` | A-6 |
| `.clangd:2` | `-std=c++2a` → `-std=gnu++2a` | A-7 |
| `USER_GUIDE.md:390` | dev-build-only qualifier | A-8 |

The mechanism is the existing preprocessor gate. `ENABLE_SERIAL_LOG` is a global `build_flags`
define, so removing it switches off every `#ifdef ENABLE_SERIAL_LOG` site at once, in this tree and
in the SDK:

- `Logging.h:44`;
- `main.cpp:342`;
- `HalPowerManager.cpp:70`;
- `WifiSelectionActivity.cpp:552`;
- `BoardConfig.h:1654`;
- `MemoryManager.cpp:26`;
- `PaperMonoDriver.cpp` ×7 (R §1).

## Data and control flow in the release build, after the change

1. **Boot.** Arduino `loopTask` runs `setup()` with no chip-debug report (A-2). `setup()` skips
   `delay(250)`, `Serial.begin` and `setTxTimeoutMs` (`main.cpp:342-353`). `HWCDC`'s `rx_queue` and
   `tx_lock` stay `NULL`.
2. **Every `loop()`.**
   - `LOG_*` calls produce no code, and their arguments are not evaluated (`Logging.h:62-66`).
   - `if (Serial && …)` is false or trivially true, and either way does nothing observable (A-5).
   - `logSerial.available()` returns `-1`, so the handler is skipped (A-2).
3. **Deep sleep.** `logSerial.end()` is skipped (`HalPowerManager.cpp:70-76`). That is consistent:
   nothing was begun.
4. **Panic.** `__wrap_panic_abort` still records the reason (`HalSystem.cpp:28-39`).
   `checkPanic()` still writes `/crash_report.txt`. "Last logs" is empty (A-4). Its own
   `LOG_INF`/`LOG_ERR` (`HalSystem.cpp:112,114,117`) are compiled out, so a failed report write is
   now silent in release. It was silent to anyone without a cable before, too.
5. **USB.** The USB-Serial/JTAG peripheral is fixed-function silicon (R §3), so cable flashing with
   esptool and the ROM bootloader are unaffected. The host sees the CDC device but receives no
   application output.

The dev env's flow is unchanged (N1).

## Error handling

The change removes code paths and adds none, so it adds no runtime error handling. What it removes,
in release:

- every `LOG_ERR`. The CLAUDE.md error rule, "`LOG_ERR` + return false", still holds as code. The
  log half now produces nothing in release, which is exactly what AGENTS.md:173-174 has always
  claimed;
- the one `loop()` stall the issue names (A-2).

Build-time failure modes, all checked in R §8:

- a symbol referenced only under the flag: the flag-removed release build succeeds (exit 0);
- new warnings: none in `src/` or `lib/`. R §8's caveat applies: `-Wall` is not enabled, so an unused
  local left behind by a vanished `LOG_*` would not be reported. At `-Os` such a local costs nothing.

## Testing strategy

TDD here means an observable check on the release binary that fails before the change and passes
after it. R §8 establishes each number.

**T1 — logging is gone from release (fails first).** After `pio run -e x4pro-gh_release`:

```bash
strings .pio/build/x4pro-gh_release/firmware.bin | grep -c '\[%lu\] \[%s\] \[%s\] '
```

Before: `1` (red). After: `0` (green). This is `logPrintf`'s prefix format (`Logging.cpp:47`). It
leaves the binary only when no `LOG_*` call survives anywhere.

**T2 — the heap `LOG_INF` is gone.** Same build: `grep -c 'Free: %d bytes'` goes from `1` to `0`.

**T3 — dev logging is untouched (guards N1).** After `pio run -e x4pro`, T1's grep on
`.pio/build/x4pro/firmware.bin` stays `1`. CI builds this env (`.github/workflows/ci.yml`).

**T4 — size.** `firmware.bin` for the release env is about 45,952 bytes smaller than the `2f303f6f`
baseline of 5,536,720 B (R §8). A result far from that means something other than the log strings
changed.

**T5 — the handler is unreachable, not absent (documents A-2).** `grep -c SCREENSHOT_START` stays
`1`. That is expected under A-2. If the orchestrator applies the offered guard, it becomes `0`.

**T6 — format and host tests.** `./bin/clang-format-fix` over the whole tree. No C++ changes, so it
should report nothing. No host suite changes, and none is expected to move.

**Human tester (flag in the PR).**

1. Flash a release build (OTA or side-load). `cat /dev/cu.usbmodem*` shows no application output.
2. Send `CMD:SCREENSHOT\n` to the port. Nothing comes back and the UI does not stall.
3. Boot feels no slower. A-3 predicts about 250 ms faster.
4. Optional: force a panic. `/crash_report.txt` has version and reason, and "Last logs" is empty
   (A-4).

guard around `src/main.cpp:618-633` from A-2. No line is needed in `test/CMakeLists.txt` or the i18n
