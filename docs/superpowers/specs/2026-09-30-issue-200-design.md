# Issue #200 — reader menu as a bottom sheet over the page

Branch `feature/200-reader-menu-sheet`, base `67eaaf1e` (release 1.21.0). Research:
`docs/superpowers/research/2026-09-30-issue-200-research.md`, cited below as **R §n**. Every
`file:line` was re-read on this branch on 2026-09-29.

## Problem

- **The menu scrolls.** A Bible can build 15 menu items: `buildMenuItems`
  (`src/activities/reader/EpubReaderMenuActivity.cpp:41-82`) on an X4 Pro, where rotation is
  compiled out (`src/CrossPointSettings.h:18-24`) and a frontlight is present. That is one more
  than the 14 rows a page holds after #197 (R §2).
- **The page is wiped.** `render()` calls `renderer.clearScreen()` (`EpubReaderMenuActivity.cpp:225`)
  although the page the user was reading is still in the single framebuffer (R §2).

## Goal

1. From the reading surface, the menu opens as a **sheet over the lower part of the page**. The
   page stays visible above it.
2. Every item is reachable **without scrolling**.
3. Sheet layout:
   - A title row with the reference (from #197's `readerMenuTitle`,
     `EpubReaderActivity.cpp:1611-1618`) and a close (✕) control.
   - A row of large quick actions: **Go to**, **Search** (Bible only), **Mark** and **Tag**.
   - The remaining items in **two columns** of compact rows.
4. Bible rules:
   - **Go to %** is hidden.
   - **"Tags here (n)"** appears when n > 0 tagged passages resolve in the current chapter.
   - Non-Bible books keep every item they have today.
5. Closing: a tap on the visible page area, the ✕, a left-edge swipe (Back) or Home.
6. Fallbacks use today's full-screen menu:
   - the snapshot allocation fails;
   - night mode is on;
   - the framebuffer is not known to hold the page;
   - the geometry doesn't fit;
   - a rotation changes the frame.

   Every fallback is logged. None may crash.
7. The page snapshot lives in PSRAM and is freed on exit. PSRAM and internal free heap are logged
   before the sheet opens, while it is open, and after it closes.

## Non-goals

- The "Recent" chip row in the mockup. That is phase 4, which brings `places.json` (R §7).
- Any new store, file or on-disk format.
- Changing what any menu action does once it has been chosen: `onReaderMenuConfirm` keeps its
  cases (`EpubReaderActivity.cpp:672-859`). The only change is the new `TAGS_HERE` case.
- Night-mode rendering of menus. Menus stay normal polarity (`ActivityManager.cpp:55-58`).
- `MappedInputManager`. It is used, not changed (ui-dev rule).
- Other boards' capabilities. `ROTATE_SCREEN` keeps compiling for a rotation-capable board and
  invalidates the sheet (A-9), but it is not device-tested.

## Assumptions (each one is a decision a reviewer can attack)

### Entry and snapshot

- **A-1: the menu owns its snapshot. It does not reuse `GfxRenderer::storeBwBuffer`/`restoreBwBuffer`.**
  `restoreBwBuffer` frees the chunks after one restore (`GfxRenderer.cpp:2354`). It also calls
  `display.cleanupGrayscaleBuffers`, which rewrites the controller's differential baseline
  (`GfxRenderer.cpp:2352`, `freeink-sdk/.../FreeInkDisplay.cpp:868-877`). Restoring on every sheet
  render through it would make the baseline disagree with the panel and re-drive the whole sheet
  (R §4). Owning the snapshot also keeps it apart from the reader's grayscale path, which shares
  `bwBufferChunks` (`EpubReaderActivity.cpp:1549,1570`, `ReaderUtils.h:204,225`). And it lets the
  snapshot use `makeUniqueNoThrow`, where `storeBwBuffer` uses a raw `malloc`
  (`GfxRenderer.cpp:2310`).
  - *Rejected:* a new non-destructive `GfxRenderer::reapplyBwBuffer()`. It would couple the menu to
    shared renderer state that three other call sites store and free.
- **A-2: `PageSnapshot` shape.**
  - Chunks of `CHUNK_BYTES = 8000`, matching `BW_BUFFER_CHUNK_SIZE` (`GfxRenderer.h:42`), with
    `MAX_CHUNKS = 8` fixed-size `std::unique_ptr<uint8_t[]>` slots, so the chunk table itself needs
    no heap.
  - `capture(const uint8_t* fb, size_t size)` allocates each chunk with
    `makeUniqueNoThrow<uint8_t[]>` and copies. On any failure it frees what it took and returns
    `false`. A `size` above `MAX_CHUNKS * CHUNK_BYTES` also returns `false`.
  - `restoreInto(uint8_t* fb, size_t size)` copies back and keeps the chunks. It returns `false` if
    nothing is captured or the size differs.
  - `release()` frees the chunks and is idempotent. The destructor releases.
  - It has no Arduino or GfxRenderer dependency, so it runs on the host.
- **A-3: the snapshot lands in PSRAM.** Each 8,000-byte `operator new` goes to `malloc`, which on
  this build routes anything over `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL 4096` to PSRAM (R §4). The
  cost is 48,000 B of PSRAM while the sheet is open and **0 B of internal SRAM**, except the
  chunk-pointer table inside the activity object (8 × 4 B). The device heap log (Verification 2)
  confirms the placement.
  - *Rejected:* `heap_caps_malloc(MALLOC_CAP_SPIRAM)` as `BibleSearchStore.cpp:25` does. That would
    pin the snapshot to PSRAM, but it makes `PageSnapshot` untestable on the host and bypasses
    `makeUniqueNoThrow`. The default routing already gets the right placement.
- **A-4: capture happens in the menu's first `render()`, on the render task, not in `onEnter`.**
  `onEnter` runs on the main loop task (`ActivityManager.cpp:159-160`), while a reader render may
  still be running on the render task. Renders are serialised under `RenderLock`
  (`ActivityManager.cpp:47-59`), so by the first menu render the framebuffer holds the last
  completed frame. Capturing there cannot tear.
- **A-5: the reader says whether the framebuffer holds the page.** `openReaderMenu` gains a
  `bool pageOnScreen` parameter:
  - It is `true` from the reading surface's own input: Confirm, a touch menu gesture or a Home-key
    hold (`EpubReaderActivity.cpp:517-519,534-535`).
  - It is `false` from every result handler that reopens the menu after a sub-screen
    (`EpubReaderActivity.cpp:675-677,728-731,745-748,757-760,771-774,798-801`). There the
    framebuffer holds the sub-screen's frame (R §2).

  `false` means the full-screen menu.
  - *Rejected:* have the reader repaint the page first, then open the sheet. Three of those paths
    release the section first (`releaseSectionKeepingPosition`, `EpubReaderActivity.cpp:718,743,772`),
    so the repaint would rebuild the section, and after a text-settings change that means
    re-indexing before the menu can appear. That is a new deferred-open mechanism the reader has no
    precedent for. A follow-up can add it if the owner wants the sheet there.
- **A-6: the snapshot matches the panel on these paths.** Whatever the reader drew last is in the
  framebuffer and on the panel. That includes the bookmark toast (`EpubReaderActivity.cpp:1276-1278`)
  and the indexing popup (`:297`). An anti-aliased page leaves the BW page in the framebuffer and
  as the controller baseline (`:1487,1536,1570`). A FAST refresh therefore drives only the sheet
  region, and the grays already on the panel stay where the sheet doesn't cover them (R §2).
- **A-7: night mode falls back.** The panel shows the page inverted, but the framebuffer holds
  normal polarity, and the menu renders normal (`ActivityManager.cpp:55-58`,
  `FreeInkDisplay.cpp:577-579`). If `SETTINGS.screenInverted != 0` at capture time, the menu does
  not capture and renders full-screen.
  - Toggling night mode **on** from inside the sheet is harmless. The menu never inverts, so the
    panel does not change until the reader re-renders after close, exactly as with today's menu.
  - Night mode can't be switched **off** from a sheet, because a sheet never opens with it on.
- **A-8: a framebuffer on loan falls back.** If `renderer.hasFrameBuffer()` is false at capture
  (`GfxRenderer.h:351`), use full-screen. No reader loan outlives the call that took it
  (block-scoped at `EpubReaderActivity.cpp:158-162,1063,1101`); this guard only makes that explicit.
- **A-9: a rotation invalidates.** The `ROTATE_SCREEN` popup callback
  (`EpubReaderMenuActivity.cpp:107-115`) releases the snapshot and switches to full-screen for the
  rest of this menu session. This is compiled out on the X4 Pro and is here for correctness only.

### Items

- **A-10: the item model is one flat, ordered list: quick actions first, then rows.** It keeps the
  existing `MenuAction` values, moves the enum into `ReaderMenuModel.h` as `ReaderMenuAction`, and
  aliases it as `EpubReaderMenuActivity::MenuAction`. Every `EpubReaderMenuActivity::MenuAction::X`
  in `EpubReaderActivity.cpp` compiles unchanged. `TAGS_HERE` is appended. `MenuResult.action` is
  an in-memory `int` (`src/activities/ActivityResult.h:24-28`) and is never persisted, so
  appending is safe.
- **A-11: quick actions, in order, each present only when its item exists today.**

  | Tile | Action | Present when |
  |---|---|---|
  | Go to | `SELECT_CHAPTER` | always |
  | Search | `SEARCH_BIBLE` | Bible |
  | Mark | `TOGGLE_BOOKMARK` | always |
  | Tag | `HIGHLIGHT_PASSAGE` | `hasHighlights` |

  A non-Bible book gets three tiles, spread evenly across the width.
- **A-12: row order.** Every row present only under today's condition:
  1. Bookmarks
  2. Tags here (n) — Bible, n > 0
  3. Highlights
  4. Footnotes
  5. Text settings
  6. Night mode
  7. Frontlight
  8. Rotate — cap only
  9. Auto turn
  10. Go to % — non-Bible only
  11. Screenshot
  12. Go home
  13. Delete cache

  Rows fill **row-major** (left, right, left, …), as in the mockup.
  - **Highlights stays.** The mockup drops it, but the acceptance criteria require every menu item
    to be reachable. "Tags here" is a chapter view, not the whole list.
- **A-13: capacity.**
  - X4 Pro maximum: Bible 4 tiles + 11 rows (Bookmarks, Tags here, Highlights, Footnotes, Text,
    Night, Frontlight, Auto, Screenshot, Home, Delete); non-Bible 3 tiles + 11 rows.
  - With rotation: 12 rows.
  - `MAX_QUICK = 4`, `MAX_ROWS = 14`. The model clamps and logs above them, as today's
    `MAX_MENU_ITEMS` does (`EpubReaderMenuActivity.cpp:184-188`).
- **A-14: "Tags here" count and target.**
  - `openReaderMenu` computes `n = STUDY.passagesInDocument(currentSpineIndex).size()`, only when
    `isBible && highlightsLoaded`, holding a `RenderLock`: the render task uses the same
    `UnitIndexCache` (`StudyStore.h:137-138`). This is the same predicate the page paints with
    (`EpubReaderActivity.cpp:1398`), so the count matches what is highlighted. Unlike a
    `documentSpine` scan, it includes Verse passages whose spine hint is stale
    (`StudyStore.cpp:251-263`).
  - Cost: one transient `std::vector<PaintedPassage>` (24 B per passage, internal heap) per menu
    open. It is freed before the menu is constructed. This is a user action, never the page-turn
    path.
  - Tapping the row opens `HighlightsActivity` with a new optional `spineFilter`. Its
    `rebuildVisibleIndices` then takes indices from `STUDY.passagesInDocument(*spineFilter)`,
    most-recent-first, ANDed with the existing tag filter. The header title becomes the passed
    reference (for example "Isaiah 40") instead of `STR_HIGHLIGHTS`.
  - It returns through the same handler as `openHighlights` (`EpubReaderActivity.cpp:338-358`).
  - The filter re-queries after a delete, so it never holds stale indices, for the reason
    `HighlightsActivity.h` gives for using indices rather than pointers.
- **A-15: labels.**
  - Tiles use `STR_SEARCH` ("Search") and `STR_TAG` ("Tag"), which exist, plus new `STR_GO_TO`
    ("Go to") and `STR_MARK` ("Mark").
  - The row uses new `STR_TAGS_HERE` ("Tags here (%d)"), formatted with `snprintf` into a member
    `char[32]`.
  - Auto turn in the sheet uses new `STR_AUTO_TURN` ("Auto turn"). The full-screen list keeps
    `STR_AUTO_TURN_PAGES_PER_MIN`.
  - Every other row keeps its current key.
  - The keys go to the orchestrator as a hand-off (ui-dev shared-file rule). English plus Spanish
    values are given in the PR body; other languages fall back to English.

### Layout and rendering

- **A-16: the sheet is sized to its content and anchored at the bottom of the safe area, not
  fixed at 60%.** `ReaderMenuSheetLayout::compute(Inputs)` takes:

  | Input | Source |
  |---|---|
  | screen and safe rect | `getScreenSafeArea(renderer, true, false)` |
  | `titleHeight` | `metrics.headerHeight` (44, `LyraTheme.h:13`) |
  | `gap` | `metrics.verticalSpacing` (8, `LyraTheme.h:14`) |
  | `tileHeight` | `max(minTouchSize, iconSize 32 + body lineHeight + 2·gap)` |
  | `rowHeight` | `ListRowHeight::resolve` (50 on touch, `LyraTheme.h:20`) |
  | `ruleWidth` | `metrics.popupFrameThickness` (2, `LyraTheme.h:53`) |
  | counts | `quickCount`, `rowCount` |

  It returns:
  - `sheetTop`, the plate rect, the title and ✕ rects, `tile[4]`, `column[2]` and
    `rowsPerColumn = ceil(rowCount / 2)`;
  - the page rect (safe top to `sheetTop`);
  - `fits`.

  `fits` requires the page rect to be at least **one third** of the screen height, so a tap target
  and the reading context survive.

  On the X4 Pro the worst case works out as follows (a sanity check, never hardcoded):

  | Part | Height |
  |---|---|
  | Title row | 44 |
  | Gap | 8 |
  | Tiles | about 77 |
  | Gap | 8 |
  | 6 rows × 50 | 300 |
  | Gap | 8 |
  | **Total** | **about 445 px** |

  That puts the sheet top at about y = 350 and leaves about 44% of the page visible. More page
  shows than in the mockup's y = 300.
- **A-17: rendering in sheet mode.**
  1. `snapshot.restoreInto(fb)`.
  2. Paint the plate: `fillRect` white over the plate rect, and a `ruleWidth` black rule on its top
     edge. Text never sits over page pixels (issue rule "opaque plate").
  3. `renderUi()` builds, in order:
     1. `frame().hit(pageRect, ACTION_CLOSE)`
     2. `frame().hit(plateRect, ACTION_CHROME)` (the guard)
     3. the title as passive text
     4. the ✕ button
     5. the tiles as `screen.button(props, rect)` with an icon
     6. the two columns, each as `screen.setContentMargin(columnInsets)` then `screen.list(props, h)`

     The order matters because routing scans newest-first (`OptionPopup.h:216-219`): tiles and rows
     win inside the plate, the guard absorbs the plate's gaps, and only the page rect closes.
  4. `renderer.displayBuffer(HalDisplay::FAST_REFRESH)`.

  No HALF refresh: only the sheet differs from the panel (A-6).
  - Setting the content margin per column is new. It is the same builder API every list screen
    uses (`EpubReaderMenuActivity.cpp:172-175`), called twice. `screen.list` still applies the
    theme, which a direct `fui::list(frame, rect, …)` call would skip (see the
    `highlights-row-value-slot-width-steal` gotcha).
- **A-18: interaction budget.** The worst case needs 2 (page, guard) + 1 (✕) + 4 (tiles) + 14 (rows)
  = 21 interactions, against `MAX_INTERACTIONS = 64` (`UiAppHost.h:35`).
- **A-19: action values.** Every tile and row carries `actionValue` = its index in the flat model,
  as today (`EpubReaderMenuActivity.cpp:36`), and routes through the existing `ACTION_ROW` into
  `activateIndex`. Tiles use `ACTION_ROW` with the same values, so one dispatch path serves both.
  `ACTION_CLOSE` and `ACTION_CHROME` are `ACTION_USER` and `ACTION_USER + 1`
  (`UiListActivity.h:25-26`).
- **A-20: physical buttons.** Nav Next/Previous walk the flat model order (tiles, then rows
  row-major) through the existing `navigateButtons` (`UiListActivity.cpp:109-122`), and Confirm
  activates. The selected tile renders focused and the selected row renders selected in its
  column. There is no paging, because nothing scrolls.
  - Hold-to-page jumps by `pageRows()`, which is meaningless here. In sheet mode `navigateButtons`
    is overridden to register only the release steps.
- **A-21: value slots.** Night mode, Frontlight and Auto turn show their value as today
  (`EpubReaderMenuActivity.cpp:191-199`). A value longer than 12 bytes goes through
  `utf8SafeSummary`, so an unbounded value can't erase the label: the Spanish "Desactivado" is 11,
  and English "OFF" is 3. Whether it fits in a half-width column is a device check (V-5), not
  something the host can measure.
- **A-22: the full-screen fallback is today's screen.** Same render path
  (`EpubReaderMenuActivity.cpp:222-232`), same list, over the flat model order: quick-action items
  first, then rows, so a Bible still hides Go to % and gains Tags here. It may scroll, and it is
  used only in the cases in Goal 6.

### Closing and lifetime

- **A-23: tap on the page closes.** It closes through `ACTION_CLOSE` → `closeCancelled()`
  (`EpubReaderMenuActivity.cpp:84-90`). A swipe release does not route as a tap (`OptionPopup.h:91-93`
  documents the −1,−1 convention). The left-edge swipe already closes via `wasReleased(Back)`
  (`MappedInputManager.cpp:265`, `EpubReaderMenuActivity.cpp:155-158`), and Home via
  `handleHomeGesture` (`:92-95`). All of these are unchanged.
- **A-24: release.** `onExit()` calls `snapshot.release()` before `UiListActivity`'s teardown. It
  runs under the manager's `RenderLock` (`ActivityManager.cpp:176-182`), so no render can be
  restoring the snapshot while it is freed. After close, the reader repaints the page through its
  normal cadence (`ActivityManager.cpp:130-133` → `renderContents` →
  `ReaderUtils::displayWithRefreshCycle`, `ReaderUtils.h:165-176`). The sheet region is cleaned by
  that refresh like any other page change, including the periodic HALF.
- **A-25: heap logs.** Each line uses `LOG_INF("MENU", …)` with `ESP.getFreeHeap()` and
  `heap_caps_get_free_size(MALLOC_CAP_SPIRAM)` (the pattern at `BibleSearchIndexer.cpp:325`):
  - `before` — first render, just before capture
  - `open` — just after capture
  - `closed` — in `onExit`, after release

  `LOG_INF` is compiled out of `x4pro-gh_release` (`LOG_LEVEL=0`, CLAUDE.md), so it costs nothing
  in production.

## Data and control flow

```
Reader loop: Confirm / centre tap / Home-hold
  └─ openReaderMenu(pageOnScreen = true)
       ├─ n = isBible && highlightsLoaded ? STUDY.passagesInDocument(spine).size() : 0   [RenderLock]
       └─ startActivityForResult(EpubReaderMenuActivity(title, orientation, footnotes, bookmarks,
                                   highlights, isBible, n, pageOnScreen))
Menu ctor: ReaderMenuModel::build(...) → flat items, quickCount; row labels set once
Menu onEnter (UiListActivity) → requestUpdate
Menu first render (render task):
  mode = pageOnScreen && !screenInverted && hasFrameBuffer ? try sheet : fullscreen
  sheet: LOG before → capture → fail? LOG_ERR + fullscreen : LOG open
         layout = ReaderMenuSheetLayout::compute(...) → !fits? release + LOG + fullscreen
  sheet render: restore → plate → renderUi → FAST display
  fullscreen render: today's path
Input (loop task): popup → buttons (Back/Confirm) → routeListTouch
  ACTION_ROW(value) → activateIndex → in-place (night/light/popups) or setResult + finish
  ACTION_CLOSE → closeCancelled ; ACTION_CHROME → consumed
Menu onExit: snapshot.release → LOG closed
Reader result handler: unchanged + TAGS_HERE → HighlightsActivity(spineFilter, reference)
Sub-screen cancel paths: openReaderMenu(pageOnScreen = false) → full-screen menu
```

The mode is decided once, on the first render, and can only degrade (sheet → full-screen), never
upgrade. That keeps it deterministic.

## Error handling

| Failure | Behaviour | Log |
|---|---|---|
| A chunk allocation fails in `capture` | Frees the partial snapshot; full-screen | `LOG_ERR("MENU", "Page snapshot OOM; full-screen menu")` |
| `restoreInto` returns false (never expected) | Release; full-screen from this render on | `LOG_ERR` |
| Layout doesn't fit | Release; full-screen | `LOG_INF` with the counts |
| Night mode, no framebuffer, not page-on-screen | Full-screen; no allocation | `LOG_DBG` naming the reason |
| Rotation in the menu (cap builds) | Release; full-screen | `LOG_DBG` |
| Model over `MAX_QUICK`/`MAX_ROWS` | Clamp and log, as `EpubReaderMenuActivity.cpp:184-188` does | `LOG_ERR` |

Nothing asserts or aborts. Every allocation is `makeUniqueNoThrow` and null-checked.

## Testing strategy

TDD, host first. The new suites go into `test/ui_layout/CMakeLists.txt`, the suite's own file,
modelled on its `ListRowHeightTest` and `BibleReferenceTest` blocks. The root `test/CMakeLists.txt`
already has `add_subdirectory(ui_layout)` (`:102`), so no shared-file hand-off is needed for tests.

1. **`ReaderMenuModelTest`** (pure):
   - Bible: Go to % absent, Search tile present, 4 tiles in order.
   - Non-Bible: Go to % present, no Search tile, 3 tiles.
   - Tags here present iff Bible and n > 0, and placed after Bookmarks.
   - Highlights present whenever `hasHighlights`.
   - Every item today's `buildMenuItems` would build is in the model, exactly once: the acceptance
     criterion "keeps all their items", tested per flag combination.
   - Clamp at `MAX_ROWS`.
   - Row-major column assignment.
2. **`ReaderMenuSheetLayoutTest`** (pure):
   - X4 Pro metrics with the worst-case counts `fits`.
   - The sheet is bottom-anchored inside the safe rect.
   - Tiles and columns stay inside the plate and don't overlap.
   - The page rect ends at `sheetTop`.
   - A second screen size (not 480×800) also lays out, which guards against hardcoded dimensions.
   - Too many rows for the height gives `fits == false`.
   - `rowsPerColumn` = ceil.
3. **`PageSnapshotTest`** (pure, with FailingNothrowNew):
   - Round trip.
   - **Repeated `restoreInto` keeps the data** (the property `restoreBwBuffer` lacks).
   - A size that is not a multiple of 8000 (48,000 and 47,999).
   - An oversize buffer is refused.
   - Restore without capture fails.
   - `release` is idempotent.
   - OOM on the k-th chunk for every k frees everything and returns false.

   It gets its own executable with `-fno-builtin`, copying `test/ditherers/CMakeLists.txt` and
   `test/ditherers/FailingNothrowNew.*` (see the clang elision gotcha).
4. **Build:** `pio run -e x4pro`, `pio check`, and `./bin/clang-format-fix` over the full tree after
   `git add`.

### Device verification (human)

- **V-1:** Open the menu from a Bible page with a centre tap. The page stays above the sheet, all
  items are visible and nothing scrolls. Repeat in a non-Bible EPUB: Go to % is present and there
  is no Search tile.
- **V-2:** Serial log from the `x4pro` dev build:
  - `before`/`open` shows PSRAM down about 48 KB and internal free unchanged, within noise.
  - `closed` shows PSRAM back at the `before` value.
  - Ten open/close cycles show no drift.
- **V-3:** Ten open/close cycles, including a tap-on-page close, a ✕ close and a swipe close. No
  ghost of the sheet remains on the page region after the reader's repaint.
- **V-4:** Cancel from Go to and from Search: the full-screen menu appears (A-5). With night mode on,
  the full-screen menu appears (A-7).
- **V-5:** Spanish UI. The night-mode, frontlight and auto-turn rows show both label and value in
  their half column.
- **V-6:** A chapter with tagged passages shows "Tags here (n)", and n matches the painted
  highlights. Tapping it lists only those passages under the reference title.
- **V-7:** The OOM fallback. Build with `-DREADER_MENU_FORCE_SNAPSHOT_OOM` in
  `platformio.local.ini`: a `#ifdef` that makes `capture` fail. The full-screen menu appears and
  `LOG_ERR` prints.

  - the `PageSnapshot` pointer table (32 B);
  - the model arrays inside the heap-allocated activity (≤ 18 small structs);
  - `char[32]` for the Tags-here label;
  - one transient `PaintedPassage` vector per open (A-14).

  No new task, no new stack buffer over 256 B.

## Risks

- **A-6 rests on the framebuffer equalling the controller baseline** after every reader render
  path. If some path leaves them different, the first sheet paint re-drives more than the sheet.
  V-3 catches it, and the fix would be a HALF first paint.
- **The two-column `setContentMargin` technique (A-17)** is new to this repo. If `screen.list`
  misbehaves in a narrow band, the plan falls back to `fui::list(frame, rect, props)` with the theme
  fields copied as `FreeInkApp.h:245-301` does.
