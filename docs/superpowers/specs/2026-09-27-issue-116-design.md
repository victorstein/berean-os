# Issue #116 design — FreeInkUI toast for transient outcome messages

Research: `docs/superpowers/research/2026-09-27-issue-116-research.md`.
Branch `feat/116-toast-outcome-messages`, on `dc97292e`. Every `file:line`
below was read on that commit.

## Problem

Every transient outcome message goes through `BaseTheme::drawPopup`
(`src/components/themes/BaseTheme.cpp:468-497`). That includes a store
refusal, "Bookmark added", and a wallpaper "Done". `drawPopup` is built for
blocking progress, and it gets three things wrong for a one-line outcome:

1. **It covers the text being read.** The box sits at
   `screenHeight * popupTopOffsetRatio` (`BaseTheme.cpp:475`). The ratio is
   0.165 on Lyra (`lyra/LyraTheme.h:49`), the default theme
   (`src/CrossPointSettings.h:317`), and 0.075 on Classic
   (`BaseTheme.h:164`). Either way it lands over the first lines of the page.
2. **It does not wrap.** It measures one line (`BaseTheme.cpp:476-477`).
   The portrait screen is 480 px wide, and the longest posted message is
   53 characters (`STR_TAG_LIMIT_PER_HIGHLIGHT`,
   `lib/I18n/translations/english.yaml`), about 626 px in Ubuntu 12 regular
   (spec review 0, summed from `lib/EpdFont/builtinFonts/ubuntu_12_regular.h`). No other translation defines the
   posted-message keys, so every language falls back to that English text.
   For those, `textWidth + 2*marginX` exceeds the screen. `x` in
   `BaseTheme.cpp:480` goes negative and both ends of the message are cut off.
   A store refusal the user cannot read is a silent failure.
3. **It looks exactly like "Indexing…"**, so an outcome reads as a state the
   user has to wait out.

FreeInkUI ships `fui::toast`
(`freeink-sdk/libs/ui/FreeInkUI/include/components/overlays/toast.h:25-50`):
an anchored, wrapping panel built on the same `fui::popup`. Nothing in `src/`
uses it.

## Goal

Add `GUI.drawToast(renderer, message)`, and route the three families of
outcome messages the issue names through it:

- posted messages (`PostedMessage::drawNext`)
- the reader's bookmark messages
- the wallpaper-save result in `BmpViewerActivity`

The toast is bottom-anchored, wraps, clears the reader's status bar, and
stays up exactly as long as the popup did.

## Non-goals

- No change to `drawPopup`, `fillPopupProgress`, or any blocking or progress
  popup: "Indexing", "Loading", "Index failed", or the 16 other `drawPopup`
  call sites (20 calls, minus the four this change moves) (research, "Blocking popups that stay on `drawPopup`").
- No change to message timing. The `PostedMessageQueue` hold of 2500 ms
  (`PostedMessageQueue.h:19`), the reader's `BOOKMARK_MESSAGE_DURATION_MS`
  of 2500 (`ReaderUtils.h:21`) and BmpViewer's `delay(1000)`
  (`BmpViewerActivity.cpp:235`) all stay.
- No new refresh mechanism. There is no windowed B/W update on this panel
  (`.claude/agents/ui-dev.md`, "Constraints that bite here").
- No new strings, so no translation YAML edits.
- No input, touch-dismiss, or hit rects. The toast is display-only.

## Architecture

Two new pieces, each modelled on an existing file.

### 1. `src/components/ToastLayout.h` — the pure bounds calculation

This is modelled on `src/activities/PostedMessageQueue.h`: a header with no
Arduino, renderer or FreeInkUI dependency, holding the one rule that matters
and host-tested with plain integers. It is the testable seam; the drawing
itself is not host-testable (research, finding 5).

```cpp
namespace ToastLayout {
struct Bounds { int x, y, width, height; };

// The area fui::toast anchors its panel inside. The bottom edge stops above
// the bezel inset and the reader status bar, so a bottom-anchored toast never
// covers either.
constexpr Bounds bounds(int screenWidth, int screenHeight, int insetTop, int insetRight,
                        int insetBottom, int insetLeft, int statusBarHeight);
}
```

It returns `x = insetLeft`, `y = insetTop`,
`width = screenWidth - insetLeft - insetRight`, and
`height = screenHeight - insetTop - insetBottom - statusBarHeight`.
Width and height are clamped at 0.

`constexpr` follows `CLAUDE.md`, "The resource protocol" rule 6.

### 2. `BaseTheme::drawToast`

```cpp
// BaseTheme.h, beside drawPopup (:221)
virtual void drawToast(const GfxRenderer& renderer, const char* message) const;
```

This is modelled on `BaseTheme::drawHeader` (`BaseTheme.cpp:284-394`). It
builds a `fui::GfxRendererFrame<1>` on the render-path stack from
`uiScaleSpec()` fonts (`:288-290`), fills a `fui::*Props`, and calls the
component. The styling is modelled on `src/components/OptionPopup.h:193-203`,
which rebuilds the legacy popup frame from the theme's popup metrics on top
of `fui::defaultPopupStyles()`.

The steps:

1. If `message` is null or empty, return without drawing or refreshing
   (A6).
2. Read the metrics. `renderer.getOrientedViewableTRBL(...)` gives the four
   insets (`lib/GfxRenderer/GfxRenderer.cpp:2371+`), and
   `UITheme::getInstance().getStatusBarHeight()`
   (`src/components/UITheme.cpp:132-140`) gives the status bar.
   `ToastLayout::bounds(...)` then gives the anchoring area.
3. Build `fui::ToastProps`:
   - `message`
   - `anchor = fui::ToastAnchor::Bottom`
   - `text.font = GfxRendererTarget::FONT_BODY` (`UI_12_FONT_ID`, the font
     `drawPopup` uses at `:476`)
   - `text.bold = metrics.popupTextBold`
   - `text.maxLines = TOAST_MAX_LINES` (4, A3)
   - `text.color`, set as in A2
   - `styles`, set as in A2
   - `padding`, set as in A4
   - `maxWidth` and `margin` left at the component defaults: 3/4 of the
     bounds width, and 16 px (`toast.h:19-21`)
4. Call `fui::toast(ui.frame, boundsRect, props)`.
5. Call `renderer.displayBuffer()`, which is FAST (A5), just as `drawPopup`
   does at `:495`.

It returns `void`; no caller needs the rect. `drawPopup` returns one only for
`fillPopupProgress` (`:499-522`).

## Data and control flow

The flow does not change. Only the draw call at the end of each path is
swapped.

- **Posted message** (research, "Posted messages"):
  1. The main task calls `PostedMessage::post` (`PostedMessage.cpp:21-26`).
  2. The render task finishes its screen and its own `displayBuffer`.
  3. `drawNext` (`:28-35`) calls `queue.next(millis())`, which returns the
     same message on every render for 2500 ms (`PostedMessageQueue.h:35-46`).
  4. `drawToast` draws into the B/W framebuffer and does a FAST refresh.
  5. The next render after the hold omits the toast. That screen's normal
     refresh is the dismissal; nothing schedules it
     (`grep -rn "MIN_DISPLAY_MS\|PostedMessage::" src` finds no timer).
- **Bookmark:**
  1. `addBookmark` arms `showBookmarkMessage` and `bookmarkMessageTime`
     (`EpubReaderActivity.cpp:1788-1789`).
  2. `render` draws the page. `renderContents` does the B/W display through
     `displayWithRefreshCycle` (`:1461`), then the grayscale pass
     (`:1465+`).
  3. `drawToast` then draws over the restored B/W buffer (`:1301-1303`).
  4. After 2500 ms, `loop()` clears the flag and calls `requestUpdate()`
     (`:504-507`). The page re-renders through the refresh cadence
     (`ReaderUtils.h:165-177`), which removes the toast.
- **BmpViewer:**
  1. `drawToast` draws over the viewer and refreshes.
  2. `delay(1000)` holds the screen.
  3. `onEnter()` redraws the viewer (`BmpViewerActivity.cpp:226-236`).

The toast holds no state across calls. It does allocate, transiently,
while drawing. The measure (`measureWrappedText`, then `layoutText`,
`FreeInkUICore.h:733+`, `:860-872`) works on the stack: `char buf[228]`
plus a `Range[16]` (`FreeInkUICore.h:744,765-770`). The draw is different.
It goes through `GfxRendererTarget::text`, whose `maxLines > 1` branch calls
`renderer.wrappedText` (`FreeInkUIGfxRenderer.h:183`). That builds a
`std::vector<std::string>` and copies `std::string`s for each word
(`GfxRenderer.cpp:1797-1850`).

Those are a few hundred bytes of short-lived heap blocks, freed before
`drawToast` returns. They are repeated on each render during the 2.5 s hold,
and every wrapping FreeInkUI text on this target already takes the same
path. Avoiding them would mean reimplementing the SDK adapter's draw, which
is out of scope for a UI-routing change. This is accepted, not denied.

The stack cost is `GfxRendererFrame<1>` (as in `drawHeader`, `:288-290`)
plus `layoutText`'s ~400 B of locals. The render task's stack is 8192 bytes
(`ActivityManager.cpp:32-33`).

## Assumptions (each is a decision the review should attack)

- **A1 — One bottom bound for every screen: always reserve
  `getStatusBarHeight()`.** `drawToast` has no parameter saying whether the
  screen has a status bar. `PostedMessage::drawNext` is called from the
  reader (`ReaderActivity.cpp:180,185`) and from list screens alike, and does
  not know which it is. On a list screen the toast therefore sits up to 26 px
  higher than strictly needed. That costs nothing: those screens draw no
  button hints on this touch device (`BaseTheme.cpp:171-173`,
  `LyraTheme.cpp:132-134`). The alternative, a `bottomInset` parameter
  threaded through `drawNext`, changes a signature in ten callers for a cosmetic
  26 px.
  The worst case is 19 + (2+1)·2 + 1 = 26 px, from `UITheme.cpp:138-139`,
  `BaseTheme.h:155,157` and `CrossPointSettings.cpp:257-258`.
  `getStatusBarHeight()` passes `clockAvailable=true` (`UITheme.cpp:136-138`),
  so it reserves the text lane even without an RTC. That is the conservative
  direction.

  Accepted edge case: with the text lane hidden and auto page turn active,
  the reader draws its "auto turn" title `statusBarVerticalMargin` higher
  (`EpubReaderActivity.cpp:1642-1647`), into space `getStatusBarHeight()`
  does not reserve. There, the title's top (~774) and the toast's bottom
  (~781) overlap by about 7 px for the 2.5 s a toast is up. It is rare, since
  it needs auto-turn and a message together, and it is not worth a
  reader-specific inset.
- **A2 — The toast looks like the theme's popup, not FreeInkUI's default.**
  Colours come from `metrics.popupTextInverted`. The name reads backwards:
  `drawPopup` passes it as `drawText`'s `black` argument (`BaseTheme.cpp:494`,
  signature `GfxRenderer.h:283`).
  - **Classic** (`popupTextInverted = true`, `BaseTheme.h:170`): white
    background, a black border of `popupFrameThickness`, black text.
  - **Lyra** (`false`, `LyraTheme.h:55`): black background, a white border,
    white text, radius `popupCornerRadius` (6, `LyraTheme.h:53`).

  `fui::popup` fills the rect and then strokes its edge inward
  (`popup.h:23-27`; `FreeInkUIGfxRenderer.h:101-115` draws the stroke with
  `drawRect`/`drawRoundedRect` on the rect itself). A white stroke on a black
  fill therefore reproduces `drawPopup`'s white rim around a black box
  (`BaseTheme.cpp:484-489`). The rim is what separates the box from page text
  under it.
- **A3 — At most three lines, ellipsised past that.** `TextStyle.maxLines`
  defaults to 1 (`FreeInkUICore.h:538`). `fui::toast` measures with it, and
  `layoutText` ellipsises past `maxLines`, capped at `MAX_LINES = 16`
  (`FreeInkUICore.h:733-750`). Left at
  1, the toast would be a one-line ellipsis and hide the refusal it exists to
  show. The text area is `474*3/4 - 2*(popupMarginX + frame)`: 319 px on Lyra
  and 321 px on Classic. Summed glyph advances, ignoring kerning (spec review
  0), show that `STR_TAG_LIMIT_PER_HIGHLIGHT` and Classic-bold
  `STR_HIGHLIGHTS_LOAD_FAILED` both need **three** lines. `TOAST_MAX_LINES`
  is therefore **4**, one line of headroom for kerning and advance error.
  The worst-case panel is four UI_12 lines plus padding, still anchored to
  end 16 px above the bounds. The component default `maxWidth` (3/4) is
  kept, so the toast stays compact for the short messages ("Bookmark
  added") that are most of what it shows.
- **A4 — Padding keeps the text clear of the rim.** The padding is
  `Insets{popupMarginY/2 + frame, popupMarginX + frame, popupMarginY/2 + frame,
  popupMarginX + frame}`. That is compact vertically, as the issue asks, and
  keeps `drawPopup`'s horizontal margin. The frame is added because the fui
  stroke draws inside the rect, whereas `drawPopup` drew it outside.
- **A5 — FAST refresh on show, unchanged dismissal.** This matches
  `drawPopup` exactly (`BaseTheme.cpp:495`, default `GfxRenderer.h:189`). No
  forced HALF refresh on dismissal is added pre-emptively. The reader already
  cleans on its cadence (`pagesUntilFullRefresh`, `ReaderUtils.h:165-177`),
  and today's popup ghosts no differently from what a toast would. If the
  device check finds a ghost at the toast's bottom position that the top
  popup did not leave, the fallback mirrors
  `ReaderActivity::handleForcedRefresh` (`ReaderActivity.cpp:188-196`). When
  `loop()` clears `showBookmarkMessage` (`EpubReaderActivity.cpp:504-507`), it
  takes `RenderLock`, sets `pagesUntilFullRefresh = 1` **and**
  `forcedRefreshPending = true`, then calls `requestUpdate()`. Setting
  `forcedRefreshPending` alone would be a no-op on a text page: it only
  feeds `cleanImageBasePending`, which only the image path reads
  (`EpubReaderActivity.cpp:1383-1385,1450-1455`). Text pages choose HALF only
  through `pagesUntilFullRefresh <= 1` (`ReaderUtils.h:165-166`).

  The fallback covers only the bookmark toast. Posted messages have no
  dismissal hook, so a ghost there has no reader-side fallback. The fallback
  is **not** in this PR. The PR's device checklist names it as the follow-up
  if step 1 finds a ghost.
- **A6 — A null or empty message draws and refreshes nothing.** `fui::toast`
  already returns on null (`toast.h:26`). `drawToast` also skips the
  `displayBuffer`, so no FAST refresh repaints an unchanged screen.
  `drawNext` never passes null today (`PostedMessage.cpp:34`). This guards
  the new public method.
- **A7 — The four unlisted `drawNext` callers move to the toast too.**
  Launcher, FontDownload, ClockSync and OtaUpdate go through
  `PostedMessage::drawNext` (research, "Posted messages"). Their messages are
  outcomes of the same kind: `STR_SETTINGS_SAVE_FAILED`,
  `STR_WIFI_SAVE_FAILED` and so on. Their progress bars are vertically
  centred (`OtaUpdateActivity.cpp:139-144`,
  `FontDownloadActivity.cpp:673-677`), and the bottom of those screens is
  free on a touch device. The Launcher is the exception: its resume strip
  sits at the bottom (`LauncherActivity.cpp:308-309`). A message posted
  there covers that card for 2.5 s. The toast takes no input, so the card
  still responds to taps, and this is accepted. Splitting `drawNext` by caller would need a second
  entry point for no user-visible gain.
- **A8 — `drawToast` is `virtual`, like `drawPopup`.** No theme overrides
  either today (`grep -rn drawPopup src/components` hits only
  `BaseTheme.{h,cpp}`). The declaration mirrors its neighbour so a theme can
  specialise both the same way.
- **A9 — BmpViewer's "Done" stays drawn immediately, not posted.** Its
  comment (`BmpViewerActivity.cpp:228-229`) records that the viewer's own
  redraw does not call `drawNext`. Only the draw call changes.

## Error handling

- A null or empty message returns early (A6). No log: it is not an error, and
  `PostedMessageQueue::post` already ignores empty messages
  (`PostedMessageQueue.h:24`).
- `ToastLayout::bounds` clamps a negative width or height to 0. `fui::toast`
  with an empty bounds still computes a panel from the text, so the result
  would be mispositioned but not out of memory. This cannot happen on an
  800 px screen with at most 26 + 12 px reserved. The clamp keeps the pure
  function total, and a host test pins it.
- No allocation, file I/O or new log call is added, so no `-Wformat`
  specifier or OOM path arises.
- The store-refusal messages themselves are unchanged. Every existing
  `post` site still posts the same `tr()` string. The issue's requirement
  that "the toast stays up as long as the popup did" holds because timing
  lives in the queue and the reader flag, and neither is touched.

## Testing strategy

**Host (TDD, red first).** Add a new suite, `test/toast_layout/`, modelled on
`test/posted_message/` (its `CMakeLists.txt` and
`PostedMessageQueueTest.cpp`). It includes only `components/ToastLayout.h`
from `${REPO_ROOT}/src`. Cases:

1. With the worst-case status bar (26) and X4 Pro insets
   `{9, 3, 3, 3}` (`BoardConfig.h:625-630`) on 480×800, the bounds' bottom
   edge equals `800 - 3 - 26`. The toast panel, which sits 16 px above it
   (`toast.h:38-39`), therefore cannot overlap the status bar.
2. With the status bar hidden (0), the bottom equals `800 - 3`.
3. Width is `480 - 3 - 3`, and `x` is the left inset.
4. Degenerate input (status bar taller than the screen) clamps height to 0
   rather than going negative.
5. A `static_assert` on one call shows `bounds` is usable in a constant
   expression.

`test/CMakeLists.txt` is a shared append point (`.claude/agents/ui-dev.md`,
"Shared files"). The PR description carries the exact line,
`add_subdirectory(toast_layout)`, for the orchestrator to apply, beside the
existing `add_subdirectory(posted_message)` at `test/CMakeLists.txt:79`.

**Build.** Run
`pio run -e x4pro` (through the batch's `pio-locked.sh`) once, after the last
code edit, then `./bin/clang-format-fix` over the whole tree.

**Not host-provable. The PR carries this as a device checklist, with
assumptions flagged:**

1. In the reader, long-press to add a bookmark, then again to remove it. The
   toast shows centred at the bottom, above the status bar with a visible gap
   (A1). It is readable over anti-aliased text, and is gone after ~2.5 s.
   Look for a ghost where it was, on a FAST-cadence page and not straight
   after a HALF refresh (A5).
2. Repeat with the status bar set to show the progress bar at Thick (the
   26 px worst case), and again with the status bar hidden.
3. Trigger a store refusal. Add tags to one highlight past
   `STR_TAG_LIMIT_PER_HIGHLIGHT`, the longest English message. It wraps to
   three lines, is fully readable, and is not ellipsised (A3). Check on
   Classic (bold) too. For a translated message, set German and hit a
   bookmark SaveFailed. `STR_ERROR_GENERAL_FAILURE` is "Fehler: Allgemeiner
   Fehler" (`german.yaml:149`).
4. On Classic and on Lyra, the toast matches that theme's popup look:
   Classic black frame on white, Lyra white-rimmed black box (A2).
5. Set a wallpaper from the BMP viewer. "Done" shows at the bottom for ~1 s.
6. A blocking popup ("Indexing" on opening an unindexed book) looks exactly
   as before: top position, same box.
7. Heap: `ESP.getFreeHeap()` returns to its baseline once a toast has
   cleared. That shows no leak; the transient `wrappedText` allocations are
   expected while it is up (see "Data and control flow").
8. If step 1 finds a ghost the old top popup did not leave, record it. The
   A5 fallback is the follow-up.

## Changes after spec review 0

Review: `docs/superpowers/reviews/issue-116-spec-review-0.md` (verdict CLEAR).
Every finding was accepted.

- **MAJOR 1:** A3's cap moves from 3 to 4 lines. The measured widths show the
  longest messages need three lines, which left no headroom. Checklist step 3
  now expects three lines.
- **MAJOR 2:** The resource paragraph now states the transient
  `wrappedText` heap use on the draw path and justifies it. The unsupported
  stack-parity claim is replaced by the actual stack cost against the 8 KB
  render task. Checklist step 7 is reframed as a leak check.
- **MAJOR 3:** A5's fallback now sets both `pagesUntilFullRefresh = 1` and
  `forcedRefreshPending` under `RenderLock`, mirroring `handleForcedRefresh`.
  It is scoped to the bookmark toast and marked as not in this PR.
- **MINOR 1-5:** The number of `drawPopup` calls that stay is now 16. The
  Bottom-anchor citation is fixed. Two more stale comments are on the reword
  list. The German checklist step now uses a string that really is
  translated. The auto-turn overlap and the Launcher resume strip are named
  as accepted edge cases in A1 and A7.
