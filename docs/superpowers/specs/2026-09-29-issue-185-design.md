# Issue #185 — X4 Pro charging indicator: design

Research: `docs/superpowers/research/2026-09-29-issue-185-research.md` (cited below as "R§n").
Branch base: `main` at `a4e2288d`, freeink-sdk submodule at `310ec61`.

This design is **gated on hardware**. Which signal, if any, tells the X4 Pro that USB power is
present can only be settled on the bench (issue #185, "Constraint for whoever implements this").
The spec therefore fixes everything that does not depend on the answer, defines the bench probe
that produces it, and gives the implementation shape for each possible answer. Only the shape for
the signal the owner confirms is built.

## 1. Problem

With USB plugged in, the X4 Pro charges, but the battery icon never shows the charging bolt.

- The themes draw the bolt from `gpio.isUsbConnected()` (`src/components/themes/BaseTheme.cpp:74`,
  `:370`; `src/components/themes/lyra/LyraTheme.cpp:27`). The loop requests a redraw on a USB edge
  (`src/main.cpp:791-795`), latched in `HalGPIO::update()` (`lib/hal/HalGPIO.cpp:158-160`).
- `HalGPIO::isUsbConnected()` returns false when `BoardConfig::ACTIVE.usbDetect < 0`
  (`lib/hal/HalGPIO.cpp:347-349`). The X4 Pro profile sets it to `PIN_UNASSIGNED`
  (`freeink-sdk/libs/hardware/BoardConfig/include/BoardConfig.h:1400`). The X3 branch above it
  (`HalGPIO.cpp:335-346`) is never taken on this build, because `_deviceType` is hard-set to X4
  outside `FREEINK_MCU_C3` (`HalGPIO.cpp:137-139`).
- The gauge can't help as it stands. `readGaugeCharging()` returns `known = false` for the CW2017
  (`freeink-sdk/libs/hardware/BatteryMonitor/src/BatteryMonitor.cpp:194-201`).

A second symptom follows from the same false: `getWakeupReason()` (`HalGPIO.cpp:353-373`) uses USB
presence to separate a power-button cold boot from a USB-plug cold boot. On the X4 Pro every
`ESP_RST_POWERON` boot is classified `PowerButton`, and the `AfterFlash` and `AfterUSBPower` rows
are unreachable (R§2).

The documentation is stale too:

- `BoardConfig.h:1400` names GPIO10 as a detect candidate. GPIO10 is the GT911 INT line, confirmed
  on hardware in the same profile (`BoardConfig.h:1402`, value at `:1414`).
- `freeink-sdk/docs/xteink-x4pro-support.md:277-279` says the pin was "not conclusively identified".
- `xteink-x4pro-support.md:259` gives the GT911 pins reversed ("INT=GPIO4, RST=GPIO10"), which
  contradicts `:125` and the profile (R§6).

## 2. Goal

1. `HalGPIO::isUsbConnected()` returns true on the X4 Pro when USB power is present, using only
   the signal the owner confirmed on hardware.
2. The bolt appears and clears within one loop of a plug or unplug. The existing edge latch and
   redraw (`HalGPIO.cpp:158-160`, `main.cpp:793`) do this unchanged once the input is real.
3. `getWakeupReason()` with real USB detection is pinned by a host test, and its newly reachable
   rows are reviewed (§5.3).
4. The stale GPIO10 comment and the "not conclusively identified" note are corrected, in the place
   the owner chooses (Decision D2, §8).

## 3. Non-goals

- **Charge-complete / "full" state.** The bolt means "USB power present", as it already does for
  every board that uses the `usbDetect` path (`HalGPIO.cpp:350`). Nothing on the CW2017 bus reports
  charge termination (`BatteryMonitor.cpp:196-197`).
- **Gauge-trend inference** (issue option 3). It is slow and can't tell "full on USB" from "idle on
  battery". It is out unless the bench finds no GPIO signal *and* the owner asks for it; it would
  then be a new spec.
- **USB-MSC ("USB Transfer")**. Present in the OEM firmware but not ported (`xteink-x4pro-support.md:335`).
- **Changing boot policy.** What the firmware does for each `WakeupReason` (`main.cpp:436-464`,
  `HalDisplay.cpp:29-32`) is unchanged. This work only makes the USB input real.
- **Other boards.** The C3 X4, X3 and every other profile keep their current paths byte for byte.
- **Shipping the probe.** The bench probe (§7) is a throwaway dev build. It is never merged.

## 4. Architecture

### 4.1 Where the X4 Pro signal is read

**Assumption A1 — the X4 Pro read lives in a board branch in `HalGPIO::isUsbConnected()`, not in
the SDK profile.** Modelled on the X3 branch in the same function (`HalGPIO.cpp:335-346`), which
reads a board-specific signal before the generic `usbDetect` path. The branch is keyed on
`BoardConfig::isX4Pro()` (`BoardConfig.h:1620`), the idiom `HalGPIO.cpp:296` already uses.

Why not set `usbDetect` in the profile, the M5PaperS3 shape (`BoardConfig.h:1252`)? That would be a
one-value change if the signal is an active-HIGH GPIO. But the profile is in the `freeink-sdk`
submodule, which tracks upstream Free-Ink (`.gitmodules`: `url =
https://github.com/Free-Ink/freeink-sdk.git`). `hal-dev.md` forbids editing it without asking, and
no bereanOS commit has ever bumped it (`git log -- freeink-sdk` shows only upstream CrossPoint PRs).
A profile value also only fits one shape of signal. A1 covers every shape in §4.2 and keeps the fix
inside this repo. D2 (§8) asks the owner to confirm it.

**Assumption A2 — a pin constant goes in `lib/hal/HalGPIO.h` beside the existing board pins.**
Modelled on `#define UART0_RXD 20  // Used for USB connection detection` (`HalGPIO.h:20`) and the
X3 block (`HalGPIO.h:22-31`). Name: `X4PRO_USB_DETECT`, with a trailing comment that gives the
polarity and "confirmed on hardware, issue #185".

**Assumption A3 — the pin is configured once in `HalGPIO::begin()`, under `isX4Pro()`.** Modelled
on the X4 branch `pinMode(UART0_RXD, INPUT);` (`HalGPIO.cpp:133-135`). Today nothing calls
`pinMode` on any `usbDetect` pin (R§2). `begin()` runs before the first `getWakeupReason()`
(`main.cpp:370` then `:375`), so the boot classification sees a configured pin. The pull mode
(`INPUT`, `INPUT_PULLDOWN`, `INPUT_PULLUP`) comes from the bench (§7.3). An externally driven line
gets plain `INPUT`.

### 4.2 Shape per bench outcome

| Bench outcome (§7.3) | `isUsbConnected()` X4 Pro branch | `begin()` |
|---|---|---|
| **S1** one GPIO follows VBUS, active-HIGH, on data cable **and** wall charger | `return digitalRead(X4PRO_USB_DETECT) == HIGH;` | `pinMode(X4PRO_USB_DETECT, <mode>)` |
| **S2** same, active-LOW | `return digitalRead(X4PRO_USB_DETECT) == LOW;` | same |
| **S3** no GPIO follows VBUS; only the USB-Serial/JTAG state does | `return usb_serial_jtag_is_connected();` | nothing |
| **S4** nothing follows VBUS | no change to detection; stop and re-decide | — |

**Assumption A4 — S3 is a partial fix, and ships only on the owner's explicit say-so.** The IDF
header says `usb_serial_jtag_is_connected()` needs SOF packets from a host, "Having the USB port
connected to a power bank will never be considered as connected", and that using it "will add some
extra overhead time to every freertos tick"
(`~/.platformio/packages/framework-arduinoespressif32-libs/esp32s3/include/esp_driver_usb_serial_jtag/include/driver/usb_serial_jtag.h:97-106`).
A wall charger would never show the bolt. That fails acceptance criterion 1 for wall chargers, so
it is the owner's call, not a default.

**Assumption A5 — ADC thresholds are out of scope for this spec.** If the bench shows VBUS only on
an analog pin (a divider reading between logic levels), that is a new signal shape, and it goes back
to the owner as a decision. It is not invented here.

### 4.3 Wake classification becomes host-testable

**Assumption A6 — the table in `getWakeupReason()` moves into a pure, host-tested function; the
ESP-IDF reads stay in `HalGPIO`.** Modelled on `NavKeyGestures`, the pure logic `HalGPIO` already
delegates to (`HalGPIO.h:6` includes `Input/NavKeyGestures.h`; implementation in
`lib/Input/Input/NavKeyGestures.cpp`; host test `test/nav_key_gestures/`, whose `CMakeLists.txt`
compiles the `.cpp` and adds `${REPO_ROOT}/lib/Input` to the include path). A second model for the
"decisions free of firmware includes" style is `src/boot/BootDecisions.h:5-6`, tested by
`test/boot_decisions/BootDecisionsTest.cpp`. `lib/hal` can't include `src/`, so the new function
follows the `lib/Input` layout:

- `lib/Input/Input/WakeupClassifier.h` — header-only, no Arduino or IDF includes:

      enum class ResetKind : uint8_t { PowerOn, DeepSleep, Unknown, Other };
      enum class WakeCause : uint8_t { Undefined, GpioOrExt1, Other };
      enum class WakeupClass : uint8_t { PowerButton, AfterFlash, AfterUSBPower, Other };
      WakeupClass classifyWakeup(ResetKind reset, WakeCause cause, bool usbConnected);

  The body is exactly today's table (`HalGPIO.cpp:359-372`), row order preserved.
- `HalGPIO::getWakeupReason()` maps `esp_reset_reason()` and `esp_sleep_get_wakeup_cause()` onto
  the two enums, calls `classifyWakeup`, and maps the result onto `HalGPIO::WakeupReason`. The public
  signature (`HalGPIO.h:132-134`) and every caller (`main.cpp:375`, `HalDisplay.cpp:29`) stay the
  same.

Placement under `lib/Input` is imperfect, since wake classification is not input. It is the only
host-testable lib the HAL already depends on. The alternative, a new `lib/Power` library, would be
a new lib directory for one header, and the review can weigh that trade.

Why do this at all, when the table's logic does not change? The acceptance criterion asks that
`getWakeupReason()` "with real USB detection is checked", and its `usbConnected = true` rows have
never been reachable on this device (R§2). A host test is the only check that doesn't need a USB
cold boot on the bench. It also stops a later edit from reordering the rows unnoticed. If review
judges the extraction too heavy, the fallback is §6.3's device check alone.

## 5. Data and control flow after the fix

### 5.1 Every loop

`main loop` → `gpio.update()` → `isUsbConnected()` → (X4 Pro branch) one `digitalRead`, or one
`usb_serial_jtag_is_connected()` under S3 → edge latch (`HalGPIO.cpp:158-160`) →
`wasUsbStateChanged()` → `activityManager.requestUpdate()` (`main.cpp:793-795`) → the theme calls
`isUsbConnected()` again at draw time (`BaseTheme.cpp:74`) → bolt.

**Assumption A7 — no debounce.** The X3 path and the generic path read the signal raw every loop
(`HalGPIO.cpp:335-350`), and the C3 X4 reads its detect pin the same way. If the bench log (§7)
shows the chosen pin chattering on a plug edge, debounce becomes a finding for the owner, not a
silent addition. The edge latch costs at most one extra redraw per bounce.

**Assumption A8 — the draw-time re-read is left as is.** The themes read `isUsbConnected()`
independently of the latched value. A plug landing between the latch and the draw shows the new
state one loop early, which is harmless. Unchanged from every other board.

### 5.2 Cost

A GPIO read is one register read, with no allocation and no I²C traffic. It is cheaper than the X3
branch, which does up to two I²C transactions with a 2 ms `delay` per loop (`HalGPIO.cpp:338-344`).
There is no new heap, stack or flash-resident data beyond one `#define` and the classifier, which is a few
comparisons on three scalar arguments. Under S3, the per-tick overhead is the
IDF's own, quoted in A4.

### 5.3 Boot

`setup()` → `gpio.begin()` (`main.cpp:370`, configures the pin per A3) → `getWakeupReason()`
(`main.cpp:375`) → `classifyWakeup(...)`. Rows that become reachable on the X4 Pro:

| Reset / cause / USB | Before | After | What `main.cpp` then does |
|---|---|---|---|
| `POWERON` / undefined / USB | `PowerButton` | `AfterUSBPower` | deep sleep (`main.cpp:446-455`) |
| `UNKNOWN` / undefined / USB | `Other` | `AfterFlash` | boot, display resync (`HalDisplay.cpp:30-31`), same as `Other` |
| `DEEPSLEEP` / GPIO-EXT1 / any | `PowerButton` | `PowerButton` | unchanged |

**Assumption A9 — `POWERON` + USB → `AfterUSBPower` → sleep is the correct X4 Pro behaviour, and is
kept.** It is the C3 X4's behaviour today, and its purpose is written at `main.cpp:447` ("If USB
power caused a cold boot, go back to sleep"). The risk is a device that is fully off (not in deep
sleep), gets a power-button press while on USB, and goes straight back to sleep. The classifier
can't tell that apart from a plug. Whether the X4 Pro's power button can cause an
`ESP_RST_POWERON` at all, rather than an EXT1 wake from deep sleep, is a bench question (§7.2 step
6). If it can, the owner decides between keeping A9 and exempting the X4 Pro the way PaperMono is
(`main.cpp:449-452`). That exemption is not built speculatively.

**Assumption A10 — a flash reset over the native USB lands in `Other`, not `AfterFlash`, and that
is acceptable.** The installed IDF has separate `ESP_RST_USB` and `ESP_RST_JTAG`
(`framework-arduinoespressif32-libs/esp32s3/include/esp_system/include/esp_system.h:36-37`), so
`ResetKind::Other` covers them, and `Other` boots and resyncs exactly as `AfterFlash` does
(`main.cpp:457-461`, `HalDisplay.cpp:30-31`). This is inferred from the enum. §6.3 confirms it on
the device.

`getWakeupReason()` is called twice per boot (`main.cpp:375`, `HalDisplay.cpp:29`), and each call
re-reads USB. A plug landing between the two could classify differently. That window is tens of
milliseconds, and it exists on every board today, so it is out of scope.

## 6. Error handling and testing

### 6.1 Error handling

- A GPIO read can't fail, so there is nothing to report.
- Under S3, `usb_serial_jtag_is_connected()` returns a bool and has no error path.
- The dev build logs each USB edge once from `update()`:
  `LOG_DBG("GPIO", "USB %s", connected ? "connected" : "disconnected")`. It fires on the edge only,
  not every loop. This is the issue's "The dev build logs the detect value on a USB edge". It
  compiles out in `x4pro-gh_release` (`LOG_LEVEL=0`).
- The boot path adds `LOG_INF("GPIO", "Wakeup: reset=%d cause=%d usb=%d -> %d", ...)` inside
  `getWakeupReason()`, so §6.3 can read the classification. This is modelled on the existing boot
  log `LOG_INF("MAIN", "Device: %s", ...)` (`main.cpp:398`).

### 6.2 Host tests (TDD, written first)

`test/wakeup_classifier/WakeupClassifierTest.cpp` + `CMakeLists.txt`, modelled on
`test/nav_key_gestures/CMakeLists.txt`. One test per row of the §5.3 table and of `HalGPIO.cpp:359-372`:

- `DeepSleep` + `GpioOrExt1` → `PowerButton`, for USB true and false.
- `PowerOn` + `Undefined` + no USB → `PowerButton`.
- `PowerOn` + `Undefined` + USB → `AfterUSBPower`.
- `Unknown` + `Undefined` + USB → `AfterFlash`.
- `Unknown` + `Undefined` + no USB → `Other`.
- `DeepSleep` + `Undefined` → `Other` (a deep-sleep reset without a GPIO cause is not a button).
- `Other` reset (USB/JTAG/SW) + USB → `Other` (A10).

The red step compiles the test against a header that doesn't exist yet. `test/CMakeLists.txt` is a
shared append point (`hal-dev.md`, "Shared files"), so its `add_subdirectory(wakeup_classifier)` line
goes in the PR description for the orchestrator. It is not edited here.

`isUsbConnected()` itself has no host test. It is a `digitalRead`, and `HalGPIO` isn't built on the
host (no test target compiles it: `grep -l HalGPIO test/*/CMakeLists.txt test/CMakeLists.txt` finds nothing). It is verified on the
device (§6.3).

### 6.3 Device verification (owner)

On an `x4pro` dev build over the serial monitor (`python3 scripts/debugging_monitor.py`, since
`pio device monitor` fails on this transport):

1. Data cable plugged: the bolt appears within one loop, and `USB connected` is logged once.
2. Unplug: the bolt clears, and `USB disconnected` is logged once.
3. Wall charger: the bolt appears and clears. There is no serial, so this is judged by eye.
4. On battery for five minutes: the bolt never appears, and there are no spurious edges in the log.
5. Deep sleep, then Power: `Wakeup ... -> PowerButton`, and the device wakes normally.
6. Flash over the cable: the log shows `-> Other` or `-> AfterFlash`, and the device boots (A10).
7. If the §7.2 step 6 answer is "yes": a fully-off device plugged into USB goes back to sleep
   (`AfterUSBPower`).

Build: `pio run` (`x4pro`) and `pio run -e x4pro-gh_release`, plus `./bin/clang-format-fix` over the
whole tree.

## 7. Bench probe — how the signal is found

This is what D1 (§8) asks the owner to run. It is a throwaway build, never merged.

### 7.1 Candidates

Only pins no X4 Pro function already claims (R§6): **GPIO15, 16, 17, 21, 43, 44, 46, 47, 48**.
Excluded: GPIO0/3/7 (buttons), 1 (master rail), 2 (GT911 power), 4/10 (GT911 RST/INT), 5 (SD
enable), 6/11/12/13/14/18 (panel), 8/9 (frontlight), 19/20 (USB D−/D+), 38/39 (I²C), 40/41/42
(SDMMC), 45 (SD CS view, strap), 26-37 (flash and octal PSRAM on N16R8).

The probe reads each candidate **twice**, once with `INPUT_PULLDOWN` and once with `INPUT_PULLUP`,
200 µs apart, every 250 ms. A line driven by the board reads the same both times. A floating line follows the
pull. So each pin reports `L`, `H` or `F` (floating). A VBUS detect is a pin that changes between
`L` and `H` with the plug, identically on both pulls. It also logs `usb_serial_jtag_is_connected()`.

It only reads inputs. It never drives a candidate, so it can't short a line the board drives. GPIO46
is a strap pin; reading it after boot is harmless. GPIO43/44 are UART0, unused as a console here
(`ARDUINO_USB_CDC_ON_BOOT=1`, `platformio.ini`).

### 7.2 Procedure

1. Apply the Appendix A patch on a scratch branch and build `x4pro` with
   `-DUSB_DETECT_PROBE=1` in `platformio.local.ini`. Flash by cable or SD side-load.
2. Open the serial monitor (`scripts/debugging_monitor.py`). Every snapshot change prints one
   `PROBE` line, and the last 32 changes are rewritten to `/usb-probe.txt` on the SD card (for the
   wall-charger runs, where there is no serial).
3. **Data cable**: unplug and replug three times, waiting 3 s each time.
4. **Wall charger**: boot on battery, then plug and unplug the charger three times.
5. **Power bank** (if available): the same three cycles.
6. **Power-button cold boot**: from a fully powered-off state, if the device has one (battery
   disconnected or fully drained), press Power *with USB attached*. Does it boot, and does the log's
   `reset=` show `POWERON`? This settles A9.
7. Send back `/usb-probe.txt` and the serial log.

### 7.3 Reading the result

- A pin that goes `L`→`H` on every plug and `H`→`L` on every unplug, over the cable **and** the
  charger → S1. The mode is `INPUT` if it read the same on both pulls.
- The mirror image → S2.
- No pin, but `jtag` flips on the cable only → S3.
- Nothing → S4.
- Two or more pins qualify → pick none; ask the owner (more than one would mean one is not VBUS).

## Appendix A — probe patch (throwaway, not merged)

Hooked at the end of `HalGPIO::update()` under `#if USB_DETECT_PROBE`. State is file-static; the
snapshot is a 64-byte stack buffer (worst case 51 bytes).

```cpp
#if USB_DETECT_PROBE
#include <HalStorage.h>
#include <driver/usb_serial_jtag.h>

namespace {
constexpr uint8_t PROBE_PINS[] = {15, 16, 17, 21, 43, 44, 46, 47, 48};
constexpr size_t PROBE_LOG_LINES = 32;
constexpr unsigned long PROBE_PERIOD_MS = 250;
char probeLast[64] = "";
String probeLog;  // throwaway probe: at most 32 short lines
size_t probeLines = 0;
unsigned long probeAt = 0;

char probeLevel(uint8_t pin) {
  pinMode(pin, INPUT_PULLDOWN);
  delayMicroseconds(200);
  const int down = digitalRead(pin);
  pinMode(pin, INPUT_PULLUP);
  delayMicroseconds(200);
  const int up = digitalRead(pin);
  if (down == up) return down ? 'H' : 'L';
  return 'F';
}
}  // namespace

static void runUsbDetectProbe() {
  if (millis() - probeAt < PROBE_PERIOD_MS) return;
  probeAt = millis();
  char snap[64];
  int n = snprintf(snap, sizeof(snap), "jtag=%d", usb_serial_jtag_is_connected() ? 1 : 0);
  for (uint8_t pin : PROBE_PINS) {
    n += snprintf(snap + n, sizeof(snap) - n, " %u=%c", pin, probeLevel(pin));
  }
  if (strcmp(snap, probeLast) == 0) return;
  strcpy(probeLast, snap);
  LOG_INF("PROBE", "t=%lu %s", millis(), snap);
  if (probeLines == PROBE_LOG_LINES) {
    probeLog.remove(0, probeLog.indexOf('\n') + 1);
    --probeLines;
  }
  probeLog += String(millis()) + " " + snap + "\n";
  ++probeLines;
  Storage.writeFile("/usb-probe.txt", probeLog);
}
#endif
```

The probe also logs the boot line from §6.1 (`reset=`, `cause=`) for §7.2 step 6.
`Storage.writeFile` overwrites the file (`lib/hal/HalStorage.h:27-29`). The probe is diagnostic, not
a store, so the §"Storage discipline" rules are deliberately not applied. It writes only on a
change, at SD root, never under `/.berean/`.
