# Issue #185 — X4 Pro charging indicator: design

Research: `docs/superpowers/research/2026-09-29-issue-185-research.md` (cited below as "R§n").
Branch base: `main` at `a4e2288d`, freeink-sdk submodule at `310ec61`.

The detect signal was settled on hardware by the owner (decision D1, bench results in §7):
**GPIO21, active HIGH, read with the internal pull-down.** Everything below is built on that one
confirmed signal, and on nothing guessed. Decision D2 put the SDK corrections in a bereanOS-owned
fork of `freeink-sdk` (§4.6). The pin therefore lives in the X4 Pro board profile, as its one source
of truth.

## 1. Problem

With USB plugged in, the X4 Pro charges, but the battery icon never shows the charging bolt.

- The themes draw the bolt from `gpio.isUsbConnected()` (`src/components/themes/BaseTheme.cpp:74`,
  `:370`; `src/components/themes/lyra/LyraTheme.cpp:27`). The loop requests a redraw on a USB edge
  (`src/main.cpp:791-795`), latched in `HalGPIO::update()` (`lib/hal/HalGPIO.cpp:158-160`).
- `HalGPIO::isUsbConnected()` returns false when `BoardConfig::ACTIVE.usbDetect < 0`
  (`lib/hal/HalGPIO.cpp:347-349`). The X4 Pro profile sets it to `PIN_UNASSIGNED`
  (`freeink-sdk/libs/hardware/BoardConfig/include/BoardConfig.h:1400`). The X3 branch above it
  (`HalGPIO.cpp:335-346`) is never taken on this build, because `_deviceType` is hard-set to X4
  outside `FREEINK_MCU_C3` (`HalGPIO.cpp:137-139`).
- The gauge can't help. `readGaugeCharging()` returns `known = false` for the CW2017
  (`freeink-sdk/libs/hardware/BatteryMonitor/src/BatteryMonitor.cpp:194-201`).

A second symptom follows from the same false: `getWakeupReason()` (`HalGPIO.cpp:353-373`) uses USB
presence to separate a power-button cold boot from a USB-plug cold boot. On the X4 Pro every
`ESP_RST_POWERON` boot is classified `PowerButton` today, and the `AfterFlash` and `AfterUSBPower`
rows are unreachable (R§2). The bench showed that simply making USB real would be *wrong* there. A
deliberate Power press from fully off, with USB attached, boots with `reset=1` (`ESP_RST_POWERON`)
and `cause=0` (§7, test 4). The existing table would call that `AfterUSBPower` and put the device
straight back into deep sleep (`main.cpp:446-455`).

The documentation is stale too:

- `BoardConfig.h:1400` names GPIO10 as the detect candidate. GPIO10 is the GT911 INT line
  (`BoardConfig.h:1402`, value at `:1414`), and the detect pin is GPIO21.
- `freeink-sdk/docs/xteink-x4pro-support.md:277-279` says the pin was "not conclusively identified".
- `xteink-x4pro-support.md:259` gives the GT911 pins reversed, contradicting `:125` and the profile
  (R§6).

## 2. Goal

1. On the X4 Pro, `HalGPIO::isUsbConnected()` returns true while USB power is present, from GPIO21.
   That covers a data cable and a wall charger alike.
2. The bolt appears and clears on plug and unplug, through the existing edge latch and redraw
   (`HalGPIO.cpp:158-160`, `main.cpp:793`). A brief glitch on the line must not flicker it (§4.3).
3. `getWakeupReason()` with real USB detection is correct on the X4 Pro: a Power-press cold boot
   is never classified `AfterUSBPower` (§4.4). The table is pinned by a host test.
4. The stale GPIO10 comment, the "not conclusively identified" note and the reversed GT911 line
   are corrected in the SDK, on the fork's `berean` branch. The submodule points at that fork
   (decision D2, §4.6).

## 3. Non-goals

- **Charge-complete / "full" state.** The bolt means "USB power present", as it already does for
  every board on the `usbDetect` path (`HalGPIO.cpp:350`). Nothing on the CW2017 bus reports charge
  termination (`BatteryMonitor.cpp:196-197`).
- **Gauge-trend inference, and the USB-Serial/JTAG state.** GPIO21 covers both the host and the
  wall-charger cases on the bench (§7), so neither fallback from the issue is needed.
- **Other boards.** The C3 X4, the X3 and every other profile keep their current paths unchanged.
  The pull-down, the debounce (§4.3) and the wake exemption (§4.4) are X4 Pro only.
- **Upstream Free-Ink.** No PR goes to `Free-Ink/freeink-sdk` (D2). Pulling later upstream SDK
  changes means merging them into the fork's `berean`, which is outside this issue.
- **Boot policy.** What `main.cpp` does for each `WakeupReason` (`main.cpp:436-464`,
  `HalDisplay.cpp:29-32`) is unchanged. Only the X4 Pro's classification input and one table row
  change.
- **The probe.** The bench build (scratch branch `probe/185-usb-detect`, local only) is never
  merged. Putting normal firmware back on the owner's device is the owner's call.
- **Sensing USB during deep sleep.** The X4 Pro wakes only on the power button (R§2). The bolt is
  resolved on the first loops after any wake.

## 4. Architecture

### 4.1 Where the X4 Pro signal is read

**Assumption A1 — the pin is `usbDetect = 21` in the X4 Pro profile, the single source of truth.
There is no HAL-side pin constant.** The owner's D2 answer says that if `usbDetect = 21` goes in
BoardConfig, there must be no separate `X4PRO_USB_DETECT`. Modelled on the M5PaperS3 profile,
`5, // usbDetect GPIO5, HIGH = USB present` (`BoardConfig.h:1252`), which the generic
`digitalRead(BoardConfig::ACTIVE.usbDetect) == HIGH` (`HalGPIO.cpp:350`) already reads. The profile
line at `BoardConfig.h:1400` becomes:

    21,  // usbDetect: VBUS sense, HIGH = USB power present (host or wall charger); floats ~280 ms
         // while VBUS rises, so read it with INPUT_PULLDOWN. Bench-confirmed 2026-09-29 (bereanOS #185).

Nothing else in the tree reads `usbDetect`: `grep -rn usbDetect freeink-sdk/libs src lib`, outside
`BoardConfig.h`, finds only `HalGPIO.cpp:347` and `:350` (R§2). So the profile value changes no SDK
behaviour; the HAL is its only consumer.

GPIO21 is free on the X4 Pro. It appears nowhere else in the X4 Pro profile
(`BoardConfig.h:1363-1474`). `HalGPIO.h:10` defines `EPD_CS 21` for the C3 X4, and
`HalDisplay.cpp:9` passes it to the display constructor. But `FreeInkDisplay::begin()` takes its
pins from `BoardConfig::ACTIVE.display` and documents the constructor pins as "legacy and unused"
(`freeink-sdk/libs/display/FreeInkDisplay/src/FreeInkDisplay.cpp:191-198`). The only other use,
`SPI.begin(... EPD_CS)` at `HalGPIO.cpp:131`, is inside `#if FREEINK_MCU_C3`. The bench confirms
this: GPIO21 tracked VBUS undisturbed through a full boot (§7).

**Assumption A2 — the X4 Pro's pull mode and debounce are HAL behaviour, keyed on
`BoardConfig::isX4Pro()`.** `BoardProfile` has no field for a detect pin's pull mode or filtering
(the field is a bare `int8_t usbDetect;`, `BoardConfig.h:646`). Adding one would change the struct
every profile initialises positionally, which is a far wider SDK change than this issue needs. So
the pin number comes from the profile, and how the X4 Pro reads it lives in `HalGPIO`. That split is
modelled on the X3 branch (`HalGPIO.cpp:335-346`) and on `isX4Pro()` at `HalGPIO.cpp:296`.

**Assumption A3 — the pin is configured once in `HalGPIO::begin()` with `INPUT_PULLDOWN`, under
`BoardConfig::isX4Pro()`.** Modelled on the C3 X4's `pinMode(UART0_RXD, INPUT);`
(`HalGPIO.cpp:133-135`), the one existing `pinMode` for a detect pin. The pull-down is the owner's
instruction (D1). While VBUS is rising, the line floats for about 280 ms (§7, `21=F`), and the
pull-down resolves that window to "not connected". `begin()` runs before the first
`getWakeupReason()` (`main.cpp:370`, then `:375`). Other boards get no new `pinMode`.

### 4.2 Reading it

- `readUsbDetectPin()`, a private helper that holds today's generic read: `return
  digitalRead(BoardConfig::ACTIVE.usbDetect) == HIGH;` (from `HalGPIO.cpp:350`). The generic path
  and the X4 Pro filter both call it, so there is one read expression.
- `isUsbConnected()` becomes: the X3 branch, unchanged; then
  `if (BoardConfig::isX4Pro()) return usbPresence.stable();`; then the unchanged `usbDetect < 0`
  guard and `return readUsbDetectPin();`. The X4 Pro check sits after the X3 branch, which is never
  taken on this build (§1), and before the generic read.

### 4.3 Debounce

The owner asked the bolt not to flicker on the transient, "e.g. require a stable level across two
update() ticks if cheap" (D1). On the bench, each plug edge is monotonic at the sampling rate the
probe had (250 ms). Plug reads F, which the pull-down reads as L, then H. Unplug reads H, decaying,
then L. A single glitch sample inside that ~300 ms window can't be ruled out at the loop's 10 ms
rate (`main.cpp:822`), and it would cost a spurious bolt flash plus two redraws.

**Assumption A4 — a two-sample stable-level filter, X4 Pro only, as a pure host-tested type.**
`lib/Input/Input/StableLevel.h`, header-only:

    namespace input {
    // A level that only changes after two consecutive samples agree.
    class StableLevel {
     public:
      void begin(bool level);   // seeds both the stable and the last sample
      bool update(bool level);  // returns the stable level after this sample
      bool stable() const;
     private:
      bool stableLevel = false;
      bool lastSample = false;
    };
    }

Modelled on `input::NavKeyGestures` (`lib/Input/Input/NavKeyGestures.h`), the pure logic `HalGPIO`
already owns and feeds from `update()` (`HalGPIO.cpp:143-156`, seeded once through
`beginWithKeysDown` at `:152`). It costs two bools of state and no allocation. `HalGPIO` holds
`input::StableLevel usbPresence`:

- `begin()` (X4 Pro): `pinMode(BoardConfig::ACTIVE.usbDetect, INPUT_PULLDOWN)`, then
  `usbPresence.begin(readUsbDetectPin())`. From its
  first call, `getWakeupReason()` sees a seeded value.
- `update()` (X4 Pro): `usbPresence.update(readUsbDetectPin())` before the existing
  `const bool connected = isUsbConnected();` (`HalGPIO.cpp:158`). The edge latch below it is
  unchanged.

Latency is at most one extra loop (~10 ms), on top of the line's own ~280 ms edge.

**Assumption A5 — the draw-time re-read stays.** The themes call `isUsbConnected()` independently
of the latch (`BaseTheme.cpp:74`). On the X4 Pro that now returns the filtered value, so the latch
and the draw agree.

### 4.4 Wake classification

The table in `getWakeupReason()` (`HalGPIO.cpp:359-372`) assumes a `POWERON` boot with USB present
was caused by the plug. On the X4 Pro the bench shows a Power press produces the same `POWERON` /
`cause=0` (§7, test 4). Classifying it `AfterUSBPower` would send a deliberate press back to deep
sleep (`main.cpp:446-455`). The owner said not to misclassify it (D1).

**Assumption A6 — on the X4 Pro, `POWERON` is always `PowerButton`, whatever the USB state.** That
keeps the X4 Pro exactly where it is today for that row. Today USB always reads false, so
`POWERON` → `PowerButton` (`HalGPIO.cpp:363-365`). The press can't be told apart from a plug by
reset reason or wake cause, since they are identical. Whether plugging USB into a fully-off X4 Pro
cold-boots it at all is not established; the bench did not test a plug without a press. If it does,
that boot runs as a power-button boot, which is again exactly today's X4 Pro behaviour. So this is
never a *new* misclassification. It is modelled on the per-board carve-out `main.cpp:449-452` makes
for PaperMono, with the carve-out made in the classifier so it can be host-tested.

**Assumption A7 — the table moves into a pure, host-tested function; the ESP-IDF reads stay in
`HalGPIO`.** `lib/Input/Input/WakeupClassifier.h`, header-only, no Arduino or IDF includes, in the
header-only inline style of `src/boot/BootDecisions.h` (its role: "free of firmware includes so
they can be tested on the host", `BootDecisions.h:5-6`). It goes in `lib/Input` because
`lib/hal` can't include `src/`, and `lib/Input` is the host-testable lib `HalGPIO` already depends
on (`HalGPIO.h:6`):

    namespace input {
    enum class ResetKind : uint8_t { PowerOn, DeepSleep, Unknown, Other };
    enum class WakeCause : uint8_t { Undefined, GpioOrExt1, Other };
    enum class WakeupClass : uint8_t { PowerButton, AfterFlash, AfterUSBPower, Other };
    // usbCanWakeFromOff: false where a Power press also cold-boots as POWERON (X4 Pro, #185).
    WakeupClass classifyWakeup(ResetKind reset, WakeCause cause, bool usbConnected, bool usbCanWakeFromOff);
    }

The body is today's table (`HalGPIO.cpp:359-372`), row order preserved. The one change: the
`PowerOn` rows use `usbConnected && usbCanWakeFromOff`. `getWakeupReason()` maps
`esp_reset_reason()` / `esp_sleep_get_wakeup_cause()` onto the enums (`ESP_RST_POWERON` →
`PowerOn`, `ESP_RST_DEEPSLEEP` → `DeepSleep`, `ESP_RST_UNKNOWN` → `Unknown`, anything else →
`Other`; `ESP_SLEEP_WAKEUP_UNDEFINED` → `Undefined`, `_GPIO` / `_EXT1` → `GpioOrExt1`, anything else →
`Other`). It passes `usbCanWakeFromOff = !BoardConfig::isX4Pro()` and maps the result back onto
`HalGPIO::WakeupReason`. The public signature (`HalGPIO.h:132-134`) and both callers
(`main.cpp:375`, `HalDisplay.cpp:29`) are untouched.

Placement is imperfect, since wake classification is not input. A new `lib/Power` for one header
is the alternative, and review may weigh it.

### 4.5 Rows after the fix

| Reset / cause / USB | X4 Pro before | X4 Pro after | Other boards |
|---|---|---|---|
| `DEEPSLEEP` / GPIO-EXT1 / any | `PowerButton` | `PowerButton` | unchanged |
| `POWERON` / undefined / no | `PowerButton` | `PowerButton` | unchanged |
| `POWERON` / undefined / yes | `PowerButton` | **`PowerButton`** (A6) | `AfterUSBPower`, unchanged |
| `UNKNOWN` / undefined / yes | `Other` | `AfterFlash` | unchanged |
| any other | `Other` | `Other` | unchanged |

**Assumption A8 — `UNKNOWN` + USB becoming `AfterFlash` is harmless.** `AfterFlash` and `Other` take
the same path, which is to boot (`main.cpp:457-461`) and resync (`HalDisplay.cpp:30-31`). A reset
from the native USB peripheral has its own `ESP_RST_USB` / `ESP_RST_JTAG`
(`framework-arduinoespressif32-libs/esp32s3/include/esp_system/include/esp_system.h:36-37`), so it
lands in `Other` either way.

`getWakeupReason()` is called twice per boot (`main.cpp:375`, `HalDisplay.cpp:29`). On the X4 Pro
it now returns the filtered value, which only moves in `update()`, so the two calls can differ only
if an `update()` tick sees a stable change between them. That is not a new window: every board has
it today with a raw read.

## 5. Data and control flow after the fix

**Boot:** `gpio.begin()` (`main.cpp:370`) → X4 Pro: `pinMode(ACTIVE.usbDetect /* 21 */,
INPUT_PULLDOWN)`, `usbPresence.begin(read)` → `getWakeupReason()` (`main.cpp:375`) → `classifyWakeup(...,
usbCanWakeFromOff=false)` → `POWERON` is `PowerButton` → the normal boot path (`main.cpp:438-445`;
the X4 Pro's `verifyPowerButtonWakeup` returns true, `HalGPIO.cpp:293-298`).

**Every loop:** `gpio.update()` → `usbPresence.update(readUsbDetectPin())` →
`isUsbConnected()` returns `stable()` → edge latch (`HalGPIO.cpp:158-160`) →
`main.cpp:793` `requestUpdate()` → the theme reads `isUsbConnected()` → bolt.

**Cost:** one GPIO register read and two bool compares per loop. There is no allocation, no I²C,
and no `delay`, which makes it cheaper than the X3 branch (`HalGPIO.cpp:338-344`, up to two I²C
reads and a 2 ms delay). No new flash-resident data beyond two small inline headers, and one
profile value that replaces `PIN_UNASSIGNED` in the existing `constexpr` profile. The internal
pull-down draws current only while VBUS is present, when the device is on external power anyway.

## 6. Error handling and testing

### 6.1 Error handling and logging

- A GPIO read can't fail, so there is nothing to report.
- **Assumption A9 — one log line per USB edge:** `LOG_DBG("GPIO", "USB %s", connected ? "connected"
  : "disconnected")`, inside the existing `if` of the edge latch in `update()`, so it fires on the
  edge only. This is the issue's "The dev build logs the detect value on a USB edge"
  (issue #185, How to verify). It compiles out of `x4pro-gh_release` (`LOG_LEVEL=0`).
- **Assumption A10 — one boot line:** `LOG_INF("GPIO", "Wakeup: reset=%d cause=%d usb=%d -> %d",
  ...)` in `getWakeupReason()`. It is modelled on `LOG_INF("MAIN", "Device: %s", ...)`
  (`main.cpp:398`), and it is how §6.3 reads the classification on the device.

### 6.2 Host tests (TDD: written first, run red, then green)

`test/stable_level/StableLevelTest.cpp` and `test/wakeup_classifier/WakeupClassifierTest.cpp`,
each with a `CMakeLists.txt` modelled on `test/nav_key_gestures/CMakeLists.txt` (include
`${REPO_ROOT}/lib/Input`, link `crosspoint_test_common` and `GTest::gtest_main`, and call
`gtest_discover_tests`). Both headers are header-only, so no `.cpp` goes in the sources list.

`StableLevel`:
- `begin(true)` → `stable()` is true, with no update needed.
- A single differing sample does not change `stable()`. The next agreeing sample reverts cleanly
  (a glitch is rejected).
- Two consecutive differing samples change it on the second.
- The bench sequences, fed one sample per tick: plug `L L F→L H H` settles to true only after two
  `H`. Unplug `H H(decay) L L` settles to false only after two `L`.

`classifyWakeup`, one test per row of §4.5, with `usbCanWakeFromOff` both ways:
- `DeepSleep` + `GpioOrExt1` → `PowerButton`, for any USB.
- `PowerOn` + `Undefined` + no USB → `PowerButton`.
- `PowerOn` + `Undefined` + USB + `usbCanWakeFromOff=true` → `AfterUSBPower` (other boards,
  unchanged).
- `PowerOn` + `Undefined` + USB + `usbCanWakeFromOff=false` → `PowerButton` (**the X4 Pro fix**, A6).
- `Unknown` + `Undefined` + USB → `AfterFlash`. `Unknown` + no USB → `Other`.
- `DeepSleep` + `Undefined` → `Other`. `Other` reset + USB → `Other` (A8).

`test/CMakeLists.txt` is a shared append point (`hal-dev.md`, "Shared files"). The two
`add_subdirectory(stable_level)` / `add_subdirectory(wakeup_classifier)` lines go in the PR
description for the orchestrator, and that file is not edited here.

`isUsbConnected()` and the enum mapping in `getWakeupReason()` have no host test. `HalGPIO.cpp` is
compiled by no host target (`grep -l HalGPIO test/*/CMakeLists.txt test/CMakeLists.txt` finds
nothing), so they are verified on the device (§6.3).

### 6.3 Verification

Build: `pio run` (`x4pro`), `pio run -e x4pro-gh_release`, the host suites, and
`./bin/clang-format-fix` over the whole tree. Submodule: the fresh-clone and CI-checkout checks in
§4.6.

On the device (owner), with an `x4pro` dev build and `python3 scripts/debugging_monitor.py`:

1. Data cable plugged: the bolt appears, and `USB connected` is logged once.
2. Unplug: the bolt clears within about a third of a second, and `USB disconnected` is logged once.
3. Wall charger: the bolt appears and clears (judged by eye, since there is no serial).
4. On battery for five minutes: no bolt, and no spurious edge lines.
5. Deep sleep, then Power: `Wakeup ... -> ` `PowerButton`, and a normal wake.
6. From fully off, Power with USB attached: the device boots and stays up (`reset=1 ... -> `
   `PowerButton`). This is the bench's test 4, and the regression A6 prevents.
7. Flash over the cable: it boots (`-> Other` or `AfterFlash`).

## 7. Bench result (decision D1, owner-run)

The probe (scratch branch `probe/185-usb-detect`, local only) read GPIO15/16/17/21/43/44/46/47/48
with pull-down then pull-up (L/H/F), plus `usb_serial_jtag_is_connected()`, every 250 ms, and logged
changes to `/usb-probe.txt`. The owner's results, fetched over File Transfer:

| Step | `/usb-probe.txt` |
|---|---|
| Data cable plugged | `jtag=1 17=H 21=H` |
| Unplugged | `177574 jtag=0 21=L` |
| Replug | `204751 jtag=0 21=F` (~280 ms floating while VBUS rises), then `205030 jtag=1 21=H` |
| Unplug from the computer | `234566 jtag=0 21=H` (~280 ms decay), then `234849 21=L` |
| Wall charger | `250401 jtag=0 21=H`, so GPIO21 senses power, not host enumeration |
| Power press from fully off, USB attached | `BOOT reset=1 cause=0`: boots, `ESP_RST_POWERON` |

- GPIO17 read H in every state, so it is tied high and is not the signal.
- Every other probed pin floated throughout.
- Test 3 (power bank) was not run; the wall charger covers the no-host case.

Classification per the draft §7.3: **S1**, one pin active-HIGH on both cable and charger.

## 8. Decisions

- **D1 — the detect signal.** Answered: GPIO21, active HIGH, `INPUT_PULLDOWN`, tolerate the
  ~300 ms edge (§7, A3, A4, A6).
- **D2 — where the stale docs get corrected.** Answered: in bereanOS only, on the fork
  `victorstein/freeink-sdk` branch `berean`, with `.gitmodules` repointed and the gitlink bumped in
  this PR. There is no Free-Ink PR. `usbDetect = 21` goes in the profile, with no HAL pin constant
  (§4.1, §4.6).
