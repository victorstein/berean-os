# Issue #156 — Bible tile: find sideloaded/older Bibles, offer a download when none

Research: `docs/superpowers/research/2026-09-27-issue-156-research.md`.
Base: `d956cc8b`. Surface: `ui`. Tier: `heavy`.

## Problem

Since #104 (`08d98a9f`), the launcher finds a Bible in two ways only
(`src/activities/launcher/LauncherActivity.cpp:115-116`):

1. `PubKeyRegistry::findBySymbol({"nwt"})`. The only writer of an `nwt` entry
   is `publication::download` (`src/network/PublicationDownloader.cpp:184,239`).
2. `findBibleOnCard()` (`LauncherActivity.cpp:183-189`). It accepts only a file
   named `nwt_<LANG>.epub` (`LauncherBible.h:18-41`), and only in the download
   folder or `/` (`src/util/CardBooks.cpp:35-44`).

A Bible that was sideloaded under another name, sits in a subfolder, or was
downloaded before the registry existed matches neither, so the tile says "No
Bible on the card". The device owner's own Bible is in exactly that case.

With no Bible, a tap on the tile goes to the file browser
(`LauncherActivity.cpp:547-553`). The comment there calls that a placeholder.

## Goal

1. **Self-healing recognition.** When the reader opens a book that it already
   knows is the Bible, it records the book in the registry under `nwt`, once.
   After that, step 1 finds the book whatever its name or folder.
2. **A first-launch fallback.** When the registry and the card scan both miss,
   the launcher uses the pre-#104 match on recent books, as the last step.
3. **A download offer.** When all three steps miss, the tile invites a
   download. A tap asks for confirmation, then downloads the NWT through
   `publication::download` with Wi-Fi handled by `WifiSession`. On success the
   launcher shows the Bible. The file browser is still one tap away.

## Non-goals

- No change to `src/study/` (another task in this batch owns it). There is no
  new `PubKeyRegistry` API: registration uses the existing `lookup` and
  `record` (`src/study/PubKeyRegistry.h:22,25`).
- No change to `CardBooks::list()`'s scope. Recursing the card on every
  launcher entry would cost more than the other steps together.
- The launcher never opens or parses an EPUB to recognise one (issue
  constraint).
- No registry pruning. A finished Bible moved to the read folder
  (`EpubReaderActivity.cpp:150-172`) leaves a stale entry. `findBySymbol`
  already skips entries whose file is gone (`PubKeyRegistry.cpp:74`), and the
  next open re-registers the new path.
- No change to `publication::download` or `HttpDownloader` (`network`
  surface).
- No new setting.

### Pure helpers in `LauncherBible.h`

The header stays free of firmware includes, as its comment at `:6-7` requires.
It gains the following:

```cpp
enum class BibleLookup : uint8_t { Registry, CardScan, Recents };
inline constexpr BibleLookup BIBLE_LOOKUP_ORDER[] = {BibleLookup::Registry, BibleLookup::CardScan, BibleLookup::Recents};

// Runs each lookup in order and stops at the first hit. `tryLookup(step)` returns std::optional<std::string>.
template <typename TryLookup>
std::optional<std::string> resolveBible(TryLookup&& tryLookup);

// The pre-#104 guess, used only as the last lookup.
constexpr bool looksLikeBibleInRecents(std::string_view path, std::string_view title);

// Records `path` as the Bible unless the registry already knows it. Returns whether it wrote.
template <typename Lookup, typename Record>
bool registerBibleIfUnknown(bool isBible, const std::string& path, Lookup&& isRegistered, Record&& recordAsBible);
```

The laziness in `resolveBible` is what the tests assert: a later lookup never
runs once an earlier one has hit. The templates take callables, as
`ButtonNavigator::Callback` does (`src/util/ButtonNavigator.h:18-23`). Each
template is instantiated once in firmware, so no `std::function` is involved
(CLAUDE.md, "Template and std::function bloat").

## Data and control flow

### A. Launcher resolution (`resolveTargets`, `LauncherActivity.cpp:113-129`)

```
biblePath.clear(); bibleSubtitle = tr(STR_BIBLE_SUBTITLE_NONE)   // text changes, see Strings
found = resolveBible([&](BibleLookup step) {
  switch (step) {
    Registry: return PubKeyRegistry::findBySymbol({BIBLE_SYMBOL});   // unchanged
    CardScan: return findBibleOnCard();                               // unchanged
    Recents:  return findBibleInRecents(recents);                     // new, static
  }
});
LOG_INF(MODULE, "Bible: %s (%s)", path-or-"(none found)", step name)
found → the existing block at :118-129, unchanged
```

`findBibleInRecents` walks `RECENT_BOOKS.getBooks()` (already loaded at
`:99-101`) in order, most recent first. It returns the first entry where
`looksLikeBibleInRecents(book.path, book.title)` holds **and**
`Storage.exists(book.path)`.

- **A1 — Match rule, verbatim from pre-#104.** The rule is: `path` contains
  `"nwt"`, or `title` contains `"Nuevo Mundo"`, or `title` contains
  `"New World"`. All three are case-sensitive substring tests, and the path
  test covers the whole path, folders included. This is the exact lambda
  removed in `08d98a9f` (quoted in the research note). The issue asks for "the
  old recents match", so the rule is not widened or narrowed.
- **A2 — The recents hit must exist on the card.** The old code did not check
  this. Without the check, a deleted Bible still in `recent.json` would fill
  the tile, and a tap would open nothing: `ReaderActivity::onEnter` finishes
  on a missing file (`ReaderActivity.cpp:44-48`). The cost is one `exists`
  call, on the recents path only.
- **A3 — The recents step runs only after both earlier steps miss.**
  `resolveBible` guarantees this. It is the issue's resolution order, and the
  reason a registered Bible beats a non-Bible titled "New World…".
- **A4 — No registration from the launcher.** A recents hit is not written to
  the registry at launcher time. The issue puts registration on open, and
  keeping it off the launcher keeps `pubkeys.json` writes off the path that
  runs on every home-screen entry. The recents hit is registered the next time
  the book opens.

### B. Register on open (`EpubReaderActivity::loadBook`)

Placed after the `#if BOARD_HAS_PSRAM` block (`EpubReaderActivity.cpp:244-261`)
and before `return true` (`:263`):

```cpp
registerBibleIfUnknown(
    epub->getBibleBookNavSpineIndex() >= 0, epub->getPath(),
    [](const std::string& p) { return PubKeyRegistry::lookup(p).has_value(); },
    [](const std::string& p) { return PubKeyRegistry::record(p, study::RegisteredPub{std::string(BIBLE_SYMBOL), "", ""}); });
```

`registerBibleIfUnknown` returns without touching the registry when
`isBible` is false. It calls `isRegistered` next, and calls `recordAsBible`
only when that returns false. It logs `LOG_INF` on a write and `LOG_ERR` when
`record` refuses.

- **B1 — The Bible signal is `getBibleBookNavSpineIndex() >= 0`.** Every
  Bible-aware site already uses it: `StudyStore.cpp:34`,
  `BibleSearchStore.cpp:124`, `BibleNavigationActivity.cpp:61`,
  `EpubReaderActivity.cpp:296,1618`. It is cached on the `Epub`
  (`Epub.cpp:981-986`), so a non-Bible book pays one int compare and no file
  I/O. The issue says not to invent a new heuristic.
- **B2 — An NWT-family book with another symbol is registered as `nwt` too,
  if it is unregistered.** A Study Bible sideloaded without a registry entry
  probably carries `biblebooknav.xhtml` as well (not verified; see research
  §2). It would then be recorded as `nwt` and could take the tile. This is
  accepted: it is still a Bible, it is the book the reader already treats as
  the Bible, and a Buscar download of it keeps its own symbol (B3).
- **B3 — Any existing entry wins, whatever its symbol.** The skip condition is
  "`lookup` returns anything", not "an `nwt` entry exists". `record`
  overwrites (`PubKeyRegistry.cpp:36-39`), so this is what keeps a Buscar
  `nwtsty` entry from being relabelled. It is also what makes the operation
  idempotent: the second open reads and does not write.
- **B4 — The language is recorded as `""`.** The registry expects a JW code
  (`"S"`), and the EPUB only offers `dc:language` (`"es"`), a different
  vocabulary (`Epub.h:59`). The setting would be a guess that is wrong for a
  user who reads a Bible in another language. For the Bible the field is
  informational only: `resolvePubKey` returns `BIBLE_PUB_KEY` before it reads
  `registered` (`lib/StudyStore/StudyStore/PubKey.cpp:25`), and
  `PublicationsActivity` shows only symbol and issue (`:60-63`). `record`
  requires only a non-empty symbol (`PubKeyRegistry.cpp:21`).
- **B5 — No change to the study key.** Follows from B4's citation. No tag or
  chapter data moves.
- **B6 — Where it runs.** Registration runs in `loadBook`, which is called
  from `ReaderActivity::onEnter` (`ReaderActivity.cpp:41-61`). That is not the
  render path. It runs on every open, and costs one extra read of
  `pubkeys.json` for a Bible only; `StudyStore::openPublication` already reads
  it once (`StudyStore.cpp:40`). The write happens at most once per path.
- **B7 — It sits outside `#if BOARD_HAS_PSRAM`.** Registration holds no
  resident document, so the reason for that gate (`:256-259`) does not apply.
  This device always has PSRAM anyway.
- **B8 — Storage discipline.** `record` already writes atomically, checks the
  byte budget, refuses newer versions, and refuses to overwrite an unreadable
  file (`PubKeyRegistry.cpp:24-47`). Its owning task is the main loop task,
  the same one the downloader's `record` runs on. Every call goes through
  `HalStorage`'s mutex.

### C. The tile with no Bible

- **C1 — The subtitle text changes, the key does not.** The launcher keeps
  `STR_BIBLE_SUBTITLE_NONE` (`LauncherActivity.cpp:114`), and only its text
  changes:
  - english: `"Not on the card · tap to download"`
  - spanish: `"No está en la tarjeta · toca para descargar"`

  Only these two files define the key (`grep -rl STR_BIBLE_SUBTITLE_NONE
  lib/I18n/translations` → 2), so no language is left with stale text, and no
  now-unused key ships in flash. `·` already renders in UI strings
  (`STR_BIBLE_SEARCH_STATUS`, `english.yaml:35`).
- **C2 — A tap starts the download screen.** `openBible()` with an empty
  `biblePath` starts `BibleDownloadActivity` through `startActivityForResult`.
  The result handler is the same as `openPublications`'s: `resolveTargets();
  requestUpdate();`.
- **C3 — After a successful download, the user returns to the launcher.** The
  Bible is not opened automatically. The launcher re-resolves and the tile
  shows the Bible and its cover, which is the issue's device check "the tile
  then shows the Bible". It also mirrors `openPublications`, and avoids
  stacking a first-open indexing popup (`EpubReaderActivity.cpp:186-189`) onto
  a screen the user just watched download. One more tap opens the Bible.

### D. `BibleDownloadActivity`

States: `Confirm → WifiSelection → Downloading → (finish ok) | Failed`.

The class shape copies `MeetingDownloadActivity` (`.h:22-90`): `Activity`
plus private `UiAppHost`, `std::optional<WifiSession> wifiSession` declared
last and emplaced in `onEnter` (`WifiSession.h:6-7`;
`MeetingDownloadActivity.cpp:39`), `preventAutoSleep() = true`, and hook
trampolines. The layout is a header plus `screen.body()` content.

1. **Confirm**, the first paint. A dialog in the shape of `buildDialog`
   (`BibleSearchActivity.cpp:744-782`):
   - title `STR_BIBLE_DOWNLOAD_TITLE`;
   - message `STR_BIBLE_DOWNLOAD_PROMPT`, formatted with the language name and
     the size;
   - primary button `STR_DOWNLOAD` (exists, `english.yaml:223`);
   - secondary button `STR_CHOOSE_FILE`.

   Back or a left-edge swipe finishes the screen, cancelled.
   - **D1 — The edition and language are named, with an approximate size.**
     The language name comes from `SETTINGS.publicationLanguage` through the
     same `STR_LANG_SPANISH` / `STR_LANG_ENGLISH` mapping Settings uses
     (`src/SettingsList.h:245-247`). The size is
     `constexpr unsigned NWT_APPROX_MEGABYTES = 15`, measured on 2026-09-27 as
     14,945,282 B (S) and 15,652,378 B (E). The exact size is only known after
     the resolve request (research §2), and fetching it before asking would
     need Wi-Fi before the user has agreed to anything.
   - **D2 — The escape hatch is on the confirm dialog.**
     `STR_CHOOSE_FILE` calls `activityManager.goToFileBrowser()`, as
     `BmpViewerActivity.cpp:260` does. `replaceActivity` clears the stack,
     launcher included (`ActivityManager.cpp:143-150`), so this matches
     today's no-Bible tap exactly. The file browser is only reachable from the
     launcher through this tile (`grep -rn goToFileBrowser src`: launcher,
     `ReaderUtils.h:263`, `BmpViewerActivity.cpp:260`), so it cannot simply be
     dropped.
2. **Download pressed.** If `WiFi.status() == WL_CONNECTED`, the download
   starts. Otherwise the state is `WifiSelection` and
   `WifiSelectionActivity(renderer, mappedInput, /*autoConnect=*/true,
   /*meetingPrefetch=*/false)` starts, exactly as at
   `MeetingDownloadActivity.cpp:64-69`.
3. **Downloading.**
   - The request is `publication::Request{symbol = "nwt", issue = "",
     language = CrossPointSettings::langWritten(SETTINGS.publicationLanguage),
     folder = publication::resolveDownloadFolder(), force = false}`. Language
     comes from `MeetingDownloadActivity.cpp:269`, folder from `:138`.
   - The work runs from `loop()` behind a `downloadPending` flag after the
     first paint, as `sequencePending` does at `:92-99`.
   - The progress screen is `buildProgressScreen` (`:332-375`) minus the
     "n / m" phase line: status, filename, bar, Cancel button.
   - The hooks copy `:225-258`: input pumped in the progress hook,
     Back / Cancel / home gesture set `cancelDownload`, and repaints throttled
     at 5 % or 5 s.
4. **Outcome mapping.**

   | `publication::Result` | Behaviour |
   |---|---|
   | `Ok`, `AlreadyOnCard` | `finish()`, returning to the launcher, which re-resolves (C2/C3). Both paths `record` `nwt` (`PublicationDownloader.cpp:184,239`). |
   | `Cancelled` | `finish()`, or `onGoHome()` if the home gesture caused it (`MeetingDownloadActivity.cpp:293-299`). No failure screen. |
   | `ChecksumMismatch` | Failed, message `STR_CHECKSUM_MISMATCH` (via `publication::failureMessage`, `PublicationDownloader.cpp:245-260`). |
   | `DownloadFailed`, `OutOfMemory`, `NoMediaLink` | Failed, message `STR_BIBLE_DOWNLOAD_FAILED_HINT`. |
   | Wi-Fi picker cancelled or failed | Failed, message `STR_NO_WIFI_CONNECTION`. |

   - **D3 — `NoMediaLink` is reported as a connection failure, not "Not
     published in this language".** `download` returns `NoMediaLink` when the
     resolve fetch itself fails (`PublicationDownloader.cpp:156-159`,
     `!fetched || !media->found()`), so on a connected-but-offline network the
     stock message would be false. Both languages the setting offers publish
     `nwt` (measured, D1). The only honest reading for this screen is
     therefore "could not reach jw.org".
   - **D4 — A cancelled Wi-Fi picker is a failure with retry, not a silent
     exit.** This departs from `MeetingDownloadActivity.cpp:74-78`. The issue
     requires "a clear failure and a retry option, not a hang" when Wi-Fi is
     unavailable. The picker cannot tell "no network in range" from "user
     backed out", so both land on the same screen, and Back from there still
     exits.
5. **Failed.** The same dialog shape: title `STR_DOWNLOAD_FAILED`, the message
   from the table, primary `STR_RETRY` (exists, `english.yaml:224`), and
   secondary `STR_CANCEL`, which finishes the screen. Back also finishes it.
   Retry re-enters step 2, so Wi-Fi is re-checked.
   - **D5 — A failure leaves the card as it was.** No code is needed:
     `HttpDownloader::downloadToFile` removes its own file on any non-`OK`
     result (`HttpDownloader.cpp:300-308`), and a checksum mismatch is removed
     at `PublicationDownloader.cpp:218-221`. On return the tile still offers
     the download, because nothing was registered.
6. **Wi-Fi teardown.** When the activity is destroyed, whether finished,
   replaced by the file browser, or sent home, `WifiSession`'s destructor
   applies `WifiSessionPolicy::onExit` (`WifiSessionPolicy.h:15-18`). There is
   no hand-rolled connect or teardown.

- **D6 — One activity, not `ConfirmationActivity` plus a download screen.**
  `ConfirmationActivity` offers only Cancel/Confirm (`ConfirmationActivity.cpp:29`)
  and truncates its body to one line (`:19-22`). The confirmation needs a
  third outcome (D2) and a two-line message. `BibleSearchActivity` already
  establishes the confirm-then-run dialog inside the working activity
  (`:710-717`).

## Error handling

| Failure | Handling |
|---|---|
| Registry unreadable or newer on open | `record` refuses and logs (`PubKeyRegistry.cpp:25-33`); the reader continues; the next open retries. Nothing is shown to the user, because this is a recognition cache, not user data. |
| Registry over budget | `record` refuses and logs (`:41-44`). Same handling. |
| Recents hit no longer on the card | Skipped (A2); the lookup falls through to "none". |
| Download failures | Table D.4; retry and cancel always available. |
| OOM building `BibleDownloadActivity` | `std::make_unique` is used at the existing launcher call sites (`:558,563`). The new site uses `makeUniqueNoThrow` and logs `LOG_ERR` on null (CLAUDE.md, "Always use makeUniqueNoThrow"). The tile then does nothing, as a failed `goToReader` does (`ActivityManager.cpp:215-219`). |

## Resource notes

- **No new persistent allocation.**
  - `BibleDownloadActivity`'s strings are a few `std::string` members, the
    same set as `MeetingDownloadActivity.h:58-69`, freed with the activity.
  - The download buffers are `publication::download`'s own.
  - `resolveBible` and `registerBibleIfUnknown` are header templates on
    stack lambdas: no heap and no `std::function`.
- **Flash.** The new activity is roughly the size of the confirm, progress and
  failure parts of `MeetingDownloadActivity` minus the week scrape. The
  `pio run` size delta goes in the PR.

## Testing strategy

TDD. Each test below is written first, run, and seen to fail.

**Host: `test/launcher_bible/LauncherBibleTest.cpp` (extended, no CMake change)**

1. `resolveBible` tries Registry, then CardScan, then Recents; asserted from
   the sequence a recording fake lambda sees.
2. A Registry hit stops the walk: CardScan and Recents are never called, and
   the registry path is returned.
3. A CardScan hit stops the walk before Recents.
4. When all three miss, `resolveBible` returns `nullopt` after calling all
   three. This is the "download offer only after all three steps miss"
   acceptance criterion: `openBible` offers the download exactly when
   `biblePath` is empty.
5. `looksLikeBibleInRecents`:
   - true for `/x/nwt_S.epub`, `/Libros/Biblia.epub` titled "La Biblia.
     Traducción del Nuevo Mundo", and a title with "New World";
   - false for `/Libros/Biblia.epub` titled "Biblia";
   - case-sensitive (`"new world"` → false), per A1.
6. `registerBibleIfUnknown`:
   - not a Bible → neither callable is invoked;
   - a Bible, unregistered → one record call with that path;
   - already registered → no record call;
   - opened twice against a fake registry that remembers the write → exactly
     one record in total (idempotency).
   - `record` returning false → the helper returns false and does not retry.

Command: build and run the host suite as `test/README:7-12` describes (`ctest --test-dir build/test`),
filtered to `LauncherBible*`, then the full suite.

**Firmware:** `pio run` for `x4pro` through the batch's `pio-locked.sh`, then
`./bin/clang-format-fix` over the whole tree after `git add`.

**Device (for the human tester, listed in the PR):**

1. Sideload `Biblia.epub` into a subfolder and open it once on the old build.
   After updating, the tile shows it (recents fallback).
2. Open it once on the new build, delete `/.crosspoint/recent.json`, and
   return home. The tile still shows it (registry). Serial shows
   `Bible: … (Registry)`.
3. With a registered Bible, open a non-Bible book titled "New World…". The

4. Remove all Bibles. The tile reads "Not on the card · tap to download". Tap,

5. With Wi-Fi off or out of range, tap and confirm. The screen says there is
   no connection and offers Retry; Cancel returns to the launcher.
6. Choose a file from the confirm dialog opens the file browser.
7. Cancel mid-download. The card has no partial file, and the tile still
   offers the download.
