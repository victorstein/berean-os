accepted and applied inline:

- **MINOR 1** — A-7 and data-flow step 3 now name the mechanism that actually runs: `nextPageNumber` on a cache hit,

## Problem

Open the reader menu sheet, tap **Go to**, back out: the sheet reopens on a blank screen. Every menu sub-screen's cancel
handler calls `openReaderMenu(false)` straight away (`EpubReaderActivity.cpp:695, 741, 755, 782, 869, 886`). The
reader never renders between the pop and the push — the handler's pending push suppresses the post-pop
`requestUpdate()` (`ActivityManager.cpp:115-133`) — so the framebuffer still holds the sub-screen. `pageOnScreen ==
false` sends `EpubReaderMenuActivity::decideMode` to `Cleared` ("not-on-page", `EpubReaderMenuActivity.cpp:255-256`),
which clears the screen (`:524`). On Go to and Search the section is also released first (`:856, :882`), so there is no
page in memory either (R §2.3).

## Goal

The owner's decision on #239: **the page stays visible behind the sheet after returning from any sub-screen.** When a
sub-screen opened from the sheet is cancelled, the reader draws the page it was on, then opens the sheet over it in
`OverPage` mode, exactly as when the sheet is opened from the page.

Acceptance (from the issue):

1. After Go to, Search, Footnotes, Bookmarks or Highlights followed by back, the sheet shows the current page above it
   — the same page, not a neighbour.
2. The Recent chips and "Tags here (n)" are correct after the round trip.
3. PSRAM and internal heap return to baseline after the sheet closes, and it is logged.
4. Device: Eclesiastés 4 → menu → Go to → back → back shows page text above the sheet.

## Non-goals

- **No snapshot kept across activities.** The reader does not own or retain the menu's page snapshot while a sub-screen
  is up. That is #200's rejected option a (`2026-09-30-issue-200-design.md:540-542`) and the issue rejects it again.
  The snapshot stays owned by `EpubReaderMenuActivity` for its own lifetime (`EpubReaderMenuActivity.cpp:174-178`).
- **Night mode and rotation stay cleared.** `decideMode` keeps its `night` and `rotated` reasons (`:252-260`). A
  snapshot OOM (`:272-277`) stays cleared too.
- **Confirmed (non-cancel) results are unchanged.** A picked chapter, verse, footnote, bookmark, highlight or percent
  still navigates and returns to the page, with no sheet.
- **Entry intents are unchanged.** `onBookLoaded` opens pickers with `CancelTo::Page` (`EpubReaderActivity.cpp:962-968`);
  cancelling them keeps returning to the page.
- **`Tag` (`HIGHLIGHT_PASSAGE`) is unchanged.** Its handler only `requestUpdate()`s (`:351`) and it is not in the
  issue's list; it already returns to the page.
- **No change to `EpubReaderMenuActivity`.** The sheet already does the right thing when told `pageOnScreen == true`.

## Assumptions (each one is a decision the review can attack)

- **A-1 — Re-render, then open over the page.** On a cancel that returns to the sheet, the reader renders its page
  synchronously with `requestUpdateAndWait()` and then calls `openReaderMenu(true)` if that render actually drew a
  page (A-4). This is the issue's recommended approach. It is legal in a result handler: `ActivityManager` has already
  made the reader `currentActivity` (`ActivityManager.cpp:116`) and released `RenderLock` (`:125-126`), so the three
  asserts in `requestUpdateAndWait` (`:313-320`) pass and the render task renders the **reader**. Precedent for the
  call from a loop-task callback with no lock held: `HighlightsActivity.cpp:441`, `PassageSelectActivity.cpp:310`.
- **A-2 — One helper, `reopenReaderMenu()`, replaces every cancel-path `openReaderMenu(false)`.** The six sites are
  Bookmarks (`progressChangeResultHandler`, `:695`), Footnotes (`:741`), Text settings (`:755`), Go to % (`:782`),
  Go to (`:869`) and Search (`:886`). After this change no sub-screen handler calls `openReaderMenu(false)` directly;
  only `reopenReaderMenu` chooses the flag (A-4, A-5). The parameter stays, and `EpubReaderMenuActivity`'s contract is
  unchanged.
- **A-3 — Highlights and Tags here reopen the sheet on cancel when opened from the sheet.** Today their handler returns
  on cancel (`EpubReaderActivity.cpp:365`), so back lands on the page with no sheet (R §2.2). The acceptance line names
  Highlights explicitly and says "the sheet shows the current page above it", so this is read as a required behaviour
  change, not as already met. `openHighlights` gains a `CancelTo` parameter, mirroring `openChapterPicker` /
  `openBibleSearch`: `CancelTo::Menu` from the `HIGHLIGHTS` and `TAGS_HERE` menu actions (`:794, :798`),
  `CancelTo::Page` from the entry intent (`:968`). A cancel with `CancelTo::Menu` calls `reopenReaderMenu()`.
- **A-4 — "Did the render draw a page" is a per-render flag, not `pageShown`.** `pageShown` is sticky for the session
  (`EpubReaderActivity.h:51-55`, set at `:1392`) and would say "yes" after a render that ended on the index-failed
  popup (`showBuildError`, `:1119-1123`), the empty-chapter or out-of-bounds message (`:1343-1358`), or a page-load
  failure (`:1363-1382`). A new member `bool pageRendered` is written on the render task and read by the loop task
  under `RenderLock`, like `chapterPassageCount` (`EpubReaderActivity.h:65-68`):
  - `reopenReaderMenu()` sets it `false` under `RenderLock` before `requestUpdateAndWait()`;
  - `renderBook` sets it `true` right after `renderContents` returns, beside `pageShown = true` (`:1392`);
  - `reopenReaderMenu()` reads it under `RenderLock` after the wait and passes it as `pageOnScreen`.
  Every non-page outcome — the failure paths above, and `ReaderActivity::render`'s end-of-book branch that never calls
  `renderBook` (`ReaderActivity.cpp:168-185`) — leaves it `false`, so the sheet falls back to `Cleared` as today.
- **A-5 — Night mode skips the re-render.** With `SETTINGS.screenInverted != 0` the sheet is `Cleared` regardless
  (`EpubReaderMenuActivity.cpp:257-260`), so a re-render would cost a page refresh the sheet immediately clears.
  `reopenReaderMenu()` calls `openReaderMenu(false)` directly in that case: today's behaviour, one HALF refresh.
- **A-6 — Text settings re-renders with the new settings.** Its handler releases the section on every result
  (`:754`), because the render spec may have changed. The re-render therefore reflows the chapter with the new
  settings before the sheet opens, which can show the "Indexing" popup and take a build (`:1223-1226`, R §2.5). The
  owner's rule is "any sub-screen", and seeing the reflowed page behind the sheet is the point of changing a text
  setting, so the cost is accepted. Position is kept by the existing rebuild (A-7).
  `requestUpdateAndWait` blocks the loop task until that page is drawn (`ActivityManager.cpp:322-323`), including the
  synchronous `buildSomeMore` loop (`EpubReaderActivity.cpp:1244-1255`), so input and the Home gesture
  (`ActivityManager.cpp:73-89`) are not polled during the "Indexing" build. Today the same build runs after the sheet
  closes, with the loop live. This is accepted: the sheet cannot usefully open over a page that does not exist yet. Go
  to and Search on a partial cached section block the same way, more briefly (`:1210-1255`).
- **A-7 — "Same page, not a neighbour" rests on the existing rebuild.** `releaseSectionKeepingPosition` saves both
  `nextPageNumber` and `cachedVisibleTextOffset` (`:258-267`). Which one restores the page depends on the section
  cache:
  - **cache hit** (Go to, Search, and Text settings with no change): `renderBook` resets `cachedVisibleTextOffset`
    when the cache loads (`:1167-1171`), before `offsetJump` is computed (`:1176-1179`), so the page comes from
    `nextPageNumber` (`:1268`). Same pagination, same page.
  - **cache miss** (Text settings with a changed render spec): `offsetJump = cachedVisibleTextOffset` (`:1178`),
    resolved by `getPageForVisibleTextOffset` (`:1272-1276`) against the new pagination.
  On the three paths that do not release the section (Footnotes, Bookmarks, Go to %), the live section's
  `currentPage` is re-rendered unchanged. No new position logic is added.
- **A-8 — Recent chips and Tags here need no change.** `openReaderMenu` computes both after the re-render
  (`:280-287`): `chapterPassageCount` is recomputed by `renderContents` for the same spine (`:1341, :1580`), and
  `captureLeftPlace` reads `currentPageVisibleOffset` of the re-rendered page (`:1476-1479`). Without a re-render
  (A-4 false, A-5), both already work from cached state (R §2.4).
- **A-9 — Two refreshes on the reopen path are accepted.** The page render displays itself (`:1559, :1608`), then the
  sheet paints FAST over just its region (`EpubReaderMenuActivity.cpp:533-535`). Today's cleared path is one HALF
  refresh. The owner chose visibility over one refresh.
- **A-10 — A toast drawn by the re-render can end up in the snapshot.** `ReaderActivity::render` calls
  `PostedMessage::drawNext` after `renderBook` (`ReaderActivity.cpp:187-188`). This is the same exposure the
  from-the-page open already has, so it is not treated as new.
- **A-11 — The existing heap log is the acceptance's "Log it".** `EpubReaderMenuActivity::logHeap` already logs
  internal and PSRAM free at `before`, `open` and `closed` (`EpubReaderMenuActivity.cpp:207-211, 251, 281, 176`). The
  reopen adds one `LOG_DBG("ERS", ...)` line naming the outcome (`over page` / `cleared: night` / `cleared: no page`),
  so a device log shows which branch each round trip took.

## Architecture

All changes are in `src/activities/reader/EpubReaderActivity.{h,cpp}`. No new file, no new allocation, no change to
the sheet, the layout, `ActivityManager`, or any store.

### New member and helper (`EpubReaderActivity.h`)

```cpp
// Written by renderBook on the render task, read by reopenReaderMenu under RenderLock: whether the
// last render drew a reading page, so the sheet may snapshot it.
bool pageRendered = false;

// Cancel from a sub-screen the sheet opened: redraw the page, then reopen the sheet over it.
void reopenReaderMenu();

void openHighlights(CancelTo cancelTo, std::optional<uint16_t> spineFilter = std::nullopt);
```

`CancelTo` is declared at `EpubReaderActivity.h:157`, after `openHighlights` (`:144`); the declaration moves below it.

### Comments that this change makes wrong

- `EpubReaderActivity.h:136-137` says `pageOnScreen` is "False from a sub-screen's result handler". Rewrite: it is
  whether the framebuffer holds the reading page; `reopenReaderMenu` decides it after its re-render.
- `EpubReaderActivity.cpp:355-362` says `progressChangeResultHandler`'s menu reopen on cancel is wrong for
  `openHighlights`. Keep the point about `bookmarks.load`, and say instead that the cancel is routed by `CancelTo`.

### `reopenReaderMenu()` (`EpubReaderActivity.cpp`, beside `openReaderMenu`)

```cpp
void EpubReaderActivity::reopenReaderMenu() {
  if (SETTINGS.screenInverted != 0) {
    LOG_DBG("ERS", "Reopening menu cleared: night");
    openReaderMenu(false);
    return;
  }
  {
    RenderLock lock;
    pageRendered = false;
  }
  requestUpdateAndWait();
  bool onPage;
  {
    RenderLock lock;
    onPage = pageRendered;
  }
  LOG_DBG("ERS", "Reopening menu %s", onPage ? "over page" : "cleared: no page");
  openReaderMenu(onPage);
}
```

## Data and control flow

Go to → back, after the change:

1. Sheet → `SELECT_CHAPTER` → `openChapterPicker(CancelTo::Menu)` releases the section (`:856`) and pushes the picker.
   Unchanged.
2. Cancel: `ActivityManager` pops the picker, sets the reader current, unlocks, calls the handler
   (`ActivityManager.cpp:115-127`).
3. Handler → `reopenReaderMenu()` → `requestUpdateAndWait()`. The render task runs `ReaderActivity::render` →
   `renderBook` (`ReaderActivity.cpp:187`), which rebuilds the section at the saved page (A-7), renders and
   displays the page, and sets `pageRendered = true`.
4. `openReaderMenu(true)` computes Tags here and Recent chips from the fresh page (A-8) and pushes the sheet. The
   post-handler `requestUpdate()` is skipped because a push is pending (`ActivityManager.cpp:131`), so the reader does
   not render twice.
5. The sheet's first render: `decideMode` finds no reason, snapshots the page region, logs
   `sheet mode: over-page (page saved)`, paints the sheet FAST over the page.

Footnotes, Bookmarks, Go to %: identical from step 2, except the section is live and step 3 re-renders its current page
without a rebuild. Bookmarks keeps its `bookmarks.load(...)` before the reopen (`:692`). Highlights / Tags here: A-3.

## Error handling

- **Render did not draw a page** (build failure, empty chapter, out of bounds, page-load retry, end of book):
  `pageRendered` stays `false` (A-4), the sheet opens `Cleared` as today. The build-error popup already logs via
  `LOG_ERR` (`:1161, :1196, :1236, :1250, :1315, :1325`). One difference from today: `renderBook` zeroes
  `chapterPassageCount` (`:1341`) before the empty-chapter, out-of-bounds and page-load-failure returns
  (`:1343-1382`), so on those failures "Tags here" may read 0 until the next successful page render. Accepted as a
  failure-only edge; no code is added for it.
- **Snapshot OOM:** unchanged — `decideMode` logs and falls back (`EpubReaderMenuActivity.cpp:272-277`).
- **Heap:** no new allocation in this change. The re-render's section load is the same allocation any page render makes
  and is freed on the next release/reset as today. The sheet's snapshot remains the only extra buffer, alive exactly
  from the sheet's first render to its `onExit`.
- **Deadlock:** `requestUpdateAndWait` asserts rather than deadlocks if called with the lock held or from the render
  task (`ActivityManager.cpp:313-320`). The only callers are result handlers on the loop task, lock released (A-1).

## Testing strategy

- **No host test for the sequencing.** Activities are not built by `test/CMakeLists.txt`; the only sheet suite is
  geometry (`test/ui_layout/ReaderMenuSheetLayoutTest.cpp`) (R §5). The decision in this change is a single boolean
  produced by a render, not a pure function worth extracting; inventing a seam here would be a new pattern. This is
  **A-12**, and it is the assumption most open to attack: the TDD evidence for this change is the build plus the device
  log, not a red/green host test.
- **Build:** `pio run` (env `x4pro`) and `./bin/clang-format-fix` over the whole tree.
- **Device (human):** with a dev build and the serial log:
  1. Eclesiastés 4 → centre tap → Go to → back → back. Page text visible above the sheet. Log shows
     `Reopening menu over page` then `sheet mode: over-page (page saved)`, and the page is the one you left.
  2. Repeat for Search, Footnotes (on a page with footnotes), Bookmarks, Go to %, Text settings (change the font size;
     the reflowed page shows behind the sheet), Highlights and Tags here.
  3. Recent chips and "Tags here (n)" match what they showed before the round trip.
  4. Close the sheet; `heap closed` internal and PSRAM match `heap before` within noise, across three round trips.
  5. Night mode on: Go to → back shows the cleared sheet, log `Reopening menu cleared: night`, no extra page flash.
  6. Highlights opened from the home screen's entry intent, then back: returns to the page, no sheet (non-goal).
  7. Text settings → change the font size on a long chapter → back. The device does not hang; the "Indexing" popup
     shows, and the sheet opens over the reflowed page once the build finishes (A-6).
