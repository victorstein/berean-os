# Issue #105 — strip the EPUB optimiser and jszip from the File Transfer page

Research: `docs/superpowers/research/2026-09-27-issue-105-research.md`. Line numbers are from
`e41880e3`. Modelled on `0d9285eb` ("refactor: drop the OPDS browser"), which removed an inherited
CrossPoint subsystem's server routes, its web-UI section, and its docs in one change, and verified
the result by orphan grep.

## Problem

`GET /files` serves `FilesPage.html`, which inherits CrossPoint's in-browser EPUB optimiser: image
re-encoding and splitting, an image picker, SVG and OPF fix-ups, and a conversion log. That code
needs jszip, which the page loads from its own route (`FilesPage.html:7`;
`CrossPointWebServer.cpp:142`, `:367-371`). The baseline build's `build_html.py` output measures
both:

| Asset | Source | Gzipped, in flash |
|---|---|---|
| `FilesPageHtml` | 217,405 chars | 49,528 B |
| `jszip_minJs` | 97,630 B | 28,379 B |

File Transfer on this device only needs list, upload, download, rename and delete
(`docs/webserver-endpoints.md`). The optimiser also targets device profiles `X4` and `X3`
(`FilesPage.html:3288-3291`) that are not this product's screen story, and it rewrites book files
in ways that break hash-based sync (its own warning, `:1746-1749`).

## Goal

1. `FilesPage.html` contains no optimiser code, markup or CSS, and does not load jszip.
2. `jszip.min.js`, its route and its handler are gone from the firmware.
3. Every kept page function works as it does today. That covers list, breadcrumbs, download, image
   preview, upload (picker, drag-and-drop, multi-file, WebSocket with HTTP fallback, name-collision
   suffixing, cancel, the failed-upload banner and retry), new folder, rename, move, and single or
   multi delete.
4. The PR reports the flash difference, measured before and after with the same env.

## Non-goals

- No server-side upload change. `POST /upload`, the WebSocket upload protocol, protected-path
  handling and `/api/status` stay byte-for-byte (`CrossPointWebServer.cpp:150`, `:645-835`,
  `:1471-1539`, `:407-409`).
- No rebrand of the page. The "CrossPoint Reader" heading and title strings (`FilesPage.html:1504`,
  `:1849`) belong to a separate change.
- No restyling or restructuring of kept UI beyond removing what only the optimiser used.
- No change to the other pages, to `XTCache` protection, or to WebDAV.
- No new build-time HTML/JS validation in CI (see A8).
- No "XTC" work. The issue's "xtc appears 42 times" counts `textContent` matched case-insensitively,
  and the page has no XTC code (research, section 2).

## Assumptions (each is a reviewable decision)

- **A1 — "Rename from Book Metadata" is removed with jszip.** The toggle (`FilesPage.html:1582-1593`)
  calls `maybeRenameEbookFile` → `getMetadataFilenameForEpub` → `JSZip.loadAsync` (`:5584-5591`,
  `:3924`, `:3896-3898`). Stripping jszip, as the issue requires, leaves it nothing to read the OPF
  with. Keeping it would mean shipping a hand-written ZIP central-directory and inflate reader in
  page JS, which is a new mechanism that the issue does not ask for. The feature is off by default
  (`:3325`) and is not in the issue's list of needed operations. Uploads keep the picked filename,
  with collision suffixing (`reserveAvailableUploadFilename`, `:3943`).
- **A2 — The upload modal has no per-type branching.** An EPUB uploads exactly like any other file.
  `validateFile` keeps only the file-input state, `has-files`, and the Upload button's enabled state
  (`:3220-3280`, minus the convert and picker branches).
- **A3 — Upload-settings persistence goes entirely.** `localStorage` key
  `crosspoint.files.uploadSettings.v1` (`:3322`) holds only optimiser settings and the A1 toggle.
  With them gone, "Remember Settings" has nothing to remember. A value already stored in a user's
  browser is left there, because it is never read again and a cleanup call would be code whose only
  job is a key that nothing reads.
- **A4 — `fetchVersion()` and its `/api/status` call are removed from this page.** Their only
  consumers are the log export (`crosspointVersion`) and the device profile (`DETECTED_DEVICE`,
  `:3413-3430`). `/api/status` stays for `HomePage.html:142`.
- **A5 — The jszip route is deleted, not kept as a stub.** A request for `/js/jszip.min.js` then
  falls through to `handleNotFound` (`CrossPointWebServer.cpp:373`). Nothing on the device, and no
  page this firmware serves, requests it after the change.
- **A6 — `src/network/html/js/` is deleted with its only file.** `build_html.py` keeps its generic
  `.js` branch (`:55-62`). Its comment example `(e.g., jszip.min.js)` (`:56`) is reworded so that it
  names no deleted file. The build script's behaviour does not change. A developer's stale
  `jszip_minJs.generated.h` is gitignored and no longer included, so it is inert.
- **A7 — Upload progress is 0-100% per file.** It drops the "conversion is the first 50%" split in
  `onProgress` (`:5608-5615`) and the purple and orange conversion colours (`:5671`, `:5713`). The
  green bar, the red failure colour and all the text formats stay.
- **A8 — Verification is a scripted static check plus a device checklist, not a committed test.**
  This repo has no harness that loads HTML or runs page JS. The host tests are C++ gtest suites
  under `test/`, and CI runs `cmake`/`ctest`, `pio check`, format and build
  (`.github/workflows/ci.yml:95`, `:188-194`). Adding a JS or HTML test stage would invent a
  pattern (net-dev: escalate before inventing). The TDD red/green uses a static checker kept in
  the implementer's scratchpad and run before and after the change. It fails on today's page and
  passes on the stripped one. Its commands and output go in the PR.
- **A9 — CSS removal is decided per selector, not per line range.** Kept rules sit between optimiser
  rules. For example, `.modal.image-preview-mode` and `.image-preview-stage` (`:172-190`) sit
  between `.modal.picker-mode` (`:169`) and `.picker-columns.picker-active` (`:191`). A selector is
  removed only when a grep finds no use of its class or id outside the removed markup and JS.
  `0d9285eb`'s warning about `.opds-server` styling the WiFi editor is the precedent.

## Data and control flow after the change

**Upload**, one or more files, picked or dropped:

1. `validateFile` enables Upload.
2. `uploadFile` calls `fetchExistingUploadNames()` (`GET /api/files?path=`). On failure it alerts and
   aborts, as today (`:5484-5491`).
3. For each file, `reserveAvailableUploadFilename` suffixes a clashing name. Then
   `uploadFileWebSocket` runs (`START:<name>:<size>:<path>`, 4 KB chunks, `DONE` / `ERROR:`). If
   the WebSocket connection fails, the page switches to `uploadFileHTTP` (`POST /upload?path=`) for
   this file and all later ones.
4. On success it moves to the next file. On a network-class error it marks the rest as failed and
   shows the banner. When all files succeed it reloads the page after 1 s (`:5534-5537`; the
   2 s batch-log branch at `:5529-5533` is removed).
5. Cancel closes the socket or aborts the XHR. The async handlers see `operationCancelled` and call
   `restoreAfterCancel`.

**Dev firmware side-load.** This path does not read the page. It is `curl -H "Expect:" -F
file=@firmware.bin "http://<ip>/upload?path=/"` → *Settings → SD firmware update*
(`SdFirmwareUpdateActivity.cpp:25-26`). A `.bin` uploaded through the page never reached the
optimiser even before this change, because `needsConversion` required `.epub` (`:5577-5578`).
After it, the `.bin` still takes step 3 above.

**Page load.** `hydrate` builds the table from `/api/files` and wires the overlay-close handlers.
It makes no `/api/status` request (A4) and no `/js/jszip.min.js` request.

## Error handling

The page adds no new failure modes, because removal only deletes paths. The kept paths, unchanged:

- A failed existing-names fetch: an alert, and the upload aborts (`:5484-5491`).
- A WebSocket connect failure falls back to HTTP (`:5736-5747`). A WebSocket `ERROR:` message or an
  HTTP non-200 is recorded as a failed file (`:5395-5399`, `:5445-5452`).
- A network-class error fails the remaining files and shows the retry banner (`:5641-5664`).
- Cancel mid-transfer: `restoreAfterCancel` (`:2145`).

The main risk is a partial strip that leaves a live reference to a removed element or function. A
`getElementById(...)` that returns null, or a call to an undefined function, throws on the first
upload or on closing the modal. No build step catches either (research, section 6). The static
check in the testing strategy exists for this.

## Testing strategy

### Red/green: the static page check (A8)

A scratchpad script, not committed, runs over `src/network/html/FilesPage.html` and asserts:

1. No `jszip` / `JSZip` string and no `<script src=`.
2. No removed identifier appears: `convertEpubFile`, `imageStates`, `renameFromMetadataToggle`,
   `convertBeforeUpload`, `startConversionBtn`, `log-section`, `picker-mode`,
   `uploadSettings`, `fetchVersion`, `DEVICE_PROFILES`.
3. Every `getElementById('<id>')` / `querySelector('#<id>')` names an `id` present in the markup.
4. Every inline handler (`onclick="fn(`, `onchange="fn(`, `oninput="…"`) calls a function defined in
   the script.
5. Every class that the markup or JS uses (`class="…"`, `classList.*('…')`, `.closest('.…')`) has a
   rule in the `<style>` block, or is on a short allow-list of JS-only hooks such as
   `image-preview-link`. This catches A9 over-deletion.
6. `node --check` passes on the extracted `<script>` body (node v24.16.0 is installed).

Run it first on today's page: checks 1 and 2 must fail. Run it after the strip: all six must pass.

### Build and flash

- `pio-locked.sh run -e x4pro`. It must pass with no new warnings, and `build_html.py` must no
  longer print `jszip_minJs`.
- Flash: the size of `.pio/build/x4pro/firmware.bin`, and `build_html.py`'s `FilesPage` compressed
  size, before (baseline in the research note) and after, in the PR.
- `./bin/clang-format-fix` over the whole tree. Only the `.h`/`.cpp` edits are in scope for it.
- Orphan grep, as in `0d9285eb`:
  `grep -rn "jszip\|handleJszip\|JSZip" src lib docs scripts test` returns nothing.

### Host tests

No C++ unit changes behaviour, so the existing suite should stay green. `cmake --build build/test`
and `ctest` are run to confirm that.

### Device checklist, for the human (in the PR)

On a dev build, over WiFi, from a desktop browser:

- [ ] `/files` loads and lists; breadcrumbs navigate; an image previews; a file downloads.
- [ ] Upload a single `.epub` via the picker, then drag-and-drop several files. Both finish, keep
      their names, and a name clash gets ` (2)`.
- [ ] Cancel mid-upload, then re-upload.
- [ ] Rename, move, new folder, delete one, and delete-selected.
- [ ] Dev firmware side-load: `curl -H "Expect:" -F file=@firmware.bin "http://<ip>/upload?path=/"`,
      then *Settings → SD firmware update* flashes it.
- [ ] Browser devtools console shows no errors, and the network tab shows no request for
      `/js/jszip.min.js` or `/api/status` from `/files`.
