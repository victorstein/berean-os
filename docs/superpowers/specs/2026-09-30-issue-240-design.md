# Issue #240 — design: tag chip grid and bigger chips

Research: `docs/superpowers/research/2026-09-30-issue-240-research.md`. Surface: `ui`. Tier:
`standard`.

## Problem

In Highlights, the tag chip row wraps to two lines and then offers **…**
(`HighlightsActivity.cpp:729`, `TagChipRow.h:84`, `:131-153`). The **…** opens
`TagFilterActivity` (`HighlightsActivity.cpp:210-212`), which is a paged list with no counts. It
shows All, Unlabelled, then every active tag (`TagFilterActivity.cpp:43-66`). With 20+ tags the
owner has to page through rows to find one. The chips are also cramped. Horizontal padding is
`spaceMd` (8 px), vertical padding is `spaceSm`, and the chip height is the small font's line
height plus `2 * spaceSm` (`HighlightsActivity.cpp:716-718`). The button is built with
`minTouchSize = 0` (`:774`), so nothing guarantees the 44 px tap height the theme asks for
(`FreeInkUICore.h:638`, `FreeInkUI.cpp:117`).

## Goal

1. The **…** screen becomes a grid of chips with counts, in the header row's style, wrapped across
   the full width. It pages only when the chips do not fit one screen.
2. Every chip, in the header row and in the grid, is at least `minTouchSize` tall and has more
   padding. All sizes come from theme tokens.
3. The selected chip stays inverted. Counts follow #226: they are chapter-scoped in the "Tags here"
   view.
4. The filtering result, retire-by-long-press, Back/Home cancel and the rebuild on return all
   behave as they do today.

## Non-goals

- No change to `TagSelectionResult` (`ActivityResult.h:86`), `StudyStore`, the palette, or any
  on-disk format.
- No change to `TagPickerActivity` or to how Highlights filters its rows (`passageMatches`,
  `computeVisibleIndices`).
- No multi-select, no tag search, no sorting other than the palette's active order.
- No change to the header row's two-line limit or its ellipsis behaviour, apart from chip size.
- `test/CMakeLists.txt`, the i18n YAML files and `src/main.cpp` are not edited.

## Modelled on

- **`BibleNavigationActivity`** (`BibleNavigationActivity.h:33`) is a `UiListActivity` that draws
  a paged grid instead of a list. It consumes vertical swipes as page turns in `handleCustomInput`
  (`BibleNavigationActivity.cpp:417-424`), turns pages under one `RenderLock` in `moveGridPage`
  (`BibleNavigationActivity.cpp:372`), overrides `navigateButtons` (`:427-439`), and puts a `"%d/%d"` page indicator in a
  sub-header drawn from `drawFooter` (`:697-715`). The grid screen follows this structure.
- **`NumberGridLayout.h` / `BookGridLayout.h`**: pure, host-tested paging arithmetic, with a
  per-page cell cap sized against the interaction table (`NumberGridLayout.h:15-18`) and page
  arrays kept small for the render stack (`BookGridLayout.h:25-30`). The grid paging follows the
  same rules.
- **`TagChips::layout` and `HighlightsActivity::buildChipRow`**
  (`TagChipRow.h:107-182`, `HighlightsActivity.cpp:708-790`): the greedy wrap, the tiled hit
  padding, and the inverted pill style. The grid reuses these rather than copying them.

## Assumptions (each one is a decision the review should attack)

- **A1 — the grid shows the header row's candidate set, uncapped.** That set is All, then every
  active tag with a non-zero count in scope, then Unlabelled when it is non-zero. A zero-count tag,
  or a zero Unlabelled, is kept only while it is the active filter
  (`HighlightsActivity.cpp:147-158`). The grid drops the header's `MAX_CHIPS + 1` cap
  (`:139`, `:153`). *Why:* the issue asks for chips "with its count" in the header row's style, and
  the owner's example lists only non-zero chips. A global palette in the chapter-scoped view would
  otherwise fill the grid with `name 0` chips that filter to an empty list. *What changes:* today's
  list also offers zero-count tags and a zero Unlabelled (`TagFilterActivity.cpp:43-58`). Those
  choices produce an empty list, so filtering on them has no use. A tag used in no passage in scope
  can still be retired from `TagPickerActivity` (`TagPickerActivity.cpp:253-271`). *Alternative
  rejected:* show every active tag, with zeros. That keeps the old list's reach but gives the
  owner a screen of zeros.
- **A2 — Highlights passes the scope in, and the grid counts for itself.** `TagFilterActivity`
  gets the count scope (`std::nullopt` = every passage, otherwise Highlights'
  `computeVisibleIndices(std::nullopt)`, as at `HighlightsActivity.cpp:134-136`) and the current
  filter id. It builds its own chips with the same builder the header uses. *Why:* a retirement
  on this screen changes counts (a retired tag's passages can become Unlabelled,
  `StudyStore.h:112-116`). The screen has to recount without going back to Highlights. Passage
  indices stay valid across a retirement because no passage is removed (`StudyStore.h:112-116`).
  The scope is computed by Highlights before the push, with no `RenderLock` held, as
  `computeVisibleIndices` requires (`HighlightsActivity.h:127-133`).
- **A3 — one chip builder for both screens.** `rebuildChips`' body
  (`HighlightsActivity.cpp:129-159`) moves into a shared function. The pure half ("which chips,
  in what order") goes in `TagChipRow.h` and is host-tested. The half that formats labels from
  `STUDY.tagName` and `tr()` goes in a small non-host helper that both activities call. The
  header calls it with a cap of `MAX_CHIPS + 1`, and the grid calls it with no cap.
- **A4 — paging, not free scrolling.** When the chips do not fit the body, the grid splits into
  pages at line boundaries. A vertical swipe or a held button turns the page; a released
  Next/Previous button steps the selected chip by one and pulls its page into view. A `"x/y"`
  indicator shows only when there is more than one page. *Why:* this is the paged-grid pattern the
  repo already has (`BibleNavigationActivity.cpp:405-439`, `:697-715`), and on e-ink a page turn is
  one refresh.
- **A5 — the per-page chip cap is 64** (`GRID_MAX_CHIPS`). `UiAppHost` holds 96 interactions
  (`UiAppHost.h:35`). The grid screen also registers the `OptionPopup` buttons while a retire
  confirmation is open, so 64 leaves room for them with margin. A page also ends when its lines
  fill the body height. With the owner's tag count, the body's line count, not the cap, should
  decide where pages break. The host test pins that 24 realistic chips fit one page.
- **A6 — chip size, same for header and grid.** Vertical padding becomes `spaceMd`, horizontal
  padding becomes `spaceLg`, and `chipHeight = max(lineHeight(smallText) + 2 * spaceMd,
  theme.minTouchSize)`. The chip width is at least `chipHeight`, as today (`:722`). The gap
  between chips stays `spaceSm`. `props.minTouchSize` stays 0: the chip itself now meets the
  minimum, and growing each hit rect would overlap the next line (`:772-774`). *Consequence:* the
  header band gets taller, so fewer passage rows fit below it. That is the issue's explicit
  trade.
- **A7 — selection visuals.** In the grid, the chip for the current filter is inverted, and
  selected-state text is bold, as in the header (`:739-768`). All chips are measured bold, so the
  selection never reflows the grid (`:712-714`). Button focus draws a 2 px outline around
  `nav.selected`'s chip, and only after a button press moved it. That mirrors the header's
  `buttonFocus_` (`HighlightsActivity.h:205-207`, `HighlightsActivity.cpp:784-790`). On entry,
  `nav.selected` is the active filter's chip, and the first page shown is the one holding it.
- **A8 — no new user-facing strings.** The header title stays `STR_FILTER_BY_TAG`
  (`TagFilterActivity.cpp:20`), and the chip labels reuse `STR_TAG_FILTER_ALL` and
  `STR_TAG_UNLABELLED` (`HighlightsActivity.cpp:147`, `:157`). The page indicator is numeric.
- **A9 — the grid body keeps `TagFilterActivity`'s existing margins.** The body is the content
  margin set at `TagFilterActivity.cpp:28-35`, minus a sub-header strip when there is more than one
  page. The line width is `body.width - 2 * listInset`, as in the header
  (`HighlightsActivity.cpp:727-728`).

## Architecture

### Pure layer — `src/activities/reader/TagChipRow.h` (host-tested)

Everything added here stays free of FreeInkUI, Arduino and GfxRenderer (`TagChipRow.h:12-13`).

- `struct Candidate { Kind kind; uint16_t slot; }` and
  `void candidates(const Counts&, const std::vector<study::TagId>& activeIds,
  std::optional<study::TagId> filter, size_t cap, std::vector<Candidate>& out)`. This is A1's
  rule, moved out of `HighlightsActivity.cpp:147-158`. `slot` indexes `activeIds` and
  `counts.perTag`, and is unused for All and Unlabelled.
- `inline int chipHeight(int textLineHeight, int padY, int minTouch)`: A6's formula.
- Hit padding generalised to work over any placement array:
  `hitPadding(const Placed* placed, int placedCount, int lines, int index, int gap)`. The
  existing `hitPadding(const Layout&, ...)` becomes a one-line wrapper, so the header's call site
  and its tests do not change.
- Grid paging:
  - `constexpr int GRID_MAX_CHIPS = 64;`
  - `inline int linesPerPage(int bodyHeight, int chipHeight, int gap)`, at least 1.
  - `struct GridPage { Placed placed[GRID_MAX_CHIPS]; int placedCount; int lines; int first; }`.
    It is about 1 KB, so it is always a member, never a stack local (`TagChipRow.h:105-106`).
  - `inline int nextPageStart(const int* widths, int count, int first, int lineWidth, int gap,
    int maxLines)`: the index of the first chip that does not fit a page starting at `first`, or
    `count`. It uses the same greedy wrap as `layout` (`:117-129`), stopping at `maxLines` lines
    or `GRID_MAX_CHIPS` chips. A chip always goes on a page, even alone and clamped to the line
    width (`:118`), so paging always makes progress.
  - `inline void layoutPage(const int* widths, int count, int first, int lineWidth, int gap,
    int maxLines, GridPage& out)`: fills `placed[]` for one page. `chip` is the absolute index.
  - `inline int pageStartOf(const int* widths, int count, int index, ..)` and
    `inline int pageCountOf(...)`. Both walk `nextPageStart` from 0. That is O(n) over at most
    202 chips, on a button press or at build time.

### Non-host layer — new `src/activities/reader/TagChipView.{h,cpp}`

Both activities draw chips with this. It is extracted from `HighlightsActivity.cpp:708-790` and
changes no behaviour except A6.

- `struct ChipEntry` moves here from `HighlightsActivity.h:106-110`, unchanged.
- `void buildChipEntries(const std::optional<std::vector<size_t>>& scope,
  std::optional<study::TagId> filter, size_t cap, std::vector<ChipEntry>& out)`. It counts
  (`TagChips::count`/`countIn`), picks (`TagChips::candidates`), and formats `"%s %u"` labels
  from `STUDY.tagName` and `tr()`. The caller must hold no `RenderLock` while it runs, and must
  swap the result into its member under the lock, as `rebuildRowItems` does today
  (`HighlightsActivity.cpp:199-206`).
- `bool chipIsSelected(const ChipEntry&, std::optional<study::TagId> filter)`, moved from
  `:161-171`.
- `struct ChipMetrics { int padX, chipHeight, gap; }` and
  `ChipMetrics chipMetrics(const ThemeTokens&, target)`. This is A6, the one place chip size is
  decided.
- `void measureChips(target, theme, const std::vector<ChipEntry>&, int* widthsOut)`. Every chip
  is measured bold (`:712-722`).
- `void drawChip(frame, theme, rect, label, selected, action, value, inputMask, pad)`. The style
  set is from `:735-749`, and the button props are from `:763-781`.

`HighlightsActivity` keeps its ring, `buttonFocus_` and ellipsis logic. `rebuildChips` and
`buildChipRow` shrink to calls into this helper.

### `TagFilterActivity` becomes the grid

It stays a `final` `UiListActivity` (the same base as `BibleNavigationActivity`). It keeps
`wantsTouchLongPress = true`, the `OptionPopup` retire flow, `onBackButton`, `handleHomeGesture`
and the custom `render` (`TagFilterActivity.cpp:69-160`).

- **Constructor:** `TagFilterActivity(renderer, mappedInput,
  std::optional<std::vector<size_t>> scope, std::optional<study::TagId> filter)`.
- **Members:**
  - `chips_` (`std::vector<ChipEntry>`, rebuilt by `buildChipEntries` with no cap), replacing
    `tags_`/`rowItems_`;
  - `widths_` (`std::vector<int>`, the same size as `chips_`);
  - `page_` (a `GridPage`);
  - `buttonFocus_`.

  The `TagFilterActivity.h:62` comment about the "100" cap is removed along with the member it
  describes.
- **`listCount()`** is `chips_.size()`, and `nav.selected` is a chip index.
- **`buildScreen`** sets the same content margin as today (`:28-35`), measures the chips, computes
  `chipMetrics` and `linesPerPage`, sets `nav.top = pageStartOf(nav.selected)` so the page follows
  the selection, then runs `layoutPage` and one `drawChip` per placed chip. Each chip carries
  `ACTION_ROW`, `value` = chip index, and `InputTouch | InputLongPress`. The base
  `rowActionTrampoline` bounds-checks the value (`UiListActivity.cpp:33-37`) and routes a long
  press to `onRowLongPress` (`:39-46`). `buildScreen` also stores the page count for the
  indicator.
- **`activateIndex(i)`** returns an empty `TagSelectionResult` for `Kind::All`, `{UNLABELLED}` for
  `Kind::Unlabelled`, and `{id}` for `Kind::Tag`, then finishes. This is the same result mapping as
  `TagFilterActivity.cpp:162-177`, keyed on the chip's kind instead of the row number.
- **`onRowLongPress(i)`** does nothing unless the chip is `Kind::Tag`, which keeps the old
  guard's intent (`TagRowMapping.h:25-27`): All and Unlabelled never retire anything. Otherwise
  it captures the chip's **tag id**, not an index, in `pendingRetireId_` and opens the same
  confirmation. `retireTag` calls `STUDY.retireTag(id)`, then rebuilds `chips_` under the render
  lock (counts may have moved) and clamps `nav.selected`. The `saveDisabled` bail
  (`:94-99`) and the save-failure message (`:128`) stay.
- **`handleCustomInput`**: after the popup handling (`:131-141`), a vertical swipe turns the page
  and is consumed, as at `BibleNavigationActivity.cpp:417-424`. A turn moves `nav.selected` to
  the first chip of the new page, which is how `moveGridPage` places the selection.
- **`navigateButtons`**: a release steps `nav.selected` by ±1 and sets `buttonFocus_`; holding the
  button turns the page. Clamped, not wrapped, the same as the number grid's non-wrapping swipe
  (`:423`).
- **`drawFooter`**: button hints as today (`:22-25`), plus a `GUI.drawSubHeader` strip with
  `"page/pages"` when there is more than one page, as at `BibleNavigationActivity.cpp:704-714`.
  The strip's height is taken out of the body in `buildScreen`.
- `FilterRows` (`TagRowMapping.h:28-42`) loses its last user. It is deleted, along with its
  tests in `TagRowsTest.cpp`. `TagRows` stays, because the picker still uses it.

### Highlights call site

`openTagFilter` (`HighlightsActivity.cpp:210-238`) computes the scope before the push, with no
lock held: `spineFilter_ ? computeVisibleIndices(std::nullopt) : nullopt`. It passes the scope and
`filterTagId_`. The result handler does not change: it applies the pick, calls
`dropRetiredFilter`, and always rebuilds.

### Stale comments corrected in passing

`TagChipRow.h:85-87` gives the interaction table as 64, but it is 96 (`UiAppHost.h:35`). The
`MAX_CHIPS` rationale is rewritten against 96, and `MAX_CHIPS` itself keeps its value.

## Data and control flow

```
Highlights: … tap / Confirm on ring 0
  └─ openTagFilter(): scope = spineFilter_ ? computeVisibleIndices(nullopt) : nullopt   (no lock)
       └─ push TagFilterActivity(scope, filterTagId_)
            onEnter → buildChipEntries(scope, filter, uncapped) → chips_
                      nav.selected = index of chipIsSelected chip (0 = All if none)
            render  → buildScreen: measure → chipMetrics → linesPerPage
                      → nav.top = pageStartOf(selected) → layoutPage → drawChip × n
            tap chip i        → activateIndex(i) → TagSelectionResult → finish
            long-press tag i  → confirm → STUDY.retireTag(id) → rebuild chips_ (locked)
            swipe / hold      → page turn (locked) → requestUpdate
            Back / Home       → cancelled result → finish
  └─ result handler (unchanged): apply pick → dropRetiredFilter → rebuild rows + header chips
```

## Error handling

- **Interaction overflow:** each page registers at most `GRID_MAX_CHIPS` (64) buttons, plus the
  popup's buttons, which stays under 96. If the table overflows anyway, `UiAppHost.cpp:24` logs
  it. There is no silent path.
- **OOM:** `chips_` (40 B × at most 202 ≈ 8 KB) and `widths_` (4 B × at most 202) are allocated
  in `std::vector` on entry and after a retirement, not per frame. That mirrors the heap-sized
  `rowItems_` this replaces (`TagFilterActivity.h:62-64`). `reserve` is called before filling. A
  failed allocation aborts under `-fno-exceptions`, the same as the `rowItems_.reserve` and
  `chips_.reserve` calls this code already makes (`TagFilterActivity.cpp:41`,
  `HighlightsActivity.cpp:131`). No new failure mode is added.
- **Stack:** `GridPage` (~1 KB) and `widths_` are members, and the build uses no large locals
  (CLAUDE.md, 256 B rule; `TagChipRow.h:105-106`).
- **Stale index:** `activateIndex`/`onRowLongPress` bounds-check against `chips_.size()`. A retire
  captures the id, so a rebuild between the long-press and the confirmation cannot retire the
  wrong tag (the same reasoning as `TagFilterActivity.h:59-61`).
- **Save failure / `saveDisabled`:** unchanged (`TagFilterActivity.cpp:94-99`, `:128`).
- **Every exit sets a result:** unchanged (`TagFilterActivity.h:30-34`).

## Testing strategy

TDD in `test/tag_rows/TagChipRowTest.cpp`, which already builds into `TagRowsTest`
(`test/tag_rows/CMakeLists.txt:1-5`), so no CMake edit is needed. Each test is written failing
first.

- **Candidates (A1):**
  - the order is All, then tags in active order, then Unlabelled;
  - zero-count tags are dropped unless they are the filter;
  - Unlabelled is dropped at zero unless it is the filter;
  - the cap is honoured (header) and uncapped means every candidate is included;
  - chapter-scoped counts feed through (reusing the `TagChipScopedCounts` fixtures,
    `TagChipRowTest.cpp:142-170`).
- **Chip height (A6):** `chipHeight` is never below `minTouch`, and equals the text height plus
  padding when that is larger.
- **Grid paging (A4, A5):**
  - 24 chips of realistic width (the owner's case) fit one page on a portrait body: one page, and
    every chip placed;
  - 202 chips split into more than one page; every chip is on exactly one page, in order; no page
    exceeds `GRID_MAX_CHIPS` or `linesPerPage`;
  - a chip wider than the line still gets a page (progress);
  - `pageStartOf` agrees with the page that `layoutPage` placed the chip on;
  - zero chips give zero pages;
  - `linesPerPage` is never below 1.
- **Hit tiling:** the existing `TagChipGeometry.HitRectsNeverIntersect` /
  `NeighboursShareTheGapExactly` properties (`TagChipRowTest.cpp:281-330`) are re-run over a
  `GridPage` through the generalised `hitPadding`.
- **Removed:** `FilterRows` tests go with `FilterRows`.
- **Build:** `pio run` (x4pro) once after the last edit; `./bin/clang-format-fix` over the whole
  tree before committing.
- **Device (owner):**
  1. With 20+ tags, **…** shows every chip on one screen, with counts.
  2. Header and grid chips are visibly larger, and taps land reliably.
  3. In "Tags here", the counts are chapter counts.
  4. Tapping a chip filters and returns; Back/Home keep the filter.
  5. Long-press retire still confirms and retires.
  6. The selected chip is inverted.
