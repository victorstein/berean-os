## Problem

In a Bible, *Select chapter* always opens the navigator at the book grid. The reader builds
`BibleNavigationActivity(renderer, mappedInput, epub)` without the position
(`EpubReaderActivity.cpp:728-729`), even though it captured it at `:716` and passes it to the
non-Bible list at `:731`. The navigator starts at `Level level = Level::Book`
(`BibleNavigationActivity.h:47`), and `onEnter` never changes that (`BibleNavigationActivity.cpp:36-50`).

So moving within the book you are reading, the common study case, costs a re-pick of that book
every time. From Gen 32:35 to Gen 31:1 today is: menu → Select chapter → find Genesis → 31 → 1.

## Goal

From a Bible chapter, *Select chapter* opens on that book's chapter grid, with the current chapter
selected and its page in view. The rest of the drill-down is unchanged. In particular:

- Back (a button press or the left-edge swipe) from that grid goes to the book grid with the current
  book selected.
- Back from the book grid cancels to the reader menu.

## Non-goals

- Previous/next-chapter gestures in the reader. The tap zones are already allocated
  (`ReaderUtils.h:140`).
- Any change to Bible verse search or to the non-Bible chapter list
  (`EpubReaderChapterSelectionActivity`).
- A setting to choose the entry level. The owner decided against one (issue #187, "Decided").
- Opening at the verse grid. The owner decided on the chapter grid (same).
- Any persisted state, on-disk format, input-layer change or new dependency.

## Decisions

### D1 — find the book from `bookTargetSpine`, then confirm the chapter from `chapterSpine`

Both arrays are already navigator members (`BibleNavigationActivity.h:53,78`). `loadBooks` fills
the first (`BibleNavigationActivity.cpp:80-83`), and `loadChapters` fills the second
(`:131-134`).

Measured on both NWT EPUBs (R§"How spine index maps"):

- `bookTargetSpine` is ascending.
- Each book's chapters are contiguous.
- Every book's chapters lie in `[bookTargetSpine[i], bookTargetSpine[i+1])`.

The book is therefore the one with the largest `bookTargetSpine[i]` that is at or below the spine.
The chapter row is the `k` with `chapterSpine[k] == spine`, found after one `loadChapters(book)`.
That load is the same work `activateIndex` already does when the user taps the book (`:240`).

**Rejected alternatives:**

- The TOC covering entry (`Epub::getTocIndexForSpineIndex`, `Epub.cpp:886`). It also names the
  book (0 mismatches, R§"How spine index maps"), but it needs a TOC-href join against the book-nav
  targets that the range rule avoids.
- The reader's cached `bibleChapterNumber` (`EpubReaderActivity.h:75-76`). It is -1 whenever a
  finished layout cache skipped the HTML (`EpubReaderActivity.cpp:1597-1601`), and it carries no
  book.

### D2 — the decision lives in a pure header, the loads stay in the activity

A new header, `src/activities/reader/BibleEntryPosition.h` (namespace `BibleEntry`), holds the
spine → entry arithmetic over plain arrays. The activity keeps the SD work (`loadChapters`) and the
level switch (`enterLevel`). This makes the whole mapping, including the five single-chapter books,
host-testable without FreeInkUI, `Epub` or `HalStorage`, as `NumberGridLayout.h` is.

## Labelled assumptions

Each is a behavioural choice the review can attack.

- **A1 — the chapter grid opens only when both the book and the chapter row resolve.** Anything
  else falls back to A3, A4 or A5. This is the issue's third acceptance criterion.
- **A2 — the book rule is "largest `bookTargetSpine[i] <= spine`", skipping entries `< 0`.**
  - It does not assume the array is sorted, although it is on both measured EPUBs.
  - `resolveFilenamesToSpineIndices` writes -1 for an unresolved target (`Epub.h:88`,
    documented in the 2026-09-12 spec at `:102-103`), so a -1 entry must never win.
  - Ties cannot occur in a real publication. If one did, the lowest index wins, which keeps the
    result deterministic.
- **A3 — on a book's own entry page, open the book grid with that book selected.** The trigger is
  `spine == bookTargetSpine[book]`. Two cases hit it:
  - a multi-chapter book's chapter-nav page, which has no chapter row;
  - a single-chapter book's only chapter (Obadiah, Philemon, 2 John, 3 John, Jude). These have no
    chapter level (`BibleNavigationActivity.h:54-56`, `:236-238`).

  The book is known in both cases. The nearest existing level is the book grid, and preselecting
  the book still saves the page hunt. **Rejected:** opening the verse grid for single-chapter books,
  because the owner ruled out verse-grid entry. Also rejected: today's unselected book grid, which
  throws away a known position.
- **A4 — a spine inside a book's range that is not one of its chapters falls back to today's entry**
  (book grid, index 0). Known cases:
  - the next book's outline page, which sits between the previous book's last chapter and the next
    nav page (measured: `1001061301.xhtml` at spine 80 between Genesis 50 at 79 and Exodus's nav
    page at 81);
  - every appendix after Revelation 22 (spine 1344 onward).

  The mapping cannot tell these apart from a chapter without loading that book's chapter list. That
  costs one `loadChapters` that goes unused: a chapter-nav stream (at most 13,940 B, the Psalms page,
  per the 2026-09-12 spec `:37-38`) plus a spine-resolution pass up to that book's last chapter
  (`resolveFilenamesToSpineIndices`, `BibleNavigationActivity.cpp:131`; `Epub.cpp:963-977` stops once
  every target resolves), at most 1,344 spine entries for Revelation. **Accepted:** the stream is bounded, it happens only from non-chapter pages, and
  avoiding it would need layout knowledge that D1 deliberately does not rely on.
- **A5 — a spine before the first book, or no resolvable book at all, falls back to today's entry.**
  This covers front matter, the book-nav page itself (spine 2) and Genesis's outline (spine 28;
  Genesis's nav page is at 29). Genesis's outline therefore falls back through A5 at no cost, while
  every other book's outline falls back through A4 at the cost of one wasted load.
- **A6 — a single-chapter book's spine that is past its only chapter falls back (A4 rule).** Such a
  spine lies within the book's range but is not the book's target. No chapter load is attempted,
  because a single-chapter book has no chapter-nav page to load.
- **A7 — a failed `loadBooks` or `loadChapters` falls back to today's entry.**
  - `loadBooks` failing leaves `bookCount == 0`, and `onEnter` already logs it (`:47-49`). The
    mapping then sees no books and returns A5's "none".
  - `loadChapters` failing (OOM or a stream error, `:108-136`) logs and stays at the book grid,
    with index 0.
- **A8 — the extra load happens synchronously in `onEnter`, before the first paint.**
  - The first render is deferred until the loop pass ends (`ActivityManager.cpp:289-293`,
    `:167-172`), so the user normally never sees the book grid flash before the chapter grid. A render
    notification still queued from an earlier pass can catch `onEnter` mid-load, as the class header
    already notes (`BibleNavigationActivity.h:69-73`). That is cosmetic, since `enterLevel` switches
    under `RenderLock` (`BibleNavigationActivity.cpp:192`).
  - Time to first paint grows by one chapter-nav stream. This is the same stream a book tap costs
    today, and the tap it replaced is saved.
- **A9 — Back and the swipe need no new code.** Chapter → Book is `enterLevel(Level::Book,
  selectedBook)` (`BibleNavigationActivity.cpp:353-354`). Book → cancel is `:350-351`, and cancel
  reopens the reader menu (`EpubReaderActivity.cpp:733-735`). The swipe reaches the same
  `onBackButton` (`MappedInputManager.cpp:265` → `UiListActivity.cpp:47-49`). Opening at Chapter
  only requires `selectedBook` to be set before `enterLevel`.
- **A10 — Back from a chapter grid the user never left lands on the right book-grid page.** The
  book layout has not been built yet at that point (it is built lazily in `buildGrid`, `:395-401`).
  `enterLevel` sets `nav.selected = selectedBook` (`:195`), and `placeSelectionLocked` returns early
  on the unbuilt layout (`:259`, `:265`). The next `buildGrid` builds the layout and picks the page
  from `BookGrid::pageOf(bookLayout, nav.selected)` (`:405-407`). The code has not been changed for
  this; the path is new at runtime, so device check 3 covers it (R§"Things the design has to
  handle").
- **A11 — the chapter grid's first paint shows the current chapter's page.** `enterLevel(Chapter,
  row)` runs with zero geometry, so `nav.top` becomes 0 (`NumberGridLayout.h:56-64`). The first
  build then sees `nav.visibleRows != grid.cellsPerPage()` and re-pages to
  `pageStartFor(nav.selected, …)` (`BibleNavigationActivity.cpp:414-417`). Covered by device
  check 2 (Psalm 119, on grid page 2+ of Psalms).
- **A12 — the reader passes the spine it captured before releasing the section.** That is
  `spineIdx` at `EpubReaderActivity.cpp:716`, the same value the non-Bible branch receives (`:731`).

## Architecture

### 1. `src/activities/reader/BibleEntryPosition.h` (new)

Header-only, `#pragma once`, includes `<cstdint>` only. Its top comment follows
`NumberGridLayout.h:6-9`: "Deliberately free of FreeInkUI, Arduino and Epub so the host suite can
exercise it (test/number_grid)."

```cpp
namespace BibleEntry {

enum class Kind : uint8_t {
  None,          // today's entry: book grid, nothing preselected
  SelectBook,    // book grid with `book` selected (A3)
  LoadChapters,  // load `book`'s chapters, then resolve the row with chapterRowFor (A4 on a miss)
};

struct Entry {
  Kind kind = Kind::None;
  int book = -1;
};

// Largest bookTargetSpine[i] <= spine, skipping unresolved (< 0) targets; -1 when none (A2, A5).
inline int bookFor(const int16_t* bookTargetSpine, int bookCount, int spine);

// A1, A3, A5, A6 in one place. `bookIsDirect[i]` marks the single-chapter books.
inline Entry classify(const int16_t* bookTargetSpine, const bool* bookIsDirect, int bookCount, int spine);

// Index k with chapterSpine[k] == spine, or -1 (A4).
inline int chapterRowFor(const int16_t* chapterSpine, int chapterCount, int spine);

}  // namespace BibleEntry
```

`classify` is:

- spine `< 0`, or `bookFor` returns -1 → `None`;
- `spine == bookTargetSpine[book]` → `SelectBook`;
- `bookIsDirect[book]` → `None` (A6);
- otherwise → `LoadChapters`.

### 2. `BibleNavigationActivity` (`.h` / `.cpp`)

- **Constructor:** gains `int currentSpineIndex`, stored as `const int entrySpine`, mirroring
  `EpubReaderChapterSelectionActivity.cpp:14-20`. The header comment on the class
  (`BibleNavigationActivity.h:15-26`) gains one sentence: the navigator opens at the chapter grid
  of the book being read.
- **`onEnter`:** after `loadBooks()` (`:47`), call a new private `enterAtPosition()`. It keeps the
  existing order: the font-cache clear stays first (`:43-45`), per the reader-overlay rule.
- **`enterAtPosition()`** (new, private, about 20 lines):

  ```
  entry = BibleEntry::classify(bookTargetSpine, bookIsDirect, bookCount, entrySpine)
  None         → return                                   (today's state: Book, index 0)
  SelectBook   → selectedBook = entry.book; enterLevel(Book, entry.book)
  LoadChapters → if !loadChapters(entry.book): LOG_ERR; return          (A7)
                 row = BibleEntry::chapterRowFor(chapterSpine, chapterCount, entrySpine)
                 if row < 0: LOG_DBG; return                            (A4)
                 selectedBook = entry.book; enterLevel(Chapter, row)
  ```

  `enterLevel` already takes `RenderLock` and places the selection's page (`:188-204`), so no new
  locking is needed. A miss after a successful `loadChapters` leaves `chapterCount` non-zero at
  Book level. That is harmless: `listCount()` reads it only at Chapter level (`:153-163`), and
  `activateIndex` reloads it on the next book tap (`:240`).
- **Nothing else changes:** `onBackButton`, `activateIndex`, `drawChrome` and the grid code are
  untouched. `drawChrome` already titles the chapter grid from `selectedBook` (`:511-512`).

### 3. `EpubReaderActivity.cpp:729`

The call becomes `std::make_unique<BibleNavigationActivity>(renderer, mappedInput, epub, spineIdx)`.
Nothing else in the handler changes.

## Resources

- **Internal SRAM:** one `const int` member (4 B) on the activity. There are no new buffers:
  `chapterSpine` (300 B) and `bookTargetSpine` (132 B) already exist (`BibleNavigationActivity.h:53,78`).
- **Heap:** `loadChapters` makes its existing transient allocations (a scanner, a
  `std::vector<std::string>` of about 50–150 targets, and `makeUniqueNoThrow<int[]>(chapterCount)`,
  `:112-134`). In the stay-in-book case they happen at entry instead of on a tap. Going Back to
  another book loads twice (the current book at entry, then the tapped one), where today it loads
  once. The allocations are sequential, never both resident.
- **Flash:** a few hundred bytes of inline code. No new strings, and no `tr()` keys.
- **SD:** one `loadChapters` per entry from a mapped position. That is a chapter-nav stream plus a
  spine-resolution pass up to the book's last chapter (≤ 1,344 spine entries; each is a `book.bin`
  seek and read, `BookMetadataCache.cpp:508-524`).
  - In the stay-in-book case it replaces the book-tap load, so it costs nothing extra.
  - It is extra when the user goes Back to another book (the issue's Exod 3:1 row), and on every
    A4 miss.
  - **Raised against acceptance criterion 4** ("without a second SD sweep … if it does need one,
    raise it as a decision"). The chapter grid the owner chose cannot be drawn without
    `chapterSpine`, and nothing else in memory provides it, so the load is intrinsic to the decided
    UX rather than a second sweep for the mapping. The PR description states this for the owner.

## Error handling

Every failure degrades to today's behaviour, never to an empty or wrong screen.

| Condition | Result | Log |
|---|---|---|
| `loadBooks` fails | book level, 0 books, "No chapters" (unchanged, `:379-381`) | existing `LOG_ERR` (`:48`) |
| spine before any book, or `< 0` | book grid, index 0 | none (an expected position) |
| spine is a book's target page | book grid, that book selected | none |
| `loadChapters` fails | book grid, index 0 | `LOG_ERR("BNV", "Entry: no chapter list for book %d", book)` |
| spine in a book's range but not a chapter | book grid, index 0 | `LOG_DBG("BNV", "Entry: spine %d is not a chapter of book %d", …)` |

No new allocation is fallible beyond what `loadChapters` already null-checks (`:125-130`).

## Testing strategy

TDD: the failing test is written and run before `BibleEntryPosition.h` exists.

### `test/number_grid/BibleEntryPositionTest.cpp` (new executable in the existing directory)

The fixture is the measured NWT layout as numbers only. It contains no publisher text, per the
public-fixture rule. It is taken from the research script's dump, which was identical for EN and ES
(`md5` of the `bookTargetSpine` dump matched):

- `BOOK_TARGET[66]`: 29, 81, 123, … 1321;
- `CHAPTER_COUNT[66]`: 50, 40, … 22;
- direct books at indices 30, 56, 62, 63, 64 (spines 977, 1272, 1315, 1317, 1319).

A helper builds a book's `chapterSpine` as `BOOK_TARGET[i] + 1 + k`. This matches every measured
book ("gaps [] 0").

Cases:

1. Gen 32 (spine 61) → `LoadChapters(0)`, row 31. Also Gen 1 (30) → row 0, and Gen 50 (79) →
   row 49.
2. Psalm 119 and Psalm 150 → book 18, rows 118 and 149. Row 149 is the `MAX_CHAPTERS - 1` edge.
3. Rev 22 (1343) → book 65, row 21.
4. Each of the five single-chapter books at its target spine → `SelectBook(i)`. The issue's
   acceptance criterion names these explicitly.
5. The spine after a single-chapter book (978, Jonah's outline) → `None` (A6).
6. Genesis's nav page (29) → `SelectBook(0)` (A3).
7. Exodus's outline (80) → `LoadChapters(0)`, then `chapterRowFor` → -1 (A4).
8. An appendix (1344, and the last spine 3940) → `LoadChapters(65)`, then row -1 (A4).
9. Front matter (0), Genesis's outline (28) and the book-nav page (2) → `None` (A5).
10. `spine = -1`, `bookCount = 0` and null-safe empty arrays → `None` / -1.
11. An unresolved target (`-1` in `bookTargetSpine`) never wins, and an unsorted array still yields
    the largest target at or below the spine (A2).
