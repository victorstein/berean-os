# Issue #238 design: make Go to open the chapter grid fast

Research: `docs/superpowers/research/2026-09-30-issue-238-research.md` (base `58546aaf`).
Revised after `docs/superpowers/reviews/issue-238-spec-review-0.md` (CLEAR, 2 MAJOR, 6 MINOR); see
"Changes from review 0" at the end. `EpubReaderActivity.cpp` and `LauncherActivity.cpp`
references are re-cited against `origin/main` `4c0b8cb5` (after PR #236). Every other file cited
here is identical on both bases.
Surface: ui (`src/activities/reader`, `src/components`). Review tier: `standard`.

## Problem

There is a large delay between tapping **Go to** and the chapter grid's first frame. This
happens both from the reader menu's quick action and from Home. The research traced the cause to
work the loop task does in `BibleNavigationActivity::onEnter` (`BibleNavigationActivity.cpp:57-83`)
**before the render task is even notified**. The render request is deferred to the end of
`ActivityManager::loop` (`ActivityManager.cpp:166-173`; `UiListActivity.cpp:26`).

- `loadBooks()` resolves the 66 book-nav targets with
  `Epub::resolveFilenamesToSpineIndices` (`BibleNavigationActivity.cpp:109`). That walks
  `book.bin` from spine 0 until the last target resolves (`Epub.cpp:963-978`). In `nwt_S.epub` the
  last target, `biblechapternav66.xhtml`, is at spine 1,321, so the walk reads **1,322 spine
  entries**. Each read is a seek, a 4-byte LUT read, a second seek, and a string plus two PODs
  (`BookMetadataCache.cpp:508-525, 46-52`), and every one of those goes through `HalFile` and takes
  `storageMutex`.
- `bookNames.joinToc` then reads **every TOC entry** (196 in `nwt_S.epub`) the same way
  (`BibleBookNameTable.cpp:53-66`, `BookMetadataCache.cpp:527-544`).
- `enterAtPosition` → `loadChapters(book)` walks the spine **from 0 again**, up to the book's last
  chapter (`BibleNavigationActivity.cpp:166`). That is ~80 entries for Genesis and **~1,344** for
  Revelation.
- None of this is kept. A second Go to repeats all of it.

The masthead is a smaller, render-task cost. It streams all 783 rows of `thumb_783.bmp` and sets
pixels one by one (`CoverBand.cpp:19-58`), on every paint. The entry refresh is **FAST**, not
HALF, on both paths (research, "Cost 4"; `UiListActivity.cpp:169`,
`BibleNavigationActivity.cpp:293-296`, `FreeInkDisplay.cpp:316-324,572-574`). Nothing on the
Go to path generates a thumbnail (`Masthead.cpp:51-60`).

## Goal

1. **Measure.** Add `LOG_DBG` milestones from the tap to the grid's first frame on both paths, so
   the before and after numbers come from the same instrumentation.
2. **Remove the long walks**, so the first Go to is fast without spending any memory:
   - Book spines come from the TOC entries the join already reads. Each `TocEntry` carries a
     `spineIndex` resolved when `book.bin` was built (`BookMetadataCache.h:37`,
     `BookMetadataCache.cpp:413-449`).
   - The chapter walk starts at the book's own nav page instead of spine 0.
3. **Cache for the life of the reader.** A second menu Go to reads neither the book-nav page, nor
   the TOC, nor the current book's chapter list.
4. **Target:** the first grid frame within ~500 ms of the tap on a warm menu Go to (the issue's
   target), and no drop in the internal free heap that the grid already logs
   (`BibleNavigationActivity.cpp:79-82`).

## Non-goals

- **The reader cold load on the Home path.** `loadBook`, `STUDY.openPublication` and
  `STUDY.repairTexts` (`EpubReaderActivity.cpp:155-240`), plus the two SD writes in
  `ReaderActivity::onEnter` (`ReaderActivity.cpp:58-60`), are the reader's open cost and are
  shared with every Home target. They get timed, not changed.
- **Painting the grid before the masthead art and then filling the band.** That is two refreshes
  for one screen. The panel's contract is a small number of deterministic refreshes
  (`.claude/agents/ui-dev.md`, "Constraints that bite here").
- **Changing the refresh mode.** Entry is already FAST (above).
- **The section rebuild when returning to the page** (`releaseSectionKeepingPosition`,
  `EpubReaderActivity.cpp:258-267`). It falls after the grid, outside the tap-to-grid window.
- **Anything in `lib/Epub`.** `Epub::resolveFilenamesToSpineIndices` keeps its signature and its
  other behaviour.

## Assumptions (each one is a decision the review should attack)

- **A1 — The cache lives for the life of the reader, not the device session.** The issue says
  "Cache the book table and chapter spines for the life of the reader". A Home Go to builds a new
  reader and a new `Epub` every time (`ActivityManager.cpp` `goToReader` → `replaceActivity`;
  `EpubReaderActivity.cpp:156`), so a repeat Home Go to gains only from goal 2, not from the
  cache. A process-wide cache keyed by the book would need an invalidation rule for a replaced
  EPUB. `BOOK_CACHE_VERSION` alone does not catch that (memory: `jw-nwt-epub-toc-doubling`;
  `BookMetadataCache.cpp` validates only the version). No such pattern exists in `src/activities`,
  so it is out of scope.
- **A2 — The book table's spine targets come from the TOC, with the spine walk as fallback.**
  `joinToc` already reads every TOC entry, and each one carries the `spineIndex` resolved at
  build time. The first TOC entry whose filename matches a target wins, the same first-match rule
  `joinToc` uses for names (`BibleBookNameTable.cpp:63-64`). Any target still unresolved after the
  join (no TOC entry, or `spineIndex` outside `[0, spineCount)`) is resolved by
  `SpineSearch::resolveFrom(first = 0)`, which skips targets already set.
  `Epub::resolveFilenamesToSpineIndices` resets every output to `-1` first (`Epub.cpp:964`), so it
  cannot serve a subset. Evidence: all 66 book-nav targets appear in `toc.xhtml` in both the
  stock and the user's trimmed `nwt_S.epub` (a Python `zipfile` check over both files). A
  publication where they do not appear still resolves, only slower.
- **A3 — A book's chapters are searched from its own nav page forward, wrapping to the start.**
  In `nwt_S.epub` no chapter precedes its book's nav page, and the furthest chapter is **150**
  entries past it (Psalms). That was checked for all 61 chapter-nav books; the 5 direct books have
  no chapter list. The walk begins at `bookTargetSpine[book]`, runs to the end of the spine, then
  wraps through `[0, start)` for anything still unresolved. It stops as soon as every target has
  resolved, as today. A publication laid out differently resolves the same indices, just slower.
- **A4 — One cache object, allocated lazily, PSRAM-preferred by size.** `BibleNavCache` is about
  6.0 KB: the book table below plus one book's chapters. That is over the 4,096 B
  `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` threshold with `CONFIG_SPIRAM_USE_MALLOC=y`
  (`framework-arduinoespressif32-libs/esp32s3/sdkconfig:2153-2154`). `makeUniqueNoThrow`
  therefore asks SPIRAM first and falls back to internal RAM only when PSRAM is exhausted, which
  is a preference and not a guarantee. The same by-size placement is already relied on for the
  `BibleBookNameTable` in `collectRecentChips` (`EpubReaderActivity.cpp:961-965` on `origin/main`).
  This deliberately differs from #204's explicit `heap_caps_malloc` + `PsramFree` for a raw byte
  buffer. `BibleNavCache` is a typed object, and placement-new over `heap_caps_malloc` would be a
  new pattern, whereas an internal fallback of 6 KB under PSRAM exhaustion is benign. A
  `static_assert(sizeof(BibleNavCache) > 4096)` keeps the object above the threshold, so a later
  shrink cannot quietly move it to internal SRAM. The object is allocated on the first Go to in a Bible, so a reader
  that never uses Go to, or a non-Bible book, pays nothing. If allocation fails, Go to runs
  uncached, with goal 2 still in force, and logs `LOG_ERR`.
- **A5 — Ownership is a `std::shared_ptr` handed to the navigator.** The reader owns it, and
  `BibleNavigationActivity` takes a `std::shared_ptr<BibleNavCache>`, as it already takes
  `const std::shared_ptr<Epub>&` (`BibleNavigationActivity.h:35-36`). This keeps the header's rule
  that nothing in the navigator "points into the reader underneath"
  (`BibleNavigationActivity.h:63-64`). The shared control block is the only new internal-SRAM
  allocation, a few dozen bytes, made once per reader.
- **A6 — The navigator copies out of the cache and never renders from it.** On a hit, the
  navigator copies the book table into its own members and bumps `booksLoadedGeneration` exactly
  as `loadBooks()` does today (`BibleNavigationActivity.cpp:137`). The render task's reads, the
  layout cache key and the `RenderLock` hand-off are therefore unchanged. The cache is read and
  written only on the loop task: `onEnter`, `activateIndex` and the reader's handlers all run there
  (`ActivityManager.cpp:89,159-160`). So it needs no lock.
- **A7 — Chapter cache: the most recently loaded book only.** Its spine targets are
  `int16_t[150]` (`MAX_CHAPTERS`, `BibleNavigationActivity.h:43`), and its marks are **not**
  cached. `markChapters` depends on `STUDY.passages()` and the bookmarks, which change between two
  Go tos, and it is in-memory work (`BibleNavigationActivity.cpp:192-206`). A hit also skips
  streaming the chapter-nav page, since the targets are all that page provides.
- **A8 — Only successes are cached.** A failed `loadBooks` or `loadChapters` (a stream failure, no
  targets, or OOM) leaves the cache as it was, so the next Go to retries. Nothing invalidates the
  cache during a reader's life: the `Epub` does not change under a live reader, and
  `DELETE_CACHE` leaves for Home, which destroys the reader (`EpubReaderActivity.cpp:805-821`).
  The book table depends on neither orientation nor font. The navigator recomputes its layout
  per render.
- **A9 — The reader menu's Recent chips read the cached names when they are present.**
  `collectRecentChips` builds a `BibleBookNameTable` on every menu open and reads
  `abbreviationFor(place.unit.book)` from it (`EpubReaderActivity.cpp:964-969` on `origin/main`).
  With the cache filled, it uses the cached table instead. It never *fills* the cache, so the
  menu-open cost is unchanged when the cache is empty.
  **This needs the navigator's table to carry abbreviations.** Today the navigator calls only
  `joinToc` (`BibleNavigationActivity.cpp:111`), which *clears* every abbreviation
  (`BibleBookNameTable.cpp:55-58`, `.h:38-40`). `load()` fills them afterwards from the page labels
  (`BibleBookNameTable.cpp:47-49`). So `load()`'s tail becomes a public
  `BibleBookNameTable::setAbbreviations(const std::vector<std::string>& labels)`. `load()` calls
  it, and so does the navigator's `loadBooks`, right after `joinToc`. The cached table then answers
  `abbreviationFor` exactly as a `load()`ed one does: the page label, or `""` when there is none.
  It never uses the navigator's `abbrev[]`, which falls back to the full name
  (`BibleNavigationActivity.cpp:118-125`). Without this, every chip would show its full reference
  after the first Go to (`PlacesDoc.cpp:64-66`).
- **A10 — The masthead band cache depends on the "before" number, and lives in the reader-life
  cache.** It is built only if the existing `"Band drawn in %lu ms"` log (`Masthead.cpp:83-85`)
  shows **> 150 ms** on the device.
  - **Where it lives.** If it is built, the band bytes live in `BibleNavCache`, which lasts as long
    as the reader, *not* in the navigator. Every Go to constructs a new navigator
    (`EpubReaderActivity.cpp:908+` on `origin/main`), so a navigator-owned buffer would never exist
    at a Go to's first frame, which is the metric this gate reads.
  - **Filling it.** `Masthead` gains a draw path that, after `CoverBand::draw` has blitted the band
    and before the header plate, snapshots it with `GfxRenderer::readFramebufferRegion`
    (`GfxRenderer.h:268-275`; the region snaps outward to byte alignment,
    `GfxRenderer.cpp:335-359`).
  - **Using it.** On every later paint, including the first frame of a warm Go to, the snapshot is
    restored with `writeFramebufferRegion` in place of `CoverBand::draw`. That is the idiom the
    menu uses for its page snapshot (`EpubReaderMenuActivity.cpp:520-523`). The plate and title
    are then drawn over it as today.
  - **Why the snapshot stays valid.** Its content is fixed for the reader's life: the same `Epub`,
    the same `mastheadCover` path and the same band rect, on a portrait-only device.
  - **The buffer.** ~7.5 KB, allocated lazily on first use with `heap_caps_malloc(MALLOC_CAP_SPIRAM)`
    and a `PsramFree` deleter, as #204 committed to for this exact buffer and as `CatalogIndexStore`
    does (`CatalogIndexStore.h:83-90`, `.cpp:40-47`). It is a raw byte buffer, so the explicit
    placement costs nothing. If the allocation fails, the band draws from SD as today.
  - **If the band time is ≤ 150 ms,** the plan records the number and skips the work.
- **A10b — A warm first frame that still misses ~500 ms is reported, not chased.** The PR names
  the dominant milestone from the "after" log. This issue adds no further change for it: the
  refresh and the reader cold load are out of scope (Non-goals).
- **A11 — The milestones are `LOG_DBG`, permanent, and compiled out of release.** They mirror
  `LOG_DBG("ERS", "Rendered page in %lums", ...)` (`EpubReaderActivity.cpp:1450` on `origin/main`). The release
  env sets `LOG_LEVEL=0` (root `CLAUDE.md`, "Environments").
- **A12 — The device numbers come from the owner.** No device was attached in this session
  (`ls /dev/cu.usbmodem*` matched nothing). The PR carries the before/after table from a dev
  build; the owner runs it or the agent runs it when a device is attached. Host tests prove the
  resolution and caching logic, not the milliseconds.

## Architecture

### New: `src/activities/reader/BibleNavCache.h` (header-only, no Arduino, no Epub)

Modelled on `BibleEntryPosition.h`: a header-only helper free of FreeInkUI, Arduino and Epub,
host-tested in `test/number_grid` (`BibleEntryPosition.h:1-8`,
`test/number_grid/BibleEntryPositionTest.cpp`).

The limits the struct needs are private to the navigator today (`BibleNavigationActivity.h:42-46`).
They move into this header as `BibleNavLimits::MAX_BOOKS`, `MAX_CHAPTERS`, `BOOK_NAME_BYTES` and
`BOOK_ABBREV_BYTES`, and the navigator's existing constants alias them.

```cpp
struct BibleBookIndex {             // what loadBooks() produces today
  BibleBookNameTable names;         // BibleNavigationActivity.h:75
  int16_t targetSpine[MAX_BOOKS];   // :76
  bool isDirect[MAX_BOOKS];         // :79
  char abbrev[MAX_BOOKS][BOOK_ABBREV_BYTES];                 // :81
  char sectionTitle[BookGrid::MAX_SECTIONS][BOOK_NAME_BYTES]; // :82
  int sectionStart[BookGrid::MAX_SECTIONS];                   // :83
  int sectionCount;
  int bookCount;
};

class BibleNavCache {
 public:
  bool hasBooks() const;
  const BibleBookIndex* books() const;          // nullptr until stored
  void storeBooks(const BibleBookIndex& index); // ignored when bookCount == 0
  // The chapter spines for `book`, or nullptr unless that book is the one stored.
  const int16_t* chaptersFor(int book, int& count) const;
  void storeChapters(int book, const int16_t* spines, int count); // ignored unless 0 < count <= MAX_CHAPTERS
};
```

`BibleBookNameTable` already has only a header dependency on `Epub.h`. If that breaks the
Epub-free host build, the plan moves `BibleBookIndex` beside the navigator and keeps only the
pure cache logic in the tested header. That is a packaging choice, not a behavioural one.

The spine search lives in its own header-only `src/activities/reader/SpineSearch.h`. It is a pure
function over an href getter: a function pointer plus a context, per the `std::function` rule in
the root `CLAUDE.md`.

```cpp
namespace SpineSearch {
using HrefTailAt = std::string_view (*)(void* ctx, int spineIndex, std::string& scratch);
// Resolves still-unset (-1) entries of `out`, walking [first, spineCount) then [0, first).
// Stops as soon as every target is resolved.
void resolveFrom(const std::string* targets, int* out, int count, int first, int spineCount,
                 HrefTailAt hrefTailAt, void* ctx);
// Fills every unset out[j] whose target matches the TOC entry's filename,
// when 0 <= tocSpine < spineCount.
void takeTocSpine(const std::string* targets, int* out, int count, std::string_view tocHref,
                  int16_t tocSpine, int spineCount);
}
```

Both functions compare **every** unset `out[j]` against `BibleNav::filenameTail(href)`
(`BibleNavScanner.h:75`), as `resolveFilenamesToSpineIndices` does (`Epub.cpp:970-976`).
Duplicate targets therefore both resolve. `BibleNav::findTargetByHref` returns only the first match,
even when that slot is already set (`BibleNavScanner.cpp:193-199`), so it stays in use for the name
join only. `joinToc` passes `epub.getSpineItemsCount()` as `spineCount`.

The test executables include `${REPO_ROOT}/src` and `${REPO_ROOT}/lib/Epub/Epub`, and link
`BibleNavScanner.cpp` plus expat with `XML_GE=0 XML_CONTEXT_BYTES=1024`, as
`test/bible_book_join/CMakeLists.txt` does.

## Data and control flow

### First menu Go to (cache empty)

1. `onReaderMenuConfirm(SELECT_CHAPTER)` → `openChapterPicker` records `goToStartMs` and logs
   `"Go to: picker"`. It allocates `navCache` if null (A4), then `releaseSectionKeepingPosition()`
   (unchanged), constructs the navigator with `navCache` and `goToStartMs`, and pushes it.
2. The navigator's `onEnter` does the following, logging `+ms` after each step:
   - `clearCache` and the masthead `fits` check, both unchanged;
   - `loadBooks()`: a miss, so it streams `biblebooknav.xhtml`, then `joinToc(…, tocSpines)`,
     which reads the 196 TOC entries it read before and now also collects spines, then
     `setAbbreviations(page.labels)`. It calls `resolveFrom(first = 0)` only when some target is
     still `-1`. It then fills
     `books`, bumps `booksLoadedGeneration`, and calls `navCache->storeBooks(books)`;
   - `enterAtPosition()` → `loadChapters(book)`: a miss, so it streams the chapter-nav page, calls
     `resolveFrom(first = books.targetSpine[book])` (≤ 151 spine reads in NWT), then
     `storeChapters`, then `markChapters`;
   - the existing heap `LOG_INF`.
3. The render task runs the unchanged `UiListActivity::render`. The navigator's override then logs
   `"Go to: first frame +%lu ms"` once, after `displayBuffer` returns (a blocking refresh,
   `GfxRenderer.cpp:1724-1728`).

In spine-entry reads, the first Go to drops from ~1,322 + 196 + (80…1,344) to 0 + 196 + (≤ 151).

### Second menu Go to (cache warm)

Step 2 becomes: `loadBooks()` is a hit, so it copies `*navCache->books()`, bumps the generation,
and makes no SD reads. `loadChapters(book)` is a hit when `book` equals the stored book: it copies
the spines and runs `markChapters`, again with no SD reads. The remaining SD cost is the masthead
`fits` check, which opens the BMP header. The render cost is the band blit plus the refresh.

### Home Go to

The launcher logs `"Go to: home tap"`. `ReaderActivity::onEnter` logs before and after `loadBook()`.
Then `onBookLoaded` → `openChapterPicker(CancelTo::Page)` (`EpubReaderActivity.cpp:999` on `origin/main`)
behaves as the first menu Go to: the reader is new, so the cache is empty (A1).

### Choosing a different book inside the grid

`activateIndex` → `loadChapters(other)`: a miss, so it walks from that book's nav page and then
**replaces** the stored chapters (A7). Book-level navigation never touches the chapter cache.

## Error handling

- **Cache allocation fails:** `LOG_ERR("ERS", "OOM: Go to cache")`. The navigator gets a null
  `shared_ptr` and runs uncached (A4). Every cache call site checks for null.
- **A stream or scanner fails, or targets are empty:** the existing `return false` paths
  (`BibleNavigationActivity.cpp:88-101, 145-157`) are unchanged, and nothing is stored (A8).
- **A target resolves nowhere:** it stays `-1`, as today (`Epub.cpp:964`). Downstream code
  already handles `-1` (`BibleEntry::classify` ignores unresolved targets, `BibleEntryPosition.h`;
  `finishWith` rejects `spineIndex < 0`, `BibleNavigationActivity.cpp:308-312`).
- **A TOC `spineIndex` out of range** (a corrupt or foreign `book.bin`): `takeTocSpine` accepts
  only `0 <= spine < spineCount`, and anything else falls through to the walk.
- **No new storage** is written, so the root `CLAUDE.md` store discipline does not apply. No
  user-facing strings are added, so there are no `tr()` or YAML changes.

## Memory

| Allocation | Size | Where | Why |
|---|---|---|---|
| `BibleNavCache` | ~6.0 KB (~5.7 KB book table plus ~0.3 KB for one book's chapters) | PSRAM by size (A4) | Held for the reader's life; read only on the loop task. |
| `shared_ptr` control block | a few dozen bytes | internal | Once per reader. `std::allocate_shared` with a PSRAM allocator would be a new pattern; not worth it. |
| Band snapshot (A10 only) | ~7.5 KB | PSRAM, explicit (`heap_caps_malloc` + `PsramFree`) | Held with the cache for the reader's life; restored at every paint, including the warm first frame. |

The navigator's own book arrays already exist; A6 groups them without growing them. The existing
heap `LOG_INF` at Go to (`BibleNavigationActivity.cpp:79-82`) is the regression check: internal
free at the grid, before and after.

## Testing strategy

TDD. Each test is written and run failing before its code.

1. **`SpineSearch::resolveFrom`**, in a new `test/number_grid/SpineSearchTest.cpp` added to
   `test/number_grid/CMakeLists.txt`. That file is the surface's own, not the shared
   `test/CMakeLists.txt`, so no orchestrator hand-off is needed. The cases:
   - targets after `first` resolve without reading any index below `first`: a counting getter
     proves how many entries were read;
   - a target before `first` resolves through the wrap;
   - the walk stops at the last resolved target;
   - a pre-set `out[i]` is never overwritten;
   - a target that is absent stays `-1`;
   - `first` outside `[0, spineCount)` behaves as `first = 0`;
   - duplicate targets both resolve.
2. **`SpineSearch::takeTocSpine`**, in the same file:
   - a base-prefixed TOC href (`OEBPS/…`, the form `TocNavParser` stores,
     `BibleBookJoinTest.cpp:16-19`) matches the bare target;
   - the first match wins;
   - a negative spine, or one `>= spineCount`, is ignored;
   - duplicate targets both take the TOC spine;
   - an outline entry for another file does not match.
3. **`BibleNavCache`**, in `test/number_grid/BibleNavCacheTest.cpp`:
   - empty before any store;
   - `storeBooks` with `bookCount == 0` is ignored;
   - `chaptersFor` answers only for the stored book;
   - `storeChapters` for another book replaces the stored one;
   - an out-of-range count is ignored;
   - the stored data is a copy, so mutating the source after the store does not change it.
4. **Abbreviations survive the navigator's fill (A9)**, in `BibleNavCacheTest.cpp` or beside it:
   a `BibleBookNameTable` filled the navigator's way (`joinToc`, then `setAbbreviations`) returns
   the page label from `abbreviationFor` and `""` for a book with no label. If
   `BibleBookNameTable.cpp` cannot build on the host, because it depends on `Epub.h` and
   `SpineHtmlStream`, the plan moves `setAbbreviations` and `copyUtf8Truncated` somewhere the test
   can reach without changing their behaviour.
5. **Build:** `pio run -e x4pro`, once after the last code edit.
6. **Format:** `./bin/clang-format-fix` over the whole tree after `git add`.
7. **Device, by the owner (A12):** flash a dev build of the instrumentation-only commit first, and
   record, for both paths, the milestones for Genesis and Revelation entry, first and second Go
   to. Repeat on the final commit. Also record the internal free heap from the grid's `LOG_INF`
   in both builds. These numbers fill the PR's before/after table. A10 is decided from the
   "before" band time.

Fixtures are synthetic filenames (`biblechapternavN.xhtml`, `100106xxxx.xhtml`). No publisher
text is copied (memory: `public-repo-test-fixtures-no-full-publisher-text`).
