# Issue #109 — one Wi-Fi session helper for the five network activities

Research: `docs/superpowers/research/2026-09-27-issue-109-research.md`. All line references are to
`dc97292e` and were re-read for this spec.

## Problem

Five activities each carry their own copy of the same Wi-Fi teardown block, and each decides for
itself whether that block should run:

```cpp
if (WiFi.getMode() != WIFI_MODE_NULL) {
  WiFi.disconnect(false);
  delay(30);
  silentRestart();
}
```

- `ClockSyncActivity.cpp:36-40`, gated by `shouldTearDownWifiOnExit` (`ClockSyncActivity.h:23`,
  set at `ClockSyncActivity.cpp:29`)
- `OtaUpdateActivity.cpp:96-100`
- `CatalogSearchActivity.cpp:81-85`
- `MeetingDownloadActivity.cpp:75-79`
- `FontDownloadActivity.cpp:49-53`

The block is identical in all five. What differs is **whose Wi-Fi it is**: ClockSync leaves alone a
connection it found already up (`ClockSyncActivity.cpp:24-30`), while MeetingDownload
(`MeetingDownloadActivity.cpp:58`) and CatalogSearch (`CatalogSearchActivity.cpp:329`) check for one
on entry and then tear it down anyway, and OTA and FontDownload never check. A new network activity
has to copy the block and pick one of those rules, and one that forgets leaves the radio in a mode
that keeps CPU power saving off (`lib/hal/HalPowerManager.cpp:39-43`).

On this board `silentRestart()` does not restart: `FREEINK_CAP_TOUCH` is true for the X4 Pro
(`freeink-sdk/libs/hardware/BoardConfig/include/BoardConfig.h:175-178`), so `silentRestart()`
(`src/main.cpp:175-190`) returns through `finishWifiSessionWithoutRestart()` (`main.cpp:160-173`),
which stops SNTP and sets `WiFi.mode(WIFI_OFF)`. The effective teardown is "drop the association,
turn the radio off".

## Goal

One RAII type, `WifiSession`, that records on entry whether Wi-Fi was already connected and, in its
destructor, ends the session only if this activity is the one that brought it up. The five
activities hold one and lose their hand-written teardown. On every path reachable today the device
does exactly what it does now.

## Non-goals

- **Bring-up stays where it is.** `WiFi.mode(WIFI_STA)` in OTA (`OtaUpdateActivity.cpp:81`),
  FontDownload (`FontDownloadActivity.cpp:41`) and CatalogSearch's lazy `ensureWifi`
  (`CatalogSearchActivity.cpp:333`), and the connect/wait loop in `WifiSelectionActivity`, are not
  moved. See A6.
- **`CrossPointWebServerActivity` is not converted.** See A7.
- **The meeting prefetch is not changed.** See A8.
- **`silentRestart()` itself, `main.cpp`, and the deep-sleep teardown (`main.cpp:282-285`) are not
  changed.**
- `src/network/MeetingWeekCache.*` is not touched (owned by another task in this batch).
- No new user-visible strings, settings, stores or on-disk formats.

## Assumptions (each is a decision the review should attack)

**A1 — "Wi-Fi was up on entry" means `WiFi.status() == WL_CONNECTED`, not `getMode() != NULL`.**
Every existing entry check uses `status()` (`ClockSyncActivity.cpp:24`,
`MeetingDownloadActivity.cpp:58`, `CatalogSearchActivity.cpp:329`). The one reachable case where the
two disagree is `MeetingDownloadActivity` launched from the web server's mode list after a cancelled
Join (`CrossPointWebServerActivity.cpp:148-149`, `:188-190`): the radio is in `WIFI_STA` but not
connected. Today MeetingDownload turns the radio off on exit in that case (`:75-79`). Under A1 the
session does not count an unconnected radio as "up", so it still turns it off — unchanged.

**A2 — "Restore" is asymmetric: leave a connection alone, or turn the radio fully off.** When the
session did not find a connection on entry, the destructor ends the session (A3) rather than
recreating the exact entry state. An entry state of "radio on, not connected" is not restored to
itself; it is turned off, as today. Recreating a half-up radio would keep power saving disabled
(`HalPowerManager.cpp:39-43`) for no purpose.

**A3 — The teardown body is kept byte-for-byte: `WiFi.disconnect(false); delay(30); silentRestart();`,
guarded by `WiFi.getMode() != WIFI_MODE_NULL`.** Calling `WiFi.mode(WIFI_OFF)` directly would be
equivalent on this board but would drop two things `silentRestart()` owns: the SNTP stop
(`main.cpp:165-167`) and the `deepSleepInProgress` short-circuit (`main.cpp:176`) that `enterDeepSleep`
relies on (`main.cpp:268-271`). The `getMode()` guard is kept so an activity that never turned the
radio on (CatalogSearch browsing the cached index, any activity backed out before selection) does no
Wi-Fi calls on exit, as today.

**A4 — The session is opened in `onEnter()` and ended by member destruction, which runs right after
`onExit()`.** Each activity holds `std::optional<WifiSession> wifiSession;` declared as its **last**
data member and calls `wifiSession.emplace()` at the point its current entry check runs. The
`ActivityManager` calls `onExit()` and then destroys the activity, under the same `RenderLock`, on
both Pop (`ActivityManager.cpp:176-182`) and Replace (`:141-149`, child first). Declared last, the
optional is destroyed before every other member, so the teardown runs where the old block ran — the
end of `onExit()` — before other members (OTA's updater, HTTP clients) are destroyed, exactly as
today. In all five `onExit()`s the teardown block is currently the last statement
(`ClockSyncActivity.cpp:33-41`, `OtaUpdateActivity.cpp:89-101`, `CatalogSearchActivity.cpp:76-86`,
`MeetingDownloadActivity.cpp:72-80`, `FontDownloadActivity.cpp:46-54`), so nothing that ran after it
now runs before it.

Why `emplace()` in `onEnter()` rather than a plain member constructed with the activity: activities
are constructed at the launch site (`std::make_unique<...>` in the caller) and can be destroyed
without ever being entered — `pushActivity` drops a pending activity it finds already queued
(`ActivityManager.cpp:253-257`). A plain member would snapshot at construction and could tear down on
a destroy that never followed an entry. An un-emplaced optional does nothing. `std::optional` is
already used in this tree (`src/WifiCredentialStore.h:65-67`); as a lazily-opened RAII member it is
standard C++, not a new repo mechanism.

**A5 — Each activity opens the session where its entry check is today:**

| Activity | Where `emplace()` goes | Replaces |
|---|---|---|
| ClockSync | top of `onEnter()`, before the `status()` check (`:24`) | the `shouldTearDownWifiOnExit` flag (`.h:23`, `.cpp:29`, `:36`) |
| OtaUpdate | top of `onEnter()`, before `WiFi.mode(WIFI_STA)` (`:81`) | block at `:96-100` |
| CatalogSearch | `onEnter()` (`:60`) | block at `:81-85` |
| MeetingDownload | `onEnter()`, before the `status()` check (`:58`) | block at `:75-79` |
| FontDownload | top of `onEnter()`, before `WiFi.mode(WIFI_STA)` (`:41`) | block at `:49-53` |

CatalogSearch opens at entry, not in `ensureWifi`, because "whose Wi-Fi is it" is about the state
when the screen was opened; a connection that appeared later could only be one this activity made.

**A6 — Bring-up is not moved into the helper.** The three bring-up styles (eager STA in OTA and
FontDownload, lazy STA in CatalogSearch, none in ClockSync and MeetingDownload, which leave it to
`WifiSelectionActivity::startWifiScan`/`attemptConnection` at `WifiSelectionActivity.cpp:206`,
`:482`) are each observable (when the radio comes on and power saving goes off), and the issue asks
for the teardown helper only. Folding them in would change when the radio turns on for at least two
activities.

**A7 — `CrossPointWebServerActivity` keeps its own teardown.** It is not named in the issue, and its
block differs: `softAPdisconnect(true)` instead of `disconnect(false)` in AP mode, after stopping DNS
and mDNS (`CrossPointWebServerActivity.cpp:115-127`). Converting it needs an AP-aware session and is
a follow-up. Its comment at `:145-147` ("Its onExit restarts the device once Wi-Fi has been used…")
is already false on this board and stays out of this diff; the PR lists it as a follow-up.

**A8 — The meeting prefetch does not get a session.** It never changes the Wi-Fi mode
(`src/network/MeetingWeekPrefetch.cpp` has no `WiFi` reference) and runs inside
`WifiSelectionActivity::checkConnectionStatus` (`WifiSelectionActivity.cpp:582`) on a radio the
parent brought up; `WifiSelectionActivity::onExit` deliberately leaves the connection to the parent
(`:185-187`). A session there would either do nothing (connected on entry is never true when
selection starts) or tear down the parent's connection before the parent can use it.

**A9 — Behaviour change on unreachable paths only.** OTA, FontDownload, CatalogSearch and
MeetingDownload stop tearing down a connection that was already up when they were entered. No launch
site reaches them with a connection up: they are launched from `SettingsActivity.cpp:322`, `:328`,
`PublicationsActivity.cpp:239`, `MeetingsActivity.cpp:150` and `CrossPointWebServerActivity.cpp:148`,
and every Wi-Fi activity already turns the radio off in its `onExit()`. The web server only offers
Meeting Publications from its mode list, which it shows before a Join succeeds or after one is
cancelled (`:188-190`), never while connected. The PR lists this change anyway.

**A10 — The helper lives in `src/network/`.** It wraps the Wi-Fi driver and nothing UI-specific, and
`src/network` is this task's surface. Its decision is a pure function in a separate header so it can
be host-tested (A11).

**A11 — One `LOG_DBG("WIFI", …)` line per destructor outcome** (session ended / connection left up /
radio never on). Logging only; `LOG_LEVEL=0` in release (`platformio.ini`, `x4pro-gh_release`).

## Architecture

Modelled on `HalPowerManager::Lock` (`lib/hal/HalPowerManager.h:47-64`, `HalPowerManager.cpp:141-164`):
an RAII object that records at construction whether it is the owner and, in its destructor, releases
only what it owns. Non-copyable and non-movable, like `Lock`. The pure core is split out the way
`src/activities/PostedMessageQueue.h` is split from `PostedMessage.cpp` and tested by
`test/posted_message/PostedMessageQueueTest.cpp`.

### `src/network/WifiSessionPolicy.h` (header-only, no Arduino)

```cpp
namespace WifiSessionPolicy {
enum class ExitAction : uint8_t { EndSession, LeaveConnected, Nothing };
// connectedOnEntry: WL_CONNECTED when the session opened.
// radioOnAtExit:    WiFi.getMode() != WIFI_MODE_NULL when it closes.
constexpr ExitAction onExit(bool connectedOnEntry, bool radioOnAtExit);
}
```

| `connectedOnEntry` | `radioOnAtExit` | Result |
|---|---|---|
| true | any | `LeaveConnected` |
| false | true | `EndSession` |
| false | false | `Nothing` |

### `src/network/WifiSession.{h,cpp}`

```cpp
class WifiSession {
 public:
  WifiSession();   // records connectedOnEntry = (WiFi.status() == WL_CONNECTED)
  ~WifiSession();  // switch on WifiSessionPolicy::onExit(connectedOnEntry, WiFi.getMode() != WIFI_MODE_NULL)
  WifiSession(const WifiSession&) = delete;
  WifiSession& operator=(const WifiSession&) = delete;
  WifiSession(WifiSession&&) = delete;
  WifiSession& operator=(WifiSession&&) = delete;

 private:
  bool connectedOnEntry;
};
```

`EndSession` runs the A3 block. The header does not include `<WiFi.h>`; only the `.cpp` does, along
with `SilentRestart.h`.

### Activity changes

For each of the five: add `#include "network/WifiSession.h"` and `#include <optional>` to the header,
add `std::optional<WifiSession> wifiSession;` as the last data member, `wifiSession.emplace()` per
A5, delete the teardown block, and drop `#include "SilentRestart.h"` from the `.cpp` (each includes it
only for that block: `ClockSyncActivity.cpp:13`, `OtaUpdateActivity.cpp:8`,
`CatalogSearchActivity.cpp:22`, `MeetingDownloadActivity.cpp:13`, `FontDownloadActivity.cpp:15`).
`<WiFi.h>` stays where the activity still calls `WiFi.*` for bring-up or status. ClockSync also loses
`shouldTearDownWifiOnExit`; the OTA `onExit()` comment at `:92-95` is rewritten to point at the
session. An `onExit()` left holding only its `Activity::onExit()` call stays as the
override it is today, so the call chain does not change.

## Data and control flow

```
launch site: make_unique<X>()               (no Wi-Fi snapshot yet)
ActivityManager: X::onEnter()
  └─ wifiSession.emplace()                  connectedOnEntry = status()==WL_CONNECTED
  └─ [bring-up as today, or skip if connected]
  … WifiSelectionActivity child, work …
finish() / onGoHome() / goToSleep()
ActivityManager: X::onExit()                (no Wi-Fi code any more)
ActivityManager: destroy X                  (same RenderLock)
  └─ ~optional → ~WifiSession
       LeaveConnected → log, return
       Nothing        → log, return
       EndSession     → disconnect(false); delay(30); silentRestart()
                          X4 Pro: stop SNTP, WiFi.mode(WIFI_OFF), return   (main.cpp:160-173)
                          deep sleep in progress: return                   (main.cpp:176)
```

The OTA success path is unchanged: `SHUTTING_DOWN` calls `ESP.restart()` from `loop()`
(`OtaUpdateActivity.cpp:239-240`), so neither `onExit()` nor the destructor runs.

Home pressed inside `WifiSelectionActivity` (including the prefetch's Home,
`WifiSelectionActivity.cpp:583-586`) is a Replace: the child is exited and destroyed, then the parent
is `onExit()`ed and destroyed from the stack (`ActivityManager.cpp:145-149`), so the parent's session
still ends.

## Error handling

- Nothing in the helper allocates: one `bool` inside a `std::optional` member. No heap, no new task,
  no SD access.
- `WiFi.disconnect()`'s return value is ignored today and stays ignored; teardown has no one to
  report to and the following `WiFi.mode(WIFI_OFF)` inside `silentRestart()` is the step that matters.
- A destructor cannot fail visibly; each outcome is logged (A11).
- The destructor runs under the `RenderLock` the manager already holds for `onExit()`
  (`ActivityManager.cpp:94`, `:140`), as the old block did, so no new lock ordering is introduced.

## Testing strategy

**Host test (TDD, first):** `test/wifi_session/WifiSessionPolicyTest.cpp` covering all four rows of
the table (connected on entry with the radio on and off, not connected with the radio on and off).
Its `CMakeLists.txt` mirrors `test/posted_message/CMakeLists.txt` (`${REPO_ROOT}/src` include,
`crosspoint_test_common`, `GTest::gtest_main`, `gtest_discover_tests`). `test/CMakeLists.txt` is a
shared append point, so the line

    add_subdirectory(wifi_session)

goes in the PR description for the orchestrator to apply, next to `add_subdirectory(posted_message)`
(`test/CMakeLists.txt:79`). The test is written and run red (header missing / wrong result) before
`WifiSessionPolicy.h` exists.

`WifiSession` itself calls the Wi-Fi driver and cannot be host-built (`test/stubs/` has no `WiFi.h`);
its only logic is the policy call, which is what the host test covers.

**Build:** `pio run -e x4pro` through the batch's locked wrapper, plus `./bin/clang-format-fix` over
the whole tree.

**Device (flag for the human tester),** with a dev build and serial logging:

1. Settings → Check for updates, back out at the Wi-Fi list and again after connecting: expect the
   `WIFI` "session ended" log and `MAIN` "WiFi stopped without restart on touch device"
   (`main.cpp:170`), and CPU power saving resuming ("Going to low-power mode",
   `HalPowerManager.cpp:50`).
2. The same for Font download, Sync clock now (Status bar settings), Meetings → download, and Buscar
   after a catalog download. Buscar opened and closed without a network action: no `WIFI` teardown
   (the "radio never on" log).
3. File transfer → Join network → cancel → Meeting Publications → back: radio off on exit, mode list
   returns (the A1 case).
4. Home gesture from inside the Wi-Fi list under OTA: session-ended log still appears.
5. Heap: `ESP.getFreeHeap()` after each exit comparable to before this change.

## Behaviour differences to list in the PR

1. OTA, FontDownload, CatalogSearch and MeetingDownload no longer turn off a connection that was
   already up when they were entered (A9; unreachable from current launch sites).
2. Teardown runs during member destruction immediately after `onExit()` rather than as its last
   statement (A4; no code ran between the two).
3. New `WIFI` debug log lines (A11).
