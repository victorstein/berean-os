## Problem

Five activities each carry their own copy of the same Wi-Fi teardown block, and each decides for
itself whether that block should run:

```cpp
if (WiFi.getMode() != WIFI_MODE_NULL) {
  WiFi.disconnect(false);
  delay(30);
  silentRestart();
}
```

- `ClockSyncActivity.cpp:36-40`, gated by `shouldTearDownWifiOnExit` (`ClockSyncActivity.h:23`,
  set at `ClockSyncActivity.cpp:29`)
- `OtaUpdateActivity.cpp:96-100`
- `CatalogSearchActivity.cpp:81-85`
- `MeetingDownloadActivity.cpp:75-79`
- `FontDownloadActivity.cpp:49-53`

The block is identical in all five. What differs is **whose Wi-Fi it is**: ClockSync leaves alone a
connection it found already up (`ClockSyncActivity.cpp:24-30`), while MeetingDownload
(`MeetingDownloadActivity.cpp:58`) and CatalogSearch (`CatalogSearchActivity.cpp:329`) check for one
on entry and tear it down anyway, and OTA and FontDownload never check.

A sixth site forgets entirely. Settings → System → *Wi-Fi networks*
(`SettingsActivity.cpp:75`) launches a standalone `WifiSelectionActivity` with no result handler
(`SettingsActivity.cpp:308-309`). That activity leaves the connection to its parent
(`WifiSelectionActivity.cpp:185-187`), and `SettingsActivity::onExit()` has no Wi-Fi code
(`SettingsActivity.cpp:178-182`). The radio stays in `WIFI_STA`, connected, after the user leaves
the screen, which keeps CPU power saving off (`lib/hal/HalPowerManager.cpp:39-43`) until some later
network activity happens to turn it off or the device sleeps (`src/main.cpp:282-285`).

On this board `silentRestart()` does not restart: `FREEINK_CAP_TOUCH` is true for the X4 Pro
(`freeink-sdk/libs/hardware/BoardConfig/include/BoardConfig.h:175-178`), so `silentRestart()`
(`main.cpp:175-190`) returns through `finishWifiSessionWithoutRestart()` (`main.cpp:160-173`), which
stops SNTP and sets `WiFi.mode(WIFI_OFF)`. The effective teardown is "drop the association, turn the
radio off".

## Goal

One RAII type, `WifiSession`, that records on entry whether Wi-Fi was already connected and, in its
destructor, leaves Wi-Fi as it found it: a connection that was up on entry and is still up is left
alone; anything else this session turned on is turned off. The five activities and the Settings →
Wi-Fi networks launch hold one; the five lose their hand-written teardown. Apart from the listed
behaviour differences, every path reachable today does what it does now.

## Non-goals

- **Bring-up stays where it is** (A6).
- **`CrossPointWebServerActivity` is not converted** (A7).
- **The meeting prefetch is not changed** (A8).
- **`silentRestart()` itself, `main.cpp`, and the deep-sleep teardown (`main.cpp:282-285`) are not
  changed.**
- `src/network/MeetingWeekCache.*` is not touched (owned by another task in this batch).
- No new user-visible strings, settings, stores or on-disk formats.

## Assumptions (each is a decision the review should attack)

**A1 — "Connected" means `WiFi.status() == WL_CONNECTED`, not `getMode() != NULL`.** Every existing
entry check uses `status()` (`ClockSyncActivity.cpp:24`, `MeetingDownloadActivity.cpp:58`,
`CatalogSearchActivity.cpp:329`). The one reachable case where the two disagree is
`MeetingDownloadActivity` launched from the web server's mode list after a cancelled Join
(`CrossPointWebServerActivity.cpp:148-149`, `:188-190`): the radio is in `WIFI_STA` but not
connected. Today MeetingDownload turns the radio off on exit in that case (`:75-79`); under A1 the
session does not count an unconnected radio as connected, so it still does. `status()` is safe to
call before Wi-Fi was ever started: on the installed core it returns a cached `_status` initialised
to `WL_STOPPED` without a driver call (`framework-arduinoespressif32/libraries/WiFi/src/STA.cpp:231`,
`:241-243`; verified by review 0).

**A2 — "Leave it as found" is judged at both ends.** The session leaves Wi-Fi alone only when it was
connected on entry **and** is still connected at exit. If it was connected on entry but the link was
dropped in between — `WifiSelectionActivity` drops any existing association before it scans or
connects (`startWifiScan`, `WifiSelectionActivity.cpp:206-207`; `attemptConnection`, `:482-483`) and
the user can then back out (`:700-702`, `:717-719`, `:864-865`) — the radio is left in `WIFI_STA`,
unconnected, and the session turns it off. It does not try to reconnect to "restore" the entry
state, and it does not preserve a half-up radio, which would keep power saving off
(`HalPowerManager.cpp:39-43`) for nothing.

**A3 — The teardown body is kept byte-for-byte: `WiFi.disconnect(false); delay(30); silentRestart();`,
guarded by `WiFi.getMode() != WIFI_MODE_NULL`.** Calling `WiFi.mode(WIFI_OFF)` directly would be
equivalent on this board but would drop two things `silentRestart()` owns: the SNTP stop
(`main.cpp:165-167`) and the `deepSleepInProgress` short-circuit (`main.cpp:176`) that `enterDeepSleep`
relies on (`main.cpp:268-271`). The `getMode()` guard keeps an activity that never turned the radio
on (CatalogSearch browsing the cached index, any activity backed out before selection) free of Wi-Fi
calls on exit, as today.

**A4 — In the five activities the session is opened in `onEnter()` and ended by member destruction,
right after `onExit()`.** Each holds `std::optional<WifiSession> wifiSession;` as its **last** data
member and calls `wifiSession.emplace()` at the point its entry check runs today (A5). The
`ActivityManager` calls `onExit()` and then destroys the activity under the same `RenderLock`, on
both Pop (`ActivityManager.cpp:176-182`) and Replace (`:141-149`, child first). No activity in these
hierarchies declares a destructor (`Activity.h:30` is `= default`; verified by review 0), so the
last-declared optional is destroyed right after `onExit()` and before every other member. In all
five `onExit()`s the teardown block is currently the last statement (`ClockSyncActivity.cpp:33-41`,
`OtaUpdateActivity.cpp:89-101`, `CatalogSearchActivity.cpp:76-86`, `MeetingDownloadActivity.cpp:72-80`,
`FontDownloadActivity.cpp:46-54`), so nothing that ran after it now runs before it.

Why `emplace()` rather than a plain member constructed with the activity: activities are constructed
at the launch site and can be destroyed without being entered — `pushActivity` drops a pending
activity it finds already queued (`ActivityManager.cpp:253-257`). An un-emplaced optional does
nothing. `std::optional` is already used in this tree (`src/WifiCredentialStore.h:65-67`).

**A5 — Each of the five opens the session where its entry check is today:**

| Activity | Where `emplace()` goes | Replaces |
|---|---|---|
| ClockSync | top of `onEnter()`, before the `status()` check (`:24`) | the `shouldTearDownWifiOnExit` flag (`.h:23`, `.cpp:29`, `:36`) |
| OtaUpdate | top of `onEnter()`, before `WiFi.mode(WIFI_STA)` (`:81`) | block at `:96-100` |
| CatalogSearch | `onEnter()` (`:60`) | block at `:81-85` |
| MeetingDownload | `onEnter()`, before the `status()` check (`:58`) | block at `:75-79` |
| FontDownload | top of `onEnter()`, before `WiFi.mode(WIFI_STA)` (`:41`) | block at `:49-53` |

CatalogSearch opens at entry, not in `ensureWifi`, because "whose Wi-Fi is it" is about the state
when the screen was opened; a connection that appears later could only be one this activity made.

**A6 — Bring-up is not moved into the helper.** The three bring-up styles (eager STA in OTA
`:81` and FontDownload `:41`; lazy STA in CatalogSearch `:333`; none in ClockSync and
MeetingDownload, which leave it to `WifiSelectionActivity::startWifiScan`/`attemptConnection` at
`WifiSelectionActivity.cpp:206`, `:482`) each decide when the radio comes on and power saving goes
off. The issue asks for the teardown helper; folding bring-up in would change that timing for at
least two activities.

**A7 — `CrossPointWebServerActivity` keeps its own teardown.** It has its own lifecycle-scoped
teardown already, and its block differs: `softAPdisconnect(true)` instead of `disconnect(false)` in
AP mode, after stopping DNS and mDNS (`CrossPointWebServerActivity.cpp:115-127`). Converting it needs
an AP-aware session and is a follow-up. Two comments claim a reboot that does not happen on this
board and stay out of this diff, listed as PR follow-ups: `CrossPointWebServerActivity.cpp:145-147`
and `SettingsActivity.cpp:313-314`.

**A8 — The meeting prefetch does not get a session.** It never changes the Wi-Fi mode
(`src/network/MeetingWeekPrefetch.cpp` has no `WiFi` reference) and runs inside
`WifiSelectionActivity::checkConnectionStatus` (`WifiSelectionActivity.cpp:582`) on a radio its
parent's session owns — including, after this change, Settings → Wi-Fi networks' (A12).

**A9 — With A12 in place, no launch site enters the five with a connection up; the
connected-on-entry branch is defensive.** Review 0 showed the pass-0 claim was wrong only because of
Settings → Wi-Fi networks. After A12, every screen that can bring Wi-Fi up ends it on the way out:
the five via their session, Settings → Wi-Fi networks via A12, and the web server via its own
teardown (`CrossPointWebServerActivity.cpp:119-127`). The web server offers Meeting Publications only
from its mode list, shown before a Join succeeds or after one is cancelled (`:95-107`, `:188-190`),
never while connected. The launch sites are `StatusBarSettingsActivity.cpp:183` (ClockSync),
`SettingsActivity.cpp:322`, `:328` (OTA, FontDownload), `PublicationsActivity.cpp:239`
(CatalogSearch), and `MeetingsActivity.cpp:150`, `CrossPointWebServerActivity.cpp:148`
(MeetingDownload). The branch is kept because it is the issue's stated semantics and ClockSync's
existing behaviour (`ClockSyncActivity.cpp:24-30`).

**A10 — The helper lives in `src/network/`.** It wraps the Wi-Fi driver and nothing UI-specific.
Its decision is a pure function in a separate header so it can be host-tested (Testing).

**A11 — One `LOG_DBG("WIFI", …)` line per destructor outcome** (session ended / connection left up /
radio never on). Logging only; `x4pro-gh_release` builds with `LOG_LEVEL=0` (`platformio.ini:190`).

**A12 — Settings → Wi-Fi networks holds a session for the life of that launch (decision d1).**
`SettingsActivity` gets `std::optional<WifiSession> wifiSession;` as its last data member (after
`rowItems_`, `SettingsActivity.h:173`). The `SettingAction::Network` case
(`SettingsActivity.cpp:308-309`) calls `wifiSession.emplace()` immediately before
`startActivityForResult`, and replaces the `nullptr` result handler with one that calls
`wifiSession.reset()`. Paths:

- Back or a completed connect: `WifiSelectionActivity` finishes, the manager pops it (onExit +
  destroy, `ActivityManager.cpp:103-106`), then calls Settings' handler (`:118-126`), which ends the
  session: radio on, not connected-on-entry → `EndSession`.
- Home or sleep from inside the picker: a Replace; the picker is exited and destroyed, then Settings
  is `onExit()`ed and destroyed from the stack (`:145-149`), destroying the still-engaged optional.
- The handler runs with the render lock released (`ActivityManager.cpp:126`), unlike the five, whose
  teardown runs under it. On this board the teardown draws nothing (`main.cpp:160-173` returns before
  `GUI.drawPopup`), so there is nothing for the lock to protect.

Why the result handler and not Settings' own exit: the leak this closes is the radio staying on
while the user is still in Settings or anywhere after it. Ending the session when the picker returns
is the earliest point nothing on this path needs the link — the picker's own meeting prefetch
(`WifiSelectionActivity` is launched with the default `meetingPrefetch=true`,
`WifiSelectionActivity.h:169-170`) has already run inside the picker before it finishes
(`WifiSelectionActivity.cpp:582`).

## Architecture

Modelled on `HalPowerManager::Lock` (`lib/hal/HalPowerManager.h:47-64`, `HalPowerManager.cpp:141-164`):
an RAII object that records at construction whether it owns something and, in its destructor,
releases only what it owns; non-copyable and non-movable. The pure core is split out the way
`src/activities/PostedMessageQueue.h` is split from `PostedMessage.cpp` and tested by
`test/posted_message/PostedMessageQueueTest.cpp`.

### `src/network/WifiSessionPolicy.h` (header-only, no Arduino)

```cpp
namespace WifiSessionPolicy {
enum class ExitAction : uint8_t { EndSession, LeaveConnected, Nothing };
// connectedOnEntry: WL_CONNECTED when the session opened.
// connectedAtExit:  WL_CONNECTED when it closes.
// radioOnAtExit:    WiFi.getMode() != WIFI_MODE_NULL when it closes.
constexpr ExitAction onExit(bool connectedOnEntry, bool connectedAtExit, bool radioOnAtExit);
}
```

Rule: `LeaveConnected` if `connectedOnEntry && connectedAtExit`; otherwise `EndSession` if
`radioOnAtExit`; otherwise `Nothing`.

| # | `connectedOnEntry` | `connectedAtExit` | `radioOnAtExit` | Result |
|---|---|---|---|---|
| 1 | false | false | false | `Nothing` |
| 2 | false | false | true | `EndSession` |
| 3 | false | true | false | `Nothing` |
| 4 | false | true | true | `EndSession` |
| 5 | true | false | false | `Nothing` |
| 6 | true | false | true | `EndSession` |
| 7 | true | true | false | `LeaveConnected` |
| 8 | true | true | true | `LeaveConnected` |

Rows 3 and 7 (connected with the radio off) cannot occur on the device; the rule still defines them
so the function is total.

### `src/network/WifiSession.{h,cpp}`

```cpp
class WifiSession {
 public:
  WifiSession();   // connectedOnEntry = (WiFi.status() == WL_CONNECTED)
  ~WifiSession();  // switch on WifiSessionPolicy::onExit(connectedOnEntry,
                   //   WiFi.status() == WL_CONNECTED, WiFi.getMode() != WIFI_MODE_NULL)
  WifiSession(const WifiSession&) = delete;
  WifiSession& operator=(const WifiSession&) = delete;
  WifiSession(WifiSession&&) = delete;
  WifiSession& operator=(WifiSession&&) = delete;

 private:
  bool connectedOnEntry;
};
```

`EndSession` runs the A3 block. The header does not include `<WiFi.h>`; only the `.cpp` does, along
with `SilentRestart.h`.

only for that block: `ClockSyncActivity.cpp:13`, `OtaUpdateActivity.cpp:8`,

## Data and control flow

The five:

```
launch site: make_unique<X>()               (no Wi-Fi snapshot yet)
ActivityManager: X::onEnter()
  └─ wifiSession.emplace()                  connectedOnEntry = status()==WL_CONNECTED
  └─ [bring-up as today, or skip if connected]
  … WifiSelectionActivity child, work …
finish() / onGoHome() / goToSleep()
ActivityManager: X::onExit()                (no Wi-Fi code any more)
ActivityManager: destroy X                  (same RenderLock)
  └─ ~optional → ~WifiSession → policy(entry, status()==WL_CONNECTED, getMode()!=NULL)
       LeaveConnected → log, return
       Nothing        → log, return
       EndSession     → disconnect(false); delay(30); silentRestart()
                          X4 Pro: stop SNTP, WiFi.mode(WIFI_OFF), return   (main.cpp:160-173)
                          deep sleep in progress: return                   (main.cpp:176)
```

Settings → Wi-Fi networks:

```
SettingsActivity: case Network
  └─ wifiSession.emplace(); startActivityForResult(WifiSelectionActivity, handler)
  … picker connects (and may prefetch) or is backed out …
Pop: picker onExit + destroy → Settings handler → wifiSession.reset() → ~WifiSession (as above)
Replace (Home/sleep): picker onExit + destroy → Settings onExit + destroy → ~WifiSession
```

The OTA success path is unchanged: `SHUTTING_DOWN` calls `ESP.restart()` from `loop()`
(`OtaUpdateActivity.cpp:239-240`), so neither `onExit()` nor the destructor runs.

Home pressed inside a picker launched by one of the five (including the prefetch's Home,
`WifiSelectionActivity.cpp:582-587`) is a Replace, so the parent's session still ends.

## Error handling

- Nothing in the helper allocates: one `bool` inside a `std::optional` member. No heap, no new task,
  no SD access.
- `WiFi.disconnect()`'s return value is ignored today and stays ignored; the following
  `WiFi.mode(WIFI_OFF)` inside `silentRestart()` is the step that matters.
- A destructor cannot fail visibly; each outcome is logged (A11).
- Locking: the five's teardown runs under the `RenderLock` the manager already holds for `onExit()`
  (`ActivityManager.cpp:94`, `:141`), as the old block did. The Settings handler runs unlocked (A12).

**Device (flag for the human tester),** dev build with serial logging:

5. Home gesture from inside the Wi-Fi list under OTA: the session-ended log still appears.
6. Heap: `ESP.getFreeHeap()` after each exit comparable to before this change.

## Behaviour differences to list in the PR

1. **Settings → Wi-Fi networks now turns the radio off when the picker returns** (A12, decision d1).
   Before, the device stayed connected with CPU power saving off until a later network screen or
   sleep. The next network screen reconnects from saved credentials, costing a few seconds.
2. The five no longer turn off a connection that was up on entry and is still up at exit (A2, A9).
   After difference 1 no launch site reaches that state.
3. Teardown in the five runs during member destruction immediately after `onExit()` rather than as
   its last statement (A4; no code ran between the two).
4. New `WIFI` debug log lines (A11).

Follow-ups (not in this diff): convert `CrossPointWebServerActivity` to an AP-aware session (A7);
correct the false "reboots" comments at `CrossPointWebServerActivity.cpp:145-147` and
`SettingsActivity.cpp:313-314`.
