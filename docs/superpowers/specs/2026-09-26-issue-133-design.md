# Covering a refused future-version store file that arrives through `.tmp` adoption

Issue #133. Only test code changes. Research: `docs/superpowers/research/2026-09-26-issue-133-research.md`.
Modelled on `test/persistable_store/PersistableStoreTest.cpp`, in particular
`ARefusedLoadBlocksEverySaveAndLeavesTheFileUntouched` (`:62-73`) and
`AMissingFileLiftsTheRefusal` (`:75-84`).

## Problem

Two separate PRs built two properties of `PersistableStore<T>`:

- **#101:** a load that `fromJson` refuses blocks every later save
  (`lib/Serialization/PersistableStore.h:152-157`, `:201`, `:223`).
- **#98:** one adoption path serves both loaders. It promotes a parseable `<path>.tmp` when the
  primary file is missing, and it keeps an unusable `.tmp` on the card
  (`lib/Serialization/PersistableStore.cpp:70-97`, `:101-113`;
  `lib/Serialization/TempAdoption.h:26-31`).

Nothing tests them together. The CRTP suite, `test/persistable_store/PersistableStoreTest.cpp:62-113`,
only ever puts a file at the primary path. The adoption suites in `test/storage_io/`
(`AdoptingReadTest.cpp`, `LoadAdoptingTest.cpp`) call the base-class readers directly, so they
never go through `loadFromFile` or its `loadRefused` flag.

The interaction matters because the order of operations is the safety argument. Promotion
happens inside the read (`PersistableStore.cpp:84-95`), before `fromJson` sees the document
(`PersistableStore.h:222`). So a future-format `.tmp` becomes the primary file first, and only
the refusal flag stops the next save from overwriting it. If that ordering or the flag
regressed, the only surviving copy of a newer build's data would be destroyed, and no test would
notice.

## Goal

Add two tests to `PersistableStoreTest.cpp` that run the real template and the real
`PersistableStore.cpp` against the in-memory `HalStorage` fake. Each asserts return values and
on-disk bytes:

1. **Future-version `.tmp`, primary missing.**
   - The load promotes the `.tmp` and refuses the document.
   - The next saves are refused.
   - The promoted primary survives byte for byte, and no `.tmp` reappears.
2. **Garbage `.tmp`, primary missing.**
   - The load reports nothing usable and leaves the `.tmp` on the card.
   - The load clears an earlier refusal.
   - A later save succeeds and writes the expected document.

## Non-goals

- **Any production change.** The research probe showed both cases pass today (research note,
  "Probe: both cases already pass"). If either test fails during implementation, stop and raise
  `hpipe decide` with the failing assertion, as the issue requires. Do not patch
  `lib/Serialization`.
- **The rename-failure path for a refused `.tmp`.** In that path promotion fails, the document
  is still used, and the `.tmp` survives (`PersistableStore.cpp:89-94`). It is already covered at
  the base-reader level by `AdoptingReadTest.AFailedPromotionStillReturnsTheDocumentAndKeepsTheTemp`
  (`test/storage_io/AdoptingReadTest.cpp:52-59`). Issue #133 names only the two cases above.
- **`loadAdopting` stores.** `LoadAdoptingTest.cpp` covers them. This issue is about the CRTP path.
- **CMake changes.** The suite already links `PersistableStore.cpp` and `HalStorageFake.cpp`
  (`test/persistable_store/CMakeLists.txt:3-8`). Nothing is added to `test/CMakeLists.txt`.
- **Unreadable (as opposed to unparseable) `.tmp`.** Both return `tempParsed == false`
  (`PersistableStore.cpp:80`) and reach the same `KeepTempReportEmpty` arm
  (`TempAdoption.h:46`), so a garbage `.tmp` covers that arm.

## Assumptions (each is a decision for the review to attack)

- **A-1: One file changes: `test/persistable_store/PersistableStoreTest.cpp`.** The two tests
  go into the existing `PersistableStoreGuard` fixture (`:50-58`). They reuse `ProbeStore`,
  `PATH`, `TMP_PATH`, `NEWER` and `bytesOn` (`:16-46`). There is no new fixture, helper file or
  store type.
- **A-2: The header comment is updated.** Lines `:1-3` currently describe the file as covering
  only #101's save guard. After this change it also covers how that guard composes with #98's
  `.tmp` adoption, so the comment gains one clause saying so. That is required for it to stay
  true, not decoration.
- **A-3: The future-version test asserts the card at two points:**
  - After the load: the primary is `NEWER` and the `.tmp` is absent. This proves the load
    promoted the file.
  - After the refused save: both are unchanged.

  The issue only requires the second check. The first is added because without it, a regression
  where promotion was skipped would leave the primary absent after the load. The second check
  alone would still fail in that case, but it would point at the save rather than the load.
  Checking both locates the fault.
- **A-4: The future-version test refuses both `saveToFileAtomic()` and `saveToFile()`.** This
  mirrors `ARefusedLoadBlocksEverySaveAndLeavesTheFileUntouched` (`:69-70`). The issue names only
  `saveToFileAtomic()`, but the guard is on both (`PersistableStore.h:183`, `:201`), and the
  existing test's contract is "every save".
- **A-5: The future-version test sets `value = 42` before saving and checks that `value == 0`
  after the refused load.** This mirrors `:66` and `:68`. A changed in-memory value means an
  unblocked save would write different bytes, so a leaked write cannot compare equal to `NEWER`
  by accident.
- **A-6: The garbage test starts from an active refusal.** It first seeds `NEWER` at `PATH` and
  asserts that `loadFromFile()` is false. That sets `loadRefused`. It then removes `PATH` and
  seeds the garbage `.tmp`.

  Without this step the test is vacuous for the "clears `loadRefused`" claim. The fixture's
  `SetUp` has already cleared the flag (`:54`). Suppose the adopting read regressed to report
  the `.tmp`'s `ParseError` instead of `Missing`. `loadRefusedAfter` would then keep the flag's
  previous value (`FormatVersion.h:27-30`). That value would be `false`, so the save would still
  succeed and the regression would pass. Starting from `true` makes the `Missing → false` arm
  (`FormatVersion.h:25-26`) the only way the save can succeed. The sequence mirrors
  `AMissingFileLiftsTheRefusal` (`:75-84`), which does the same with no `.tmp`.
- **A-7: The garbage bytes are a torn prefix of a valid document, `{"v":1,"val`.** An interrupted
  `.tmp` write actually leaves this shape (`PersistableStore.cpp:31` writes the whole document
  through a single `writeFile`). `AdoptingReadTest.cpp:62` uses the same kind of prefix. The
  suite's existing `"not json"` would also exercise the arm; the torn prefix is chosen because
  it states the scenario. It is a named constant, `TORN`, beside `NEWER`.
- **A-8: The garbage test asserts the card at two points:**
  - After the load: the `.tmp` still holds `TORN` and `PATH` is absent. This is the issue's
    required assertion; `KeepTempReportEmpty` renames nothing.
  - After the save: `PATH` holds exactly `{"v":1,"value":9}` and the `.tmp` is absent.

  The second point relies on the atomic write replacing the `.tmp`: the fake's `writeFile`
  erases and then writes (`test/stubs/HalStorageFake.cpp:128-133`), and the rename then moves
  it (`PersistableStore.cpp:31-43`). That is the documented contract behind
  `TempAdoption.h:26-29` ("the next save truncates it"). Asserting it pins the stated reason the
  load may leave garbage behind.
- **A-9: Test names follow the suite's sentence style** (`:62`, `:75`, `:86`):
  - `AFutureVersionTempIsPromotedThenRefusedAndNeverOverwritten`
  - `AGarbageTempIsKeptByTheLoadAndStillLiftsTheRefusal`
- **A-10: The TDD red step is shown by temporary, uncommitted mutation of production code.**
  The behaviour already exists, so a new test cannot be red against an unchanged tree. Each
  mutation below is applied alone and the suite is run. The named assertion must fail. The
  mutation is then reverted with `git checkout -- <file>`, and `git status --short` must show
  only the test file. The failing output goes in the PR description. No mutation is committed.
  This is the one pattern here the repo does not already establish. It is a verification
  technique, not a code pattern, so it does not need a decision.

## Architecture

There is no new component. The tests sit on top of three existing layers:

```
PersistableStoreGuard (gtest fixture, PersistableStoreTest.cpp:50-58)
  └─ ProbeStore : PersistableStore<ProbeStore>   FORMAT_VERSION = 1   (:16-37)
       └─ PersistableStoreBase                   real PersistableStore.cpp
            └─ Storage                           in-memory fake (test/stubs/HalStorageFake.cpp)
```

`ProbeStore::fromJson` refuses any `"v"` above 1 through `persist::isKnownFormatVersion`
(`:31-36`; `FormatVersion.h:13-15`), so `NEWER = {"v":2,"value":7}` (`:41`) is a future-format
document.

## Error handling

Only test code changes, so there is no runtime error path to design. Two process rules apply:

- **A test fails against the unmodified tree.** Stop and raise `hpipe decide --task t2` with the
  failing assertion and its output. Do not change production code under this issue.
- **A mutation in A-10 fails to turn its target assertion red.** That means the test does not
  guard what it claims to. Fix the test, not the mutation, before committing.

## Testing strategy

### TDD order

1. Add test 1. Build and run it against the unmodified tree. It is expected to pass, as the
   research probe showed.
2. Apply mutation M1 and confirm test 1 fails at the step-4/5 assertions, then revert. Do the
   same with M4 and the step-3 assertions.
3. Add test 2 and run it green. Apply M2 and M3 in turn, confirm the named failures, and revert
   each.
4. Run the whole suite and confirm the existing 5 tests plus the 2 new ones pass (7 total).
