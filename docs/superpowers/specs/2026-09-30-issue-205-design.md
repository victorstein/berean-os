# Issue #205 design — tag chip row in Highlights

Status: revised after spec review pass 0 (`docs/superpowers/reviews/issue-205-spec-review-0.md`,
CLEAR with 2 MAJOR, 8 MINOR — all accepted; see "Changes from review pass 0" at the end). Research:
`docs/superpowers/research/2026-09-30-issue-205-research.md`. Base `67eaaf1e`.

## Problem

The Highlights screen filters by tag through one list row, "Filter by tag / <current>", which opens
a full-screen picker (`HighlightsActivity.cpp:84-89`, `:117-143`; `TagFilterActivity.cpp:27-67`).
To browse by tag you open the picker, pick, come back, and repeat. Nothing on the screen shows how
many passages carry each tag.

## Goal

Replace that row with a wrapping row of tag chips at the top of the list: `All 37`, `hope 12`,
`ministry 9`, …, `Unlabelled 4`, and `…` when they do not fit on two lines. Tapping a chip filters
the list, and the selected chip is inverted. Tapping `…` opens today's `TagFilterActivity`.

Acceptance criteria from the issue:

1. The counts match the passages in the list.
2. Filtering by chip matches today's filter behaviour. The counting and overflow logic has a host test.
3. It works with 0 tags and with more tags than fit on two lines.
4. Rows use #194's compact metrics.

## Non-goals

- **No change to the passage rows.** Their content, the value slot, long-press actions, delete and
  retag stay as they are (`HighlightsActivity.cpp:78-115`, `:182-415`). They already get their
  height from #194's path: `syncListViewport` → `ListRowHeight::resolve`
  (`UiListActivity.cpp:124-140`, `ListRowHeight.h:19-28`). Criterion 4 is met by keeping that
  path, not by a new metric. See A11.
- **No change to `TagFilterActivity`**, its row mapping (`TagRowMapping.h:28-42`) or its retire
  gesture (`TagFilterActivity.cpp:83-129`).
- No screen rename, and no Home entry for Tags. Those belong to the overhaul's Home phase (see the
  mockup's phase table).
- No store, file-format, network or HAL change. No new translation key (see A9).
- No cross-publication list: the list is still the open publication's (`HighlightsActivity.h:16-21`).

## Assumptions (each is a reviewable decision)

- **A1 — Chip set and order.** The order is `All`, then every active tag in palette allocation
  order (`STUDY.activeTags()`, `StudyStore.cpp:129-133`, which is `TagPalette::activeIds()` order,
  `TagPalette.cpp:57-63`), then `Unlabelled`, then `…` if there is overflow. This matches the
  mockup, which is not sorted by count (`name 4` before `trust 5`) and puts Unlabelled last. It
  differs from the picker, which puts Unlabelled second (`TagRowMapping.h:30-31`). Sorting by count
  was rejected because a chip would jump position after a retag. **Consequence, stated for the
  owner's device check:** because A4 drops chips from the end, `Unlabelled` is always the first
  chip hidden behind `…` whenever the row overflows; it stays reachable through the picker, which
  lists it second.
- **A2 — Zero-count chips are hidden.** A tag chip, or the `Unlabelled` chip, is drawn only when its
  count is > 0 **or** it is the active filter. The palette is global, so tags from other
  publications are active here with 0 passages (`HighlightsActivity.h:18-21`). Drawing them would
  fill two lines with filters that match nothing. The "or active filter" clause means a filter that
  drops to 0 (its last passage was retagged) still shows as inverted, so the user can see why the
  list is empty. `All` is always drawn.
- **A3 — Count definition.** `All` = `STUDY.passages().size()`. A chip's count is the number of
  passages whose `tags` contain that id. This is exactly the predicate `rebuildVisibleIndices`
  filters on (`HighlightsActivity.cpp:49-52`). `Unlabelled` uses the same predicate with
  `study::UNLABELLED`, which is correct because normalisation stores UNLABELLED explicitly and only
  alone (`PassageDoc.cpp:15-26`, `:202-205`). A passage with two tags counts under both, so the tag
  counts can sum to more than `All`. The filter predicate becomes one free function,
  `TagChips::passageMatches`, that `rebuildVisibleIndices` calls. The counter does **not** call it:
  it walks each passage's carried ids once through a sorted id→slot lookup. The two agree because
  `normaliseTags` removes duplicate ids on every write and load path (`PassageDoc.cpp:17-27`, and
  its callers at `:151, :197, :329`). Criterion 1 is therefore guaranteed by the **equivalence host
  test** (Testing strategy), not by shared code.
- **A4 — Overflow rule.** Chips are laid out greedily left to right and wrap onto at most **two**
  lines. If every chip fits, no `…` is drawn. If not, `…` takes the last slot on line 2, and chips
  are dropped from the end of line 2 until `…` fits. Chips that do not fit are reachable only
  through `…` → `TagFilterActivity`. This reconciles the issue's "overflow onto a second line" with
  "more tags than fit on two lines" and the mockup (research, "Open questions").
- **A5 — Selected chip hidden by overflow.** If the active filter's chip is not placed, `…` is
  drawn inverted, so the screen always shows where the filter lives. Rejected alternative: moving
  the selected chip forward into view. That reorders chips as you filter, which contradicts A1.
- **A6 — Hard cap.** At most `MAX_CHIPS = 24` chips are placed, plus `…`. Past the cap, the
  overflow rule applies even if width remains. Reason: `UiAppHost::MAX_INTERACTIONS = 64`, and hits
  past it are dropped silently (`UiAppHost.h:24-37`). 25 chip hits plus the visible passage rows
  (fewer than 15 at any row height on this panel) stays under 64. `NumberGrid::MAX_CELLS` caps its
  grid for the same reason (`NumberGridLayout.h:15-18`).
- **A7 — Tapping a chip.** A tap on a tag, `Unlabelled` or `All` chip sets `filterTagId_`
  (`nullopt` for All, `study::UNLABELLED` for Unlabelled, the id otherwise; the same values
  `openTagFilter` stores at `HighlightsActivity.cpp:126-130`). It then rebuilds under `RenderLock`
  and moves the selection to ring position 0 (the chip row), as `openTagFilter` does with
  `moveSelectionTo(0)` (`:141`). Tapping the chip that is already selected does nothing: no rebuild
  and no refresh. Tapping `…` calls the existing `openTagFilter()` unchanged, including its
  always-rebuild and `dropRetiredFilter` handling (`:133-141`).
- **A8 — No long-press on chips.** Chips register `InputTouch` only. The picker's long-press
  retires a tag across every publication (`TagFilterActivity.h:17-20`). Putting that on a chip
  that a quick tap filters by would put a device-wide destructive action one hold away from a
  browse gesture.
- **A9 — Labels.** `All` and `Unlabelled` reuse `STR_TAG_FILTER_ALL` and `STR_TAG_UNLABELLED`
  (`english.yaml:389-390`), and a tag chip uses the palette name. The label is `"<name> <count>"`,
  built with `snprintf` into a fixed buffer. The count is a number, not a word, so it needs no
  key. The overflow chip is the SDK's own truncation glyph, `fui::TEXT_ELLIPSIS`
  (`FreeInkUICore.h:713-714`), which the UI font has (`ubuntu_10_regular.h:2557`). It is a symbol,
  as it is when the SDK appends it to truncated text, so it gets no translation key.
- **A10 — Physical buttons keep reaching the filter.** The X4 Pro has Left/Right buttons and an
  optional Power-as-Confirm (`MappedInputManager.cpp:247-251, 259, 267`). Today, button users reach
  the filter because row 0 is in the navigation ring (`HighlightsActivity.cpp:438-456`). This
  design keeps that: ring position 0 is the chip row and 1..N are the passages, and Confirm on
  position 0 opens `TagFilterActivity`, which is today's row-0 behaviour. The ring mirrors
  `UiTabListActivity`'s "position 0 = tab bar, 1..N = rows" (`UiTabListActivity.cpp:44-72`,
  `:74-106`; `UiTabListActivity.h:7-18`). The chip band gets a 2 px black outline only when
  position 0 has focus **and** that focus was reached by a button step (a `buttonFocus_` flag set
  in `navigateButtons`, cleared on any routed touch). Ring 0 is also the default on entry
  (`UiListActivity.cpp:22`) and after every chip tap (A7), so an unconditional outline would be on
  screen nearly always on this touch-first device, which the mockup does not show. No dither is
  drawn under text. Rejected alternative: making the chips touch-only, which would take filtering
  away from button users. **Button semantics:** a release steps the ring by one, and a continuous
  hold jumps by `pageRows()`; both go through `moveRingTo`. The ring size is `listCount()` (A-arch
  keeps `listCount()` = rows + 1), **not** `listCount() + 1` as in the tab version
  (`UiTabListActivity.cpp:66`).
- **A11 — Metrics.** Chips use the small text style (`screen.theme().smallText`), the same one the
  tab bar's label-hugging pills use (`UiTabListActivity.cpp:142`). Chip height is the small line
  height plus vertical padding. The gap between chips and between lines is
  `screen.theme().spaceSm`. Every chip is at least `chipHeight` wide, so `…` and short labels are
  never narrower than they are tall. The list below keeps `hasSubtitle=true` and the resolved row
  height, unchanged.
- **A11b — Hit rects tile; `minTouchSize` expansion is switched off for chips.** `Screen::button(props,
  rect)` forces `minTouchSize` to the theme token (`FreeInkApp.h:223-230`), and
  `ensureMinTouchRect` grows the hit rect symmetrically to it (`button.h:37-41`,
  `FreeInkUI.cpp:821-830`). That token is at least 44 px (`FreeInkUICore.h:637`,
  `FreeInkUI.cpp:117`), which is more than the chip line pitch. A line-2 chip's hit rect would then
  cover the bottom of the chip above it, and it wins because `findTouch` scans last-registered-first
  (`FreeInkUICore.h:1165-1178`). So chips are drawn with **`fui::button(screen.frame(), rect,
  props)` directly**, as `buildTabBar` calls `fui::tabBar(screen.frame(), …)`
  (`UiTabListActivity.cpp:189`). They get `props.minTouchSize = 0`, text and styles set
  explicitly (the direct call does not theme them), and `hitPadding` of half the gap on every edge
  that faces another chip. The hit bands then tile the band with no overlap. The tap target per
  line is `chipHeight + gap`: smaller than the 44 px token, accepted to fit two lines in the band
  the mockup draws (38 px pitch). This is flagged for the device check.
- **A12 — Empty publication.** With zero passages the screen is unchanged: `STR_NO_HIGHLIGHTS`, no
  chip row (`HighlightsActivity.cpp:477-482`). With passages but zero active tags, the row is
  `All n` plus `Unlabelled m`, with `m ≤ n`, and no `…`. They are not necessarily equal: `retireTag`
  strips a retired id only from the open publication's passages (`StudyStore.cpp:232-240`,
  `PassageDoc.cpp:199-205`). A passage in another publication can therefore keep a retired id as
  its only tag. It then counts under `All` and under no chip, and it is reached through `All`.
- **A13 — Selected style.** Inverted means a black fill, white text and bold, with `focused` and
  `active` copied from `selected` so a tap flash keeps the pill. This mirrors
  `UiTabListActivity.cpp:160-182`, first branch. Unselected: white fill, 1 px black border, black
  text. Both are solid; no `Paint::dither`. Bold is a `TextStyle` field, not a per-state paint
  (`FreeInkUICore.h:534-544`, `button.h:77-80`), and the bold face has different advances. So
  **every candidate is measured with the bold style**, whether selected or not, and unselected
  chips draw regular text inside that width. Chip widths, and therefore the layout, do not depend on
  which chip is selected: selecting a chip never reflows the row or pushes it behind `…`.

## Architecture

### New header: `src/activities/reader/TagChipRow.h` (pure, host-tested)

Modelled on `src/activities/reader/NumberGridLayout.h`: plain data in and out, free of FreeInkUI,
Arduino and GfxRenderer, so `test/tag_rows` can exercise it. It includes only
`<StudyStore/TagPalette.h>` for `study::TagId`. Every non-template function is defined `inline` in
the header, as `NumberGridLayout.h:34` does; there is no `.cpp`.

```cpp
namespace TagChips {
constexpr int MAX_CHIPS = 24;   // A6
constexpr int MAX_LINES = 2;    // A4

// The filter predicate HighlightsActivity::rebuildVisibleIndices calls. count() agrees with it via
// the dedup invariant, pinned by the equivalence test (A3).
inline bool passageMatches(const std::vector<study::TagId>& tags, std::optional<study::TagId> filter);

struct Counts {
  size_t all = 0;
  size_t unlabelled = 0;
  std::vector<uint16_t> perTag;   // aligned with the activeIds passed in
};
// One pass over the passages. Lookup of a carried id goes through a sorted (raw id, slot)
// copy of activeIds, so the cost is O(P * tags-per-passage * log T), not O(P * T).
template <typename Passages>
Counts count(const Passages& passages, const std::vector<study::TagId>& activeIds);

enum class Kind : uint8_t { All, Tag, Unlabelled, More };
struct Chip { Kind kind; int tagSlot; int width; };        // tagSlot: index into activeIds, -1 otherwise
struct Placed { int chip; int line; int x; int width; };   // chip: index into the input, -1 for "…"
struct Layout {
  Placed placed[MAX_CHIPS + 1];
  int placedCount = 0;
  int lines = 0;
  bool overflow = false;          // "…" was placed
};
// Greedy wrap into MAX_LINES lines of lineWidth, gap between chips; applies A4 and A6.
// A chip wider than lineWidth is clamped to lineWidth (its text is ellipsised by the target).
inline Layout layout(const Chip* chips, int count, int moreWidth, int lineWidth, int gap);
}
```

The `Passages` template argument lets the test pass a vector of a small struct with a `tags`
member, and lets the device pass `STUDY.passages()`. The helper does not depend on
`TaggedPassage.h` or StudyStore.

Which chips are *candidates* (A2) is decided in the activity, from `Counts` plus `filterTagId_`,
before `layout()` runs. `layout()` sees only widths. Whether the selected chip was placed (A5) is
answered by scanning `placed`.

### `HighlightsActivity` changes

Nearest examples: `UiTabListActivity` for the ring (A10) and inverted pills (A13), and
`BibleSearchActivity.cpp:102-104, 755-781` for extra actions and buttons at explicit rects.

- **State**, rebuilt with the rows in `rebuildRowItems()` (called only on data changes,
  `HighlightsActivity.h:104-108`):
  - **Locals of `rebuildRowItems`, freed on return:** the `STUDY.activeTags()` snapshot and the
    `TagChips::Counts`. Nothing reads them after the chips are built, because each chip copies its
    label and id.
  - `std::vector<ChipEntry> chips_`: the candidate chips in A1 order, **at most `MAX_CHIPS + 1`**
    (decided; this was O1). Each entry holds a kind, a tag id and a `char label[40]` (24-byte
    name max, `TagPalette.h:39`, plus a space, up to 10 digits and NUL). The vector is reserved to
    exactly `MAX_CHIPS + 1` (CLAUDE.md resource rule 7). `layout()` can never place more than
    `MAX_CHIPS`, so the last slot is enough to trigger overflow. A `bool moreCandidates_` records
    that further candidates exist past the bound, which also forces `…` (A4).
  - `TagChips::Chip chipInputs_[MAX_CHIPS + 1]` and `TagChips::Layout chipLayout_` are members
    filled in `buildScreen`, not locals, so the render task's locals stay under 256 B (resource
    rule 1).
  - `bool buttonFocus_` (A10).
- **The filter row leaves `rowItems_`.** `rowItems_` now holds passages only. Each keeps
  `actionValue = i + 1`, which is the ring position (unchanged, `HighlightsActivity.cpp:112`).
  `listCount()` stays `visibleIndices_.size() + 1` (`:38`), now meaning the ring size, so
  `rowActionTrampoline`'s bound (`UiListActivity.cpp:33-36`) and `activateIndex`/`onRowLongPress`
  index arithmetic (`HighlightsActivity.cpp:166-188`) keep working unchanged: index 0 opens the
  picker, index k > 0 is `visibleIndices_[k-1]`.
- **Viewport sync.** A private `syncRingViewport(screen, props)` mirrors
  `UiTabListActivity::syncTabListViewport` (`UiTabListActivity.cpp:74-106`): the row count is
  `visibleIndices_.size()`, and `props.selectedIndex = nav.selected - 1`, so position 0 highlights
  no row. It clamps with `n.scrollBy(0, rowCount)` on every build, and it leaves `props.nav` null,
  as `syncTabListViewport` does. `ListNav::onListRendered` reads `selected` as a row index
  (`list.h:182-201`), so wiring it would be off by one. **`moveSelectionTo` is replaced by a
  `moveRingTo`** modelled on `UiTabListActivity::moveRingTo` (`:49-62`), because `ListNav::follow`
  reads `selected` as a row index. It differs from the tab version in two ways:
  - it passes `visibleIndices_.size()` as the row count to `listTopIndexFor`, where the tab version
    uses `listCount()`, which here is the ring size;
  - it writes `selected` and `top` under `RenderLock`, then calls `requestUpdate()` after releasing
    it, as `UiListActivity::moveSelectionTo` does (`UiListActivity.cpp:72-82`).

  `navigateButtons()` is overridden (A10). Every current `moveSelectionTo` call site
  (`HighlightsActivity.cpp:141, 369, 414`) switches to `moveRingTo`. The base swipe path still
  clamps with `listCount()` (`UiListActivity.cpp:100`), which lets `top` go one row past the end.
  That costs at most one extra refresh, and the next `syncRingViewport` clamp corrects it.
- **Chip actions.** `ACTION_CHIP = ACTION_USER` and `ACTION_MORE = ACTION_USER + 1` are registered
  in `onEnter` after `UiListActivity::onEnter()`, mirroring `BibleSearchActivity.cpp:102-104`. A
  chip's `value` is its index in `chips_`, bounds-checked in the handler. The handler runs A7.
- **`buildScreen`.** After the header margin and `spacer`, as today (`:469-475`), and after the
  empty-publication return (`:479-482`):
  1. Measure each candidate chip with `screen.target().measureText(smallFont, label, style)`, the
     same way `button.h:62` does, plus horizontal padding. Run `TagChips::layout` against
     `screen.body().width`.
  2. `screen.takeTop(lines * chipHeight + (lines - 1) * gap, verticalSpacing)` reserves the band.
  3. Draw each placed chip with `fui::button(screen.frame(), rect, props)` (A11b):
     - `props.state = StateSelected` for the active chip, or for `…` per A5;
     - the A13 styles, with `props.text` explicitly `smallText`, bold only when selected;
     - `inputMask = fui::InputTouch`;
     - `minTouchSize = 0`, and `hitPadding` of half the gap on each edge that faces another chip.
  4. If `nav.selected == 0 && buttonFocus_`, stroke the band with 2 px (A10).
  5. The help band and the list follow as today (`:487-509`), with `syncRingViewport` in place of
     `syncListViewport`.
- **Rebuild points.** Chips are rebuilt wherever rows are: `onEnter`, the filter-picker handler,
  `applyTagEdit` and `deleteHighlight` (`:34-35, 139-140, 363-364, 408-409`). The last three
  already hold `RenderLock` or run where the picker's handler runs, and the chip storage is behind
  the same lock, because `chips_` labels are borrowed by `ButtonProps.label` during the render.
  The chip-tap handler takes `RenderLock` around its rebuild, as `applyTagEdit` does (`:357-365`).
- **`filterSubtitle_` and `computeFilterSubtitle()`** (`HighlightsActivity.h:109, 142`,
  `.cpp:57-61`) exist only for row 0's subtitle, so they are removed. `STR_FILTER_BY_TAG` stays in
  use as the picker's title (`TagFilterActivity.cpp:20`).
- **Class comment** (`HighlightsActivity.h:23-30`) is rewritten for the chip row and the ring.

## Data and control flow

```
onEnter / data change
  └─ rebuildVisibleIndices()          filter via TagChips::passageMatches (A3)
  └─ rebuildRowItems()                passages → rowItems_; activeTags + TagChips::count (locals)
                                      → A1+A2 → chips_ (≤ MAX_CHIPS+1, own labels) + moreCandidates_
render task: buildScreen
  └─ measure chips_ → TagChips::layout → buttons at rects (+ ring-0 outline)
  └─ list(rowItems_) with selectedIndex = ring - 1
loop task: touch
  ├─ ACTION_CHIP(value)  → A7: set filterTagId_, RenderLock{rebuild}, moveRingTo(0)
  ├─ ACTION_MORE         → openTagFilter() (unchanged; its handler rebuilds, then moveRingTo(0))
  └─ ACTION_ROW(value=k) → k>0: jump / long-press actions (unchanged)
loop task: buttons
  └─ Left/Right walk ring 0..N (moveRingTo); Confirm at 0 → openTagFilter(), at k → jump
```

## Resource budget

All allocations happen on data changes (`rebuildRowItems`), never per render. Allocations over
4096 B are auto-routed to PSRAM on this build, and the table states which side each lands on:

| Allocation | Lifetime | Bound | Lands in | Why not stack/static |
|---|---|---|---|---|
| `activeTags()` snapshot | local to `rebuildRowItems` | 200 × `sizeof(TagView)` (~28 B with a 24 B `std::string`) ≈ 5.6 KB at the cap; ~1.3 KB at the user's real 48-tag palette (`TagPalette.h:36`). Names over the SSO limit allocate separately, each < 4 KB. | PSRAM at the cap, internal SRAM at real sizes | Already the store's API (`StudyStore.cpp:129-133`), as `TagFilterActivity` uses; freed on return. |
| `Counts.perTag` | local | ≤ 200 × 2 B = 400 B | internal | Sized to the live palette. |
| sorted id→slot copy inside `count()` | local to `count()` | ≤ 200 × 4 B = 800 B | internal | A fixed 800 B array would be on a 2–4 KB task stack. |
| `chips_` | member | exactly `MAX_CHIPS + 1` = 25 × ~44 B ≈ 1.1 KB | internal | Label storage is borrowed by the render, so it must outlive `rebuildRowItems`. |
| `chipInputs_` + `chipLayout_` | members (inline in the activity object) | 25 × 12 B + (25 × 16 B + 12 B) ≈ 712 B | part of the activity's own heap block | Filled on the render task; as locals they would break the 256 B rule. |

## Error handling

There is no I/O, and this design adds no failure path to the store. The existing failure paths
(save failure on retag or delete, `saveDisabled`) are untouched (`HighlightsActivity.cpp:318-415`).

- A stale chip `value` (the data changed between render and tap) is bounds-checked against
  `chips_.size()` in the handler and ignored, as `rowActionTrampoline` ignores stale rows
  (`UiListActivity.cpp:33-36`).
- A filter on a tag retired elsewhere is still reset by `dropRetiredFilter()` on the existing
  paths (`HighlightsActivity.cpp:63-69, 135, 356`). A2's "or active filter" clause therefore never
  keeps a retired tag's chip on screen: the palette has no active entry for it, so it is not a
  candidate, and its filter has already been dropped.
- A label longer than its chip is ellipsised by the draw target, whose contract is to honour
  `maxLines` and ellipsis truncation (`FreeInkUICore.h:690-691`). `snprintf` truncates safely
  into the fixed buffer, and a UTF-8 name at the 24-byte cap plus a count fits in 40 B.
- A chip tap is followed by a touch-routed repaint. `buttonFocus_` is cleared on any routed touch,
  so the outline disappears as soon as touch is used.
- If the interaction table overflows despite A6, `renderUi()` logs it (`UiAppHost.h:29-31`).
  The host test pins `MAX_CHIPS`.

## Testing strategy

TDD, host suite, in `test/tag_rows/`: a new `TagChipRowTest.cpp` added to the existing
`add_executable(TagRowsTest …)` list in `test/tag_rows/CMakeLists.txt`. That per-directory file is
not the shared root `test/CMakeLists.txt`. The target gains
`${REPO_ROOT}/lib/StudyStore` on its include path and links `ArduinoJson`, because `TagPalette.h`
includes it, mirroring `test/passage_doc/CMakeLists.txt`. The plan must confirm this links; if it
does not, the fallback is a new `test/tag_chips/` directory, and its `add_subdirectory` line is
handed off in the PR body.

Count tests (criterion 1):
- `All` equals the passage count; a multi-tag passage counts under each tag; an UNLABELLED passage
  counts only under `Unlabelled`.
- **Equivalence:** for random tag assignments, each chip's count equals the number of passages for
  which `passageMatches` is true with that filter. `rebuildVisibleIndices` calls the same
  `passageMatches`, so the list and the count cannot diverge.
- Ids that are not active (retired) are not counted under any chip slot. A passage whose only tag
  is retired counts under `All` and under nothing else, so `Unlabelled ≤ All` (A12).
- Zero passages give all counts 0.

Layout tests (criteria 2–3, A4–A6):
- 0 tags: `All` + `Unlabelled` on one line, no overflow.
- Everything fits on one line; wraps to exactly two lines with no `…`.
- More than fits on two lines: `…` is placed last on line 2 and never beyond `lineWidth`; the chips
  before it are the input prefix, in order.
- `…` fits even when its would-be neighbour must be dropped.
- A single chip wider than the line is clamped to `lineWidth`.
- More than `MAX_CHIPS` narrow chips give `placedCount ≤ MAX_CHIPS + 1` and `overflow == true`.
- No placed rect exceeds `lineWidth`, and `lines ≤ 2`, for every candidate count from 0 to 60.
- **Hit rects never intersect (A11b):** for each placed chip, the visual rect grown by its
  `hitPadding` (half the gap on each inner edge) does not intersect any other chip's. The layout
  therefore reports each chip's edges, so the activity and the test compute padding the same way.
- **Selection-independent layout (A13):** widths come from the bold measurement, so the placements
  are identical whichever chip is selected. The test pins this by running `layout()` on one width
  set, since `layout()` never sees the selection.
- The `moreCandidates_` bound: 26+ candidates, truncated to 25 inputs, still yield `overflow`.

Ring mapping stays pinned: `activateIndex(0)` opens the picker and row k maps to
`visibleIndices_[k-1]`, both unchanged. There is no new host test for the activity itself; the
activity depends on the renderer, and no suite hosts one today.

Verification the implementer reports: `pio run` (x4pro) builds; the host suite passes;
`./bin/clang-format-fix` over the whole tree. **Flagged for the human on device:** counts against a
known publication; tapping each chip; `…` with a 30+ tag palette; tapping chips on line 1 near their bottom edge (A11b, the line pitch
is below the 44 px token); Power-as-Confirm and Left/Right walking onto the chip row, with the
outline showing only then (A10); free heap before and after one enter/exit of Highlights, which should
not leak.

None expected: no translation key (A9) and no root `test/CMakeLists.txt` line, unless the fallback
