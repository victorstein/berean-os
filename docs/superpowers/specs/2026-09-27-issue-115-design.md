## Problem

The Meetings screen is a three-row text list: Watchtower, Workbook and Refresh, each
row carrying a one-word status (`src/activities/network/MeetingsActivity.cpp:62-81,
97-128`). It shows no cover, no dates and no reading progress, and it has no sense of
the week. The launcher tile in front of it already shows this week's cover
(`src/activities/launcher/LauncherActivity.cpp:156-163`), so the screen behind the
tile is the poorer of the two.

## Goal

Replace the list body with a week card (mockup, sixth screen:
https://claude.ai/artifact/AQwedpQgJDr4vAdsPdJYBb):

1. A header, "Reuniones", with the Monday–Sunday range of the week being shown
   beneath it.
2. A seven-cell week strip, Monday first. Today is inverted, the user's meeting days
   carry a dot, and a one-line legend sits underneath.
3. One card per publication the week carries, Watchtower first. Each card has a cover
   thumbnail, the title and issue, and either a reading-progress bar with a label or
   the row's current status word. Tapping a card does what tapping the row does today.
4. Refresh, as today.

Plus two persisted settings, `midweekMeetingDay` and `weekendMeetingDay`.

## Non-goals

- Naming the week's study article. `MeetingWeekEntry` holds only the issues
  (`src/network/MeetingWeekTable.h:16-20`).
- Reminders or notifications.
- Changing what "this week" means anywhere else on the device. See A3; the UTC week
  boundary is recorded as a follow-up.
- Changing how the reader reads `progress.bin`. The new parser mirrors it; the reader
  is not refactored onto it (A9).
- Any new on-disk format or any new write. This screen only reads existing files.

## Assumptions (each is a decision the review should attack)

**A1 — Progress comes from `book.bin` and `progress.bin` through `Epub::load(false, true)`,
without opening the zip.** Research §3 established that the cheap path exists.
`Epub::load` with `buildIfMissing = false` and `skipLoadingCss = true` loads
`book.bin` through `BookMetadataCache::load()` (`lib/Epub/Epub.cpp:374`,
`BookMetadataCache.cpp:460-499`). It returns at `Epub.cpp:409` without touching the
zip, and at `:413-415` without building when the cache is absent. The percentage is
then `Epub::calculateProgress` itself (`Epub.cpp:924-933`). Reusing it rather than
re-deriving its arithmetic keeps the spine-size weighting identical to the reader's.
The cost is one `CssParser` object constructed and cleared (`:367`, `:407`), which is
accepted over a duplicated formula. The issue's fallback, "no bar until opened this
session", is therefore not taken.

**A2 — The percentage is the reader menu's formula applied to the *saved* position, and
it is an approximation in one stated case.** The reader menu computes
`clampPercent(int(calculateProgress(spine, currentPage / estimatedTotalPages) * 100 + 0.5))`
from the **live** section, and it skips the calculation entirely when
`estimatedTotalPages()` is 0 (`src/activities/reader/EpubReaderActivity.cpp:296-303`).

In the normal case, `progress.bin` stores `spine`, `section->currentPage` and
`section->estimatedTotalPages()` as they were at the last render
(`EpubReaderActivity.cpp:1304-1306` → `EpubReaderUtils.h:14-37`). The card applies
the same expression to them, so it shows the reader's number for the position last
saved, under the layout in force when it was saved.

**The stated divergence** (pass 0, MAJOR 1): when the reader is destroyed with a
non-empty return stack, which is every exit after following an in-book link or
footnote, it overwrites `progress.bin` with the stack's origin and a **page count of
0** (`EpubReaderActivity.cpp:160-166`; the stack is pushed at `:1701-1703`). In that
state the card shows the percentage at the **start of the saved chapter**, while the
reader, once reopened, shows the true page. The gap is at most one spine item's share
of the issue. This is accepted. Recovering the page fraction would mean reading the
section cache's layout format from this screen, which couples it to
`SECTION_FILE_VERSION` for a one-chapter error.

The parse rules mirror the reader's reader (`EpubReaderActivity.cpp:213-232`):
- only 4-, 6- or 10-byte files are accepted;
- `page == 0xFFFF` is the stale sentinel and counts as page 0;
- a 4-byte legacy file has no page count, so the chapter fraction is 0;
- a page count of 0 also gives a chapter fraction of 0.

Two guards the reader does not need, because it never feeds a corrupt file into
`calculateProgress` unchecked (pass 0, MINOR 1):
- `spine >= epub.getSpineItemsCount()` is **unreadable**. It would wrap the `size_t`
  subtraction at `Epub.cpp:928-929`, so it gives no bar, as in A6's "Open" row.
- `roundPercent` clamps the fraction to `[0, 1]` as a float **before** multiplying and
  converting to `int`, so no out-of-range float is ever converted.

Like the reader, the card never shows exactly 100% on the last page. That is accepted
as parity, not fixed here.

**A3 — "This week" stays the UTC ISO week; only "today" on the strip is local.** Every
existing week computation feeds the RTC's UTC date straight into
`isoWeekFromUtcDate` (research §6): `MeetingsActivity.cpp:40`,
`LauncherActivity.cpp:178`, `MeetingDownloadActivity.cpp:129` and
`MeetingWeekPrefetch.cpp:31`.

The cache key, and therefore which publications the cards show, stays on that
definition. If this screen alone switched to a local week, then on a Sunday evening
west of UTC its header would disagree with the launcher tile. The resolve it
launches, which the downloader computes in UTC, would then fetch a week this screen
is not looking for.

The inverted "today" cell, however, uses the **local** date: the UTC date and time
shifted by `SETTINGS.clockUtcOffsetQ` (quarter-hours biased by 48,
`src/CrossPointSettings.h:259-262`, decoded as `HalClock::formatTime` does it at
`lib/hal/HalClock.cpp:59-66`). A cell is inverted only when the local date falls
inside the week being shown. So on a Sunday evening at UTC−6 the strip may show next
week with no cell inverted. That is honest, where inverting UTC's "Monday" would not
be. Moving the device's week boundary to local time is a follow-up issue listed in the
PR, not this change.

Accepted skew (pass 0, MINOR 6): `getDate` reads the RTC fresh
(`HalClock.cpp:42-52`), while `getTime` may return a value cached for up to
`CLOCK_POLL_MS = 10000` (`HalClock.h:17`). Within about 10 s of UTC midnight the pair
can straddle the day boundary, and the inverted cell is then a day off until the next
render. That is cosmetic and brief. A combined date-and-time read belongs to the HAL
(hal-dev's surface) and is out of scope.

**A4 — The header and strip describe the week whose publications are on the cards.**
Today the screen falls back to `table.newest()` when the current week is not cached
(`MeetingsActivity.cpp:54, 59`). Labelling last week's cards with this week's dates
would be false. So the week shown is chosen like this:
- The entry for the current week, if it is held.
- Otherwise the entry actually displayed, with its week parsed back from its key
  (`"2026-38"`, `MeetingWeekTable.h:22-25`).
- Otherwise, when no entry exists at all, the current UTC week.
- With no usable clock and no entry: no range line and no strip, only the title.

The auto-resolve flow (`resolvePending_`, `MeetingsActivity.cpp:53, 84-95`) is
unchanged. When it lands, `refresh()` re-runs and the header moves with the cards.

**A5 — Cards: one per publication the displayed entry carries, Watchtower first.** An
entry with an empty `workbook` (the Memorial week, `MeetingWeekTable.h:14-15`) shows
one card, the Watchtower. An entry with an empty `watchtower` shows one card, the
workbook; this is symmetric and costs nothing. With **no** entry, both cards are
shown with "This week's publications are not known yet"
(`STR_MEETING_WEEK_UNKNOWN`), exactly as the rows do today (`:78-79`), because tapping
one is how a resolve starts (`:143-145`). Refresh is always the last item. So
`listCount()` is the number of cards plus 1, which is 2 or 3.

This drops today's third status, "No workbook is published for this week"
(`STR_WORKBOOK_UNAVAILABLE`, `:76-77`). The card is simply absent. The string stays in
the YAML because the key is shared and removing it is not this change's business.

**A6 — What each card shows.**

| State | Cover | Line under title | Bar |
|---|---|---|---|
| On the card and `book.bin` loads | thumbnail (A7) | "`N`% read" (new `STR_MEETING_PROGRESS`) | yes, `N`/100 |
| On the card, `progress.bin` absent | thumbnail | "0% read" | yes, empty |
| On the card, `Epub::load(false, true)` fails, or the saved spine is out of range (A2) | thumbnail or placeholder | "Open" (`STR_OPEN`) | no |
| Issue known, not on the card | placeholder | "Download" (`STR_DOWNLOAD`) | no |
| No entry | placeholder | `STR_MEETING_WEEK_UNKNOWN` | no |

An unread publication shows an empty bar at 0%. It is on the card and has not been
read, which is exactly what an empty bar says.

"No bar" means `BookCardProps::progressMax = 0`. `bookCard` draws its bar whenever
`progressMax > 0`, and the default is 100 (`book-card.h:21, 133-140`). The placeholder
is `bookCard`'s own dithered light-grey cover fill, drawn when the `coverPainter`
returns false (`book-card.h`, `if (!coverDrawn) fill(...)`). The title is
`nameFor(pub)` plus the issue, as the row label is today (`:69-70`).

Activation is unchanged:
- Path present → `activityManager.goToReader(path)`.
- Anything else → a non-forced resolve (`:138-145`).
- Refresh → a forced resolve (`:133-135`).

**A7 — Cover thumbnails reuse the launcher's path, extracted into one shared helper.**
`LauncherActivity::coverThumbFor` (`:271-289`) and `drawCoverNative` (`:357-376`) move
into `src/util/CoverThumb.{h,cpp}` as free functions. The launcher calls through them,
and its behaviour is unchanged.
- `drawCoverNative` loses its launcher dependencies: it takes the renderer, and takes
  the corner radius as a parameter (the launcher passes `TILE_RADIUS / 2`, `:375`).
- The log tag becomes the helper's own `"COVER"`.
- Both keep their rules: the thumbnail is requested at exactly the drawn height and is
  never rescaled (`:261-266`, `:367-370`).

The card's thumbnail height is derived from the layout (A8), so it is cached once per
screen geometry at `thumb_<h>.bmp` (`lib/Epub/Epub.cpp:668`). On a publication's
first visit it is **generated**, and when `book.bin` does not exist yet that includes
`epub.load(true, true)` (`LauncherActivity.cpp:283`). This mirrors the launcher,
which also generates synchronously before its first paint (`:74-80`). The first visit
is slower. Later visits only draw.

**A8 — Layout is computed before the thumbnails, from theme metrics and the panel size,
never from constants.** As in `LauncherActivity::onEnter` (`:74-80`, "layout first"),
a `computeLayout()` runs in `onEnter()` before `refresh()`. It derives:
- the range band height from a text line height;
- the strip cell size from the body width divided by 7;
- the legend line;
- `refreshH`, the Refresh band, which is
  `max(metrics.listWithSubtitleRowHeight, renderer.getLineHeight(body) + renderer.getLineHeight(small))`.
  The body and small fonts are the IDs `uiScaleSpec()` binds (`src/components/UIScale.h:16-17`).
  `list()` grows a subtitle row to at least those two line heights, and drops any row
  taller than its band (`list.h:436-446`). On Classic the metric alone is 50
  (`BaseTheme.h:134`) against 29 + 24 = 53 (pass 1, MAJOR 1). The band is taken
  from the bottom of the body with `takeBottom(refreshH)`
  (`freeink-sdk/libs/ui/FreeInkUI/include/FreeInkApp.h:85`), so it can never be
  squeezed out by the cards;
- the card height, from what remains, split for **two** cards even when only one is
  shown, so the Memorial week does not generate a second thumbnail size;
- the cover height `h` = card height minus `bookCard`'s vertical padding. This is the
  only size the thumbnail is requested at;
- the placeholder box `{placeholderW, h}`, with
  `placeholderW = int(h × PLACEHOLDER_COVER_ASPECT)` and
  `static constexpr float PLACEHOLDER_COVER_ASPECT = 0.75f`. That is the top of the
  launcher's "roughly 0.6-0.75" (`LauncherActivity.cpp:54-58`), so a placeholder is as
  wide as the widest expected cover (pass 1, MAJOR 2).

**Every band is always reserved** (pass 1, MINOR 2). The range band, the strip and the
legend are reserved at fixed heights in `computeLayout()`, whatever `refresh()` later
finds, and are left blank when their content is absent: no clock, both meeting days
unset, or a failed date. `buildScreen` places the cards and Refresh from `Layout`'s
rects only, never from what `screen.body()` has left. So `h`, and with it
`thumb_<h>.bmp`, depends only on the theme and the panel. It does not change when the
clock or a meeting-day setting changes.

**The cover's width is not predicted; it is measured** (pass 0, BLOCKER 1).
`generateThumbBmp` passes `height * 0.6` only as a *target* (`Epub.cpp:706-709`, and
the PNG branch the same way). The 1-bit converters run in crop mode:
- they scale by the **larger** of the two fit ratios (`JpegToBmpConverter.cpp:582-589`,
  called with `crop = true` at `:731-733`; `PngToBmpConverter.cpp:588-594, 848-850`);
- they write the scaled image at full size, with no later crop.

So a cover of aspect `a ≥ 0.6` comes out `a·h` wide and `h` tall. The launcher's own
note says covers run "roughly 0.6-0.75" (`LauncherActivity.cpp:54-58`).

`refresh()` therefore reads each generated thumbnail's BMP header (new
`CoverThumb::sizeOf`, the same `Bitmap::parseHeaders` call `drawCoverNative` makes at
`LauncherActivity.cpp:360-366`) and stores its real `coverWidth`/`coverHeight` on the
card. `buildScreen` sets `BookCardProps::coverSize` to exactly that size, so
`drawNative`'s box equals the bitmap and the never-rescale rule holds.

A measured size is **usable** only if `height <= h` and `width <= cardContentWidth / 2`.
Anything else gets the placeholder box, and `CoverThumb::drawNative` is not attempted:
- A cover narrower than 0.6 comes out `0.6·h` wide and **taller** than `h`. The
  launcher has the same limit for the same reason (`LauncherActivity.cpp:370`), and JW
  covers are not that narrow.
- A square or landscape image would take the text column
  (`book-card.h:89-90`) down to nothing, so it is refused as too wide (pass 1, MINOR 1).

Both are stated, not fixed.

The two cards' covers may differ in width, so each card's text column starts at its
own cover's right edge. `bookCard` already lays out that way (`book-card.h`,
`content.x = coverRect.right() + props.gap`). All of it stays inside
`getScreenSafeArea` and the header band, as `buildScreen` already does
(`MeetingsActivity.cpp:98-105`).

**A9 — Keep `UiListActivity`; draw the cards as `fui::bookCard` hits on `ACTION_ROW`.**
`UiListActivity`'s header says multi-widget screens should use `UiAppHost` directly
(`src/activities/UiListActivity.h:15-16`). This screen is still one ordered set of
activatable items (cards, then Refresh) with one selection. Keeping the base keeps its
Back/Confirm, tap routing, Left/Right stepping and render skeleton
(`UiListActivity.cpp:47-121, 152-169`), where moving would rewrite them.

The cards are drawn with FreeInkUI's `bookCard`
(`freeink-sdk/libs/ui/FreeInkUI/include/components/media/book-card.h`), which already
registers an `ACTION_ROW` hit with its `value` (`frame.hit(..., props.action,
props.value, ...)`). Its `coverPainter` hook calls the shared `drawCoverNative`.
Refresh is a one-item `fui::list` whose item `actionValue` is the card count; hits
carry `item.actionValue` (`list.h:475-477`).

`bookCard` settings (pass 0, MINOR 4):
- `selectionIndicator = BookCardSelectionIndicator::CoverFrame` (`book-card.h:55-57,
  79-88`). The default `Card` indicator inverts the whole card, and the bar's fill is
  fixed solid black (`book-card.h:137-138`), so the filled part would vanish on a
  selected card.
- `titleText` and `metaText` are set from `screen.theme()` explicitly, because
  `Screen::bookCard` passes the props through unthemed (`FreeInkApp.h:373-379`).
- The card is drawn into an explicit `Rect` from the layout, with `ui::bookCard(screen.frame(),
  rect, props)`, rather than `Screen::bookCard`'s default `theme_.rowHeight * 2`
  height.

Selection is drawn by setting `StateSelected` on the card when `nav.selected == i`, and
`selectedIndex = 0` on the Refresh list when `nav.selected == cardCount`.

Refresh (pass 0, MINOR 3): the Refresh list is given the band reserved by
`takeBottom(refreshH)` (A8), with `props.rowHeight = refreshH` and the subtitle style's
`maxLines = 1`. `list()` breaks off any row that does not fit its band
(`list.h:444-446`), so the row height must equal the band. On this touch board
`props.rowHeight` would otherwise stay at the theme's `rowHeight`
(`UiListActivity.cpp:124-136` overrides it only for non-touch hardware).

Everything fits one page, so the viewport's `top` is ignored and
`syncListViewport` is not called. Two consequences are handled (pass 0, MINOR 5):
- **Swipes.** With no sync, `nav.visibleRows` stays 1 (`list.h:148`), and a vertical
  swipe would move `top` and `requestUpdate()`, which is a full refresh that changes
  nothing (`UiListActivity.cpp:90-101`). `handleCustomInput()` consumes Up and Down
  swipes and returns true, before the base loop sees them (`UiListActivity.cpp:84`).
- **Stale selection.** `refresh()` can drop `listCount()` from 3 to 2, for example
  when a resolve returns the Memorial week. Afterwards it clamps `nav.selected` into
  `[0, listCount() - 1]` under a `RenderLock`, as `moveSelectionTo` does
  (`UiListActivity.cpp:71-81`). Otherwise Confirm would be ignored
  (`UiListActivity.cpp:53-54`).
The precedent for chrome drawn above a list inside a `UiListActivity` is
`EpubReaderMenuActivity::buildScreen` (`EpubReaderMenuActivity.cpp:182-191`, a
`takeTop` band before the list). No firmware screen calls `bookCard` yet (research §5),
so this is its first use. It is an SDK widget, not a new pattern.

**A10 — Settings: two enums in the System category, next to `meetingPrefetch`.** The
issue offers Reader or a new Meetings category. Neither fits well:
- A meeting day is not a reader setting.
- A new category is a fifth tab plus a new vector and switch arm in
  `SettingsActivity` (`src/activities/settings/SettingsActivity.cpp:34-35, 51-72`).
  That widens the change for two rows.

The existing meeting settings, `publicationLanguage` and `meetingPrefetch`, already
live in `STR_CAT_SYSTEM` (`src/SettingsList.h:380-383`). This is a deliberate
deviation from the issue's two options, and the review should attack it.

Values: `0 = Not set` (default), `1..7 = Monday..Sunday`. These match ISO weekday
numbers, so a stored value compares directly with a date's weekday. Labels are
assigned by enum value, as `SettingsList.h:231-248` requires, using the existing
`STR_NOT_SET` plus seven new weekday keys. Persistence is automatic through
`toJson`/`fromJson`: a missing key takes the default, and an out-of-range value
clamps to it (`CrossPointSettings.cpp:63-84, 163-169`). There is no
`FORMAT_VERSION` bump (`CrossPointSettings.h:428`). Both settings are also exposed in
the web settings API, like every keyed `SettingInfo`.

**A11 — Two settings on the same day draw one dot.** The strip marks meeting days, and
the legend reads "Meeting day" (new `STR_MEETING_DAY_LEGEND`). It does not tell
midweek from weekend. Both unset means no dots and no legend line.

**A12 — The date text is translated with whole-phrase formats in a fixed argument order.**

| Key | English | Spanish |
|---|---|---|
| `STR_MEETING_WEEK_RANGE` (same month) | `"Week of %u–%u %s"` | `"Semana del %u al %u de %s"` |
| `STR_MEETING_WEEK_RANGE_SPAN` (two months) | `"Week of %u %s – %u %s"` | `"Semana del %u de %s al %u de %s"` |

A week that spans two years uses the two-month form; the year is not shown. The
argument order is (day, [month], day, month) in every language, so no positional
`%1$` specifiers are needed.

Full month names come from one space-separated key, `STR_MONTHS_LONG`, and the strip
letters from `STR_WEEKDAYS_NARROW` (`"M T W T F S S"` / `"L M X J V S D"`). This
follows the `STR_MONTHS_SHORT` precedent: "without twelve more keys"
(`lib/Catalog/Catalog/CatalogStamp.h:38-43`, `spanish.yaml:381`).

The weekday labels in the settings enum need one `StrId` each, because
`SettingInfo::Enum` takes `std::vector<StrId>` (`SettingsList.h:245-247`). Hence
`STR_MONDAY` … `STR_SUNDAY`.

**Every word taken from these lists is copied into a `char[]` with
`snprintf(buf, n, "%.*s", len, data)` before it reaches a translated `%s` format or a
text draw** (pass 1, MINOR 3). A `wordAt` view points into the middle of the translated
string and is not null-terminated (`CLAUDE.md`, "`std::string_view` and null
termination"). The catalog precedent gets away without the copy only because it owns
its format and uses `%.*s` (`CatalogStamp.cpp:82`). A translator's `%s` format cannot
do that.

The tokenizer `wordAt` is file-local to `CatalogStamp.cpp`. A four-line equivalent
lives in the new pure module rather than widening `lib/Catalog`'s public API for a
non-catalog caller.

### `src/network/WolWeekScan.{h,cpp}`: calendar helpers beside `isoWeekFromUtcDate`

Added here, not in a new file, because the Hinnant `daysFromCivil` these need is
file-local to `WolWeekScan.cpp` (`:20-29`). Four host suites already compile this
`.cpp` (`test/wol_week_scan`, `meeting_week_table`, `meeting_filename`,
`month_name_map`), so no test CMake changes are needed. Modelled on
`isoWeekFromUtcDate` (`WolWeekScan.cpp:41-60`).

```cpp
struct CivilDate { uint16_t year = 0; uint8_t month = 0; uint8_t day = 0; };

// ISO weekday, 1 = Monday .. 7 = Sunday. 0 for an invalid date.
uint8_t isoWeekday(const CivilDate& date);
// The date `days` after (or before) `date`.
CivilDate addDays(const CivilDate& date, int days);
// Monday of an ISO week (week 1 contains the year's first Thursday). False for a
// week the year does not have: validated by round trip, so {2025, 53} is refused
// rather than dated as 2026/W01.
bool mondayOfIsoWeek(const IsoWeek& week, CivilDate& out);
// Local calendar date from the RTC's UTC date and time and the biased
// quarter-hour offset the clock setting stores (48 = UTC+0).
bool localDateFromUtc(const CivilDate& utc, uint8_t hour, uint8_t minute, uint8_t offsetQuarterHoursBiased,
                      CivilDate& out);
```

`addDays` uses `daysFromCivil` and a new file-local `civilFromDays`, its Hinnant
inverse. `mondayOfIsoWeek` computes the candidate Monday as the Monday on or before
January 4th of `week.year`, plus `7 × (week − 1)` days. It then returns true only if
`isoWeekFromUtcDate(candidate)` gives back the same year and week (pass 0, MINOR 7).
`localDateFromUtc` clamps the offset exactly as `HalClock.cpp:61-62` does.

## Error handling

| Failure | Behaviour |
|---|---|
| No RTC or oscillator stopped (`HalClock.h:36-41`) | As today, `LOG_ERR` and the newest entry. The header week comes from the entry's key (A4). No inverted cell. With no entry either: title only. |
| `getTime` fails but `getDate` succeeds | No local today, so no inverted cell. The week is unaffected. |
| `mondayOfIsoWeek` / `isoWeekFromKey` fails | No range line and no strip, with a `LOG_ERR` that has exact specifiers (`%u` with `static_cast<unsigned>`, as `WolWeekScan.cpp:66-67` does). |
| `formatWeekRange` buffer too small | No range line, with a `LOG_ERR`. It never truncates mid-UTF-8. |
| Thumbnail generation fails | `LOG_DBG` inside `CoverThumb::pathFor` (as `:285` today), and the placeholder cover. |
| Thumbnail header unreadable, taller than `h`, or wider than half the content width (A8) | The placeholder box `{placeholderW, h}`, and a `LOG_DBG` with the measured size. |
| `book.bin` absent or wrong version | No bar, status "Open" (A6). |
| Saved spine at or beyond the spine count (corrupt or stale `progress.bin`) | No bar, status "Open" (A2, A6). |
| `progress.bin` absent or wrong size | 0% (A2, A6). |
| Card count 0 | Impossible by A5 (no entry → both cards; an entry has at least one issue: empty scans are refused before caching, `MeetingDownloadActivity.cpp:218-221`, `MeetingWeekPrefetch.cpp:84-87`). Guarded anyway: `listCount()` is at least 1 (Refresh). |

Nothing on this screen writes, so the storage-discipline rules for stores do not
apply. All reads go through `HalStorage` (`CLAUDE.md`, "SdFat is not thread-safe").
