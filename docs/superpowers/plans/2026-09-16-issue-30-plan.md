## Change to the spec: A10 is amended, not followed

**The spec's A10 says no host test is added. This plan adds one.** That reverses
a reviewed assumption, so here is the evidence that A10's premise was wrong,
stated up front for the next review to attack first.

A10 argued: "none [of the suites] constructs an activity, because that needs the
renderer, the theme, `HalStorage` and `Epub` … Testing a two-boolean ternary
would mean extracting it into a free function the reference implementation does
not have — inventing a pattern for one line." Both halves fail against the tree:

1. **Nothing needs to construct an activity.** `test/return_stack/` compiles
   `src/activities/reader/ReturnStack.h` on the host with `${REPO_ROOT}/src` as
   its only extra include directory
   (`test/return_stack/CMakeLists.txt:1-16`, `test/return_stack/ReturnStackTest.cpp:3`).
   Testing a small unit that lives *beside* an activity is an established
   pattern in this repo.
2. **The stub this needs already exists.** `test/stubs/HalDisplay.h:18-21`
   declares `HalDisplay::RefreshMode { FULL_REFRESH, HALF_REFRESH, FAST_REFRESH }`
   — the same three enumerators in the same order as `lib/hal/HalDisplay.h:14-17`
   — and `test/pagination/CMakeLists.txt:26` shows the established way to put
   `${REPO_ROOT}/test/stubs` on a suite's include path so `<HalDisplay.h>`
   resolves to it.
3. **A free-function header beside an activity is not an invented pattern.**
   `src/activities/reader/ReaderUtils.h:131` is exactly that — `inline bool
   isInMenuZone(...)` and siblings, free functions in an activity directory.

The extraction also earns its place independently of the test. The spec's own
review found MINOR 1: the log field `first` printed the negation of
`firstRenderDone`, and every testing expectation depended on that inversion.
That is a polarity bug in a two-boolean expression, which is precisely what a
four-case truth table pins and what no amount of reading catches reliably. The
helper is `constexpr`, header-only and generates no code of its own, so it costs
no flash and no RAM (CLAUDE.md, "constexpr first").

**What does not change:** the design. `HALF_REFRESH` on the first paint of a
flagged entry, the `firstRenderDone` latch, the defaulted constructor parameter,
`goHome`'s unchanged signature, `initialMenuItem` still discarded. A1–A9 and A11
are implemented as written.

**Steps 2–5 have no automated test and cannot have one.** Their gate is the
compiler plus the serial check in step 7. Do not invent a test for them.

## Step 1 — the decision helper, test first

### Red

Create `test/launcher_refresh/LauncherRefreshTest.cpp`:

```cpp
#include <gtest/gtest.h>

#include "activities/launcher/LauncherRefresh.h"

// The launcher's first paint after a wake has to be non-differential: the panel
// is still showing the sleep screen, and a differential refresh only drives the
// pixels that differ from a baseline that does not contain it. Every later paint
// in the same entry is an ordinary fast refresh.
//
// The second argument is "this entry has already painted", not "this is the
// first paint". That polarity is the one thing a caller can silently invert, and
// the launcher reads it before setting its own latch -- so it is pinned here.

TEST(LauncherRefresh, FirstPaintOfAFlaggedEntryIsNonDifferential) {
  EXPECT_EQ(launcherRefreshMode(true, false), HalDisplay::HALF_REFRESH);
}

TEST(LauncherRefresh, LaterPaintsOfAFlaggedEntryAreFast) {
  EXPECT_EQ(launcherRefreshMode(true, true), HalDisplay::FAST_REFRESH);
}

TEST(LauncherRefresh, AnUnflaggedEntryIsFastFromItsFirstPaint) {
  EXPECT_EQ(launcherRefreshMode(false, false), HalDisplay::FAST_REFRESH);
  EXPECT_EQ(launcherRefreshMode(false, true), HalDisplay::FAST_REFRESH);
}

TEST(LauncherRefresh, ResolvesAtCompileTime) {
  static_assert(launcherRefreshMode(true, false) == HalDisplay::HALF_REFRESH);
  static_assert(launcherRefreshMode(false, false) == HalDisplay::FAST_REFRESH);
  SUCCEED();
}
```

### Green

Create `src/activities/launcher/LauncherRefresh.h`:

```cpp
#pragma once

#include <HalDisplay.h>

// The refresh mode for one launcher paint.
//
// cleanInitialRefresh is set by the wake path when the panel is still showing a
// frame the launcher did not draw: the sleep screen, after a wake that found no
// Quick Resume frame on the card. A differential refresh cannot clear that, so
// the first paint of such an entry must be non-differential. Every later paint
// in the same entry diffs against a baseline the launcher itself drew, so it
// takes the ordinary fast refresh.
//
// firstRenderDone is "this entry has already painted" -- the first paint passes
// false. Inverting it silently costs the wake paint its clean.
constexpr HalDisplay::RefreshMode launcherRefreshMode(const bool cleanInitialRefresh,
                                                      const bool firstRenderDone) {
  return cleanInitialRefresh && !firstRenderDone ? HalDisplay::HALF_REFRESH : HalDisplay::FAST_REFRESH;
}
```

Then replace the last statement of `LauncherActivity::render`, currently line
473:

```cpp
  renderer.displayBuffer();
}
```

with:

```cpp
  const auto mode = launcherRefreshMode(cleanInitialRefresh, firstRenderDone);
  LOG_DBG(MODULE, "Paint: clean=%d firstPaint=%d mode=%s", cleanInitialRefresh ? 1 : 0,
          firstRenderDone ? 0 : 1, mode == HalDisplay::HALF_REFRESH ? "HALF" : "FAST");
  renderer.displayBuffer(mode);
  firstRenderDone = true;
}
```

Three things to get right, each of which the spec calls out:

- **No `requestUpdate()` after this** (spec A3). `HomeActivity.cpp:308-311` calls
  one behind `!firstRenderDone` because it paints a skeleton and loads recents
  afterwards. The launcher resolves everything in `onEnter`
  (`LauncherActivity.cpp:65-72`) and has no second pass. Adding it would put a
  second full-screen refresh on every launcher entry.
- **`firstPaint` is the negation of `firstRenderDone`** (spec A8, review MINOR 1).
  It is read before the latch is set. `firstRenderDone ? 0 : 1`, not
  `firstRenderDone ? 1 : 0`.
- **The latch is set unconditionally** (spec A6), after the paint, not inside a
  branch.

`MODULE` is already defined in this file as `"LAUNCH"` (line 39). `LOG_DBG`
compiles out at `LOG_LEVEL=1`, the release env, so this ships as nothing.

No test runs here. Do not build the firmware yet.

## Step 7 — hand back

Say plainly what was and was not verified. What you can claim: the host suite
passes, `pio run` succeeds, the formatter is clean. What you cannot: anything
about the panel.

Leave these for the human tester, from the spec's testing section. With a dev
build flashed and `python3 scripts/debugging_monitor.py` attached:

1. Sleep screen set to anything but Quick Resume (default is `DARK`). Sleep,
   wake. Expect `[DBG] LAUNCH Paint: clean=1 firstPaint=1 mode=HALF`, and exactly
   one `Paint:` line for that entry. Other `LAUNCH` lines are normal —
   `resolveTargets` logs the meeting publication and any generated thumbnail.
2. Press a nav button on the launcher. Expect `clean=1 firstPaint=0 mode=FAST`.
3. Sleep screen set to Quick Resume. Sleep, wake. Expect
   `clean=0 firstPaint=1 mode=FAST`.
4. Home gesture back to the launcher from the reader. Expect
   `clean=0 firstPaint=1 mode=FAST`.
5. Exactly one refresh per launcher entry. A second full-screen refresh on entry
   means step 3's "no `requestUpdate()`" was violated.

And state the limit explicitly, because it is the thing most likely to be
misread as a failed fix: **on a default unit there is no visible difference
before and after.** All three X4 Pro panel drivers already force the first paint
after a wake to be non-differential. The change matters on an SSD1677 unit with
`fadingFix` persisted to 1 through the web settings API, and as the thing that
keeps the paint correct if the pinned `freeink-sdk` ever changes. Anyone
reporting "no ghosting after the fix" without checking the unedited build on the
same unit has measured nothing.

Two items the spec defers to a follow-up, not to be done here:

- The comment at `src/main.cpp:453-456` is wrong for all three X4 Pro drivers
  (spec A7).
- The `BootResume::Silent` route at `src/main.cpp:566` reaches the launcher in
  the same stale-frame state and passes no flag (spec Non-goals, review MAJOR 2).
  The fix is passing `true` there; it is an edit to `src/main.cpp`, which A7
  defers.
